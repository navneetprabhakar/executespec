## Recovery options (ordered by cost + risk)

### Option A — re-submit a fresh run (recommended)

Resubmit the same spec from the dashboard's compose surface. New run
gets a new id, fresh workspace clone, fresh execution. Original run
`7483896a` stays as-is in the DB as a historical record.

- Cost: ~$18 (one full run)
- Time: ~90 minutes (run length matches original)
- Pros: clean state, no DB poking, no risk of inconsistency.
- Cons: doubles spend on this spec; loses the running diagnostic
  thread that's been building on `7483896a`.

### Option B — retry with PR #99 deployed (after merge)

After PR #99 merges + deploys to dev, the retry path will correctly
SKIP_TERMINAL on COMPLETE tasks. With the cancel-cascade fix in the
same PR, future cancels won't overwrite remaining tasks.

But the run state is already corrupted. Options before retry:

1. **SQL-restore the corrupted task statuses** to their pre-retry
   values. Risky — touching prod data:
   ```sql
   -- BEFORE: snapshot the current state for rollback safety.
   COPY (SELECT * FROM agent_task WHERE run_id = '7483896a-efd6-46be-9ce7-035902797c02')
   TO '/tmp/agent_task_7483896a_backup.csv' CSV HEADER;

   -- T11, T13, T14, T15, T16, T20: were COMPLETE. Restore.
   UPDATE agent_task
   SET status = 'COMPLETE',
       last_llm_failure = NULL,
       completed_at = '...'  -- specific original timestamps from logs
   WHERE run_id = '...' AND task_id IN ('7483896a_T11', '7483896a_T13', ...);

   -- T17, T19: were PARTIAL. Restore.
   UPDATE agent_task SET status='PARTIAL', last_llm_failure=NULL
   WHERE run_id = '...' AND task_id IN ('7483896a_T17','7483896a_T19');

   -- T12 (FAILED VARCHAR-overflow), T18 (FAILED stagnation): keep
   -- FAILED but null out the spurious BackOffInterruptedException
   -- reason.
   UPDATE agent_task SET last_llm_failure = NULL
   WHERE run_id = '...' AND task_id IN ('7483896a_T12','7483896a_T18');

   -- Reset run row to COMPLETE so retry-task is allowed.
   UPDATE pipeline_run SET status='COMPLETE', failure_reason=NULL
   WHERE run_id = '7483896a-efd6-46be-9ce7-035902797c02';
   ```
   Original timestamps need to be pulled from VM journalctl —
   `persistTaskStatus: 7483896a_TN -> COMPLETE` events between
   `01:10:47` and `02:33:34` UTC on 2026-05-10. **NOT recommended
   without explicit user sign-off** — production data mutation.

2. **Discard the working-tree drift** in the workspace before retry,
   so the LLM doesn't re-process its own duplicate edits:
   ```bash
   sudo bash -c 'cd /opt/app/workspace/7483896a-.../repos/pplai-api && \
     git -c safe.directory=* checkout HEAD -- .'
   sudo bash -c 'cd /opt/app/workspace/7483896a-.../repos/frontend && \
     git -c safe.directory=* checkout HEAD -- .'
   sudo bash -c 'cd /opt/app/workspace/7483896a-.../repos/pplai-frontend-mobile && \
     git -c safe.directory=* checkout HEAD -- .'
   ```

3. Then retry only the genuinely-broken tasks: T12 (V184 overflow,
   should now persist), T17 / T19 (same), T18 (genuine stagnation —
   needs spec edit or skip).

- Cost: ~$0.10–$0.50 per task retry × 4 retries (with Option B PR #99
  deployed, only the targeted task runs, not the whole plan).
- Time: ~5–15 minutes per retry.
- Pros: cheaper than full re-run.
- Cons: requires SQL surgery on prod-ish data; T18 will likely
  re-stagnate.

### Option C — accept the run as lost

Mark `7483896a` as "wreckage" and move on. Submit new runs for
remaining work. Use the diagnostic value of `7483896a` (logs,
analyses, etc) but don't try to bring it back to a coherent state.

- Cost: $0
- Time: 0
- Pros: simplest. The workspace files (5 modified, uncommitted)
  contain real worker-generated edits that may be useful — copy them
  out via `git diff > patch.diff && scp` if you want to keep the
  output.

## Open questions for the operator

1. Are the workspace working-tree edits from the buggy re-run
   actually different from what was already committed? If they're
   identical (worker re-generating the same code), Option C losing
   them costs nothing. If they differ in interesting ways, Option A
   loses information.
2. Is the dev VM workspace dir bind-mounted to persistent disk, or
   ephemeral? Affects whether retry-after-deploy is even possible
   (RunOrchestrator.retryTask requires the workspace to exist
   on-disk).

## Recommended path

**Option A.** The cost premium is real but the risk is zero, the data
is clean, and the time investment is bounded. Options B and C both
require touching dev DB / VM state in ways that compound the risk.
