### RL-2026-06-039 - Local tool-result envelopes are normalized server-side
- **Change:** `POST /api/runs/{id}/tool-results` now validates and normalizes the client tool-result envelope before unblocking `RemoteToolDispatcher`: result must be a JSON object with boolean `ok`; success content is coerced to a string; failure envelopes get bounded `kind` / `message` defaults; malformed replies become `{"ok":false,"kind":"INTERNAL","message":"malformed tool result"}`. The CLI local execution pump now catches unexpected runtime crashes and posts an `INTERNAL` tool envelope instead of leaving the server-side worker waiting for a result. `run local` also has accepted-path coverage through the command layer: backend acknowledgement, SSE `TOOL_CALL`, local `ToolRuntime` write, formatted file output, and `postToolResult`.
- **Why:** Local-hands is a trust boundary. A buggy or hostile client should not be able to send arbitrary JSON into the worker context, and a crashed local runtime must not strand an in-flight server tool call until timeout.
- **Validation:** `JAVA_HOME=/opt/homebrew/opt/openjdk@21 mvn -q -Dtest='RemoteToolDispatcherTest,RemoteToolControllerTest,RunControllerLocalExecutionAuthTest,RunLocalExecutionFlagTest' test`; `npm --prefix core test`; `npm --prefix cli test`.

### RL-2026-06-038 - CLI local-folder context is an explicit evidence contract
- **Change:** CLI folder inspection now injects a stable marker (`EXECUTESPEC_LOCAL_CONTEXT: approved_read_only=true`) plus explicit instructions that the snapshot is real read-only evidence. `SpecChatService` mirrors that contract in its system prompt: when the marker is present, the assistant must use the provided bounded tree/key-file contents and must not answer that it cannot inspect the local folder. The core chat client still sends the full augmented conversation to the model, but strips the appended local snapshot from the durable agent-session `message` field so server-side turn metadata remains clean.
- **Why:** The CLI had a read-only scan prompt, but the model could still behave like a blind remote chatbot and ask the user to paste files. Also, storing the entire folder snapshot as the durable turn text would make chat history noisy and over-retentive.
- **Validation:** `npm --prefix cli test -- test/chat-setup.test.mjs`; `npm --prefix core test -- test/chat-sse.test.mjs`; `JAVA_HOME=/opt/homebrew/opt/openjdk@21 mvn -q -Dtest=SpecChatServiceTest test`.

### RL-2026-06-037 - Local-hands run submit is PAT-only
- **Change:** `JwtAuthenticationFilter` now tags authenticated requests as JWT or Personal Access Token. `RunController` rejects `localExecution=true` unless the request came from the PAT path, after the existing feature-flag fail-closed check and before quota/billing increments. The browser/web UI remains remote-run-only; CLI and VS Code keep using PAT sessions where local filesystem and command approvals are enforced.
- **Why:** The web create-run client does not expose local-hands, but a browser/devtools caller could still hand-post `localExecution=true`. Browser JWT sessions cannot enforce local command/file approvals, so the server contract must make local-hands a programmatic-client capability only.
- **Code:** `src/main/java/com/navneet/executespec/auth/security/JwtAuthenticationFilter.java`, `src/main/java/com/navneet/executespec/api/controller/RunController.java`, `src/test/java/com/navneet/executespec/api/controller/RunControllerLocalExecutionAuthTest.java`

### RL-2026-06-036 - Provider preference is account-scoped across web, CLI, and VS Code
- **Change:** Add `app_user.preferred_ai_provider` (V242), `AiProviderPreferenceService`, and `GET/PUT /api/auth/me/provider-preference`. `POST /api/runs`, agent-session turns, and the legacy `/api/spec/chat` fallback now remember explicit provider choices and resolve omitted provider input through the account preference. Web compose, CLI config/chat/run submit/local, and VS Code submit/chat all read/write the same preference.
- **Why:** Provider selection was still fragmented: a CLI `/provider deepseek` could affect one chat turn while a later run, web submission, or VS Code chat fell back to a different default. That breaks user expectation and makes cost/model routing investigations hard to trust.
- **Rule:** explicit provider on the current request wins and is persisted; absent provider uses the account preference; project/YAML defaults remain fallback only. Legacy `GOOGLE` input normalizes to `GEMINI`.
- **Code:** `src/main/java/com/navneet/executespec/auth/service/AiProviderPreferenceService.java`, `src/main/java/com/navneet/executespec/auth/controller/AuthController.java`, `src/main/java/com/navneet/executespec/api/controller/RunController.java`, `src/main/java/com/navneet/executespec/agentsession/AgentSessionService.java`, `src/main/java/com/navneet/executespec/specchat/SpecChatController.java`, `frontend/src/ide/IdeSurfaces.tsx`, `executespec-cli/core/src/api.ts`, `executespec-cli/cli/src/commands/run.ts`, `executespec-cli/vscode/src/client.ts`, `src/main/resources/db/migration/V242__user_preferred_ai_provider.sql`

### RL-2026-06-033 - CLI local-hands submit handshake and scope discipline
- **Change:** `POST /api/runs` now rejects `localExecution=true` before quota/billing when `worker.local-hands.enabled` is OFF, and echoes `localExecutionRequested` / `localExecutionAccepted` on accepted submit summaries. V241 seeds the local-hands feature flag as DEFAULT OFF so operators can enable it without manual DB edits. Local-hands execution now passes an explicit `localHandsMode` flag into `SequentialExecutor`, which appends a local-only prompt guard plus a final override of the generic test mandate: obey exact file scope, do not invent tests/scaffolds for empty content-only workspaces, and complete once the requested local edits are done. The live smoke also exposed a noisy SSE cleanup path; `SseBroadcaster` now removes emitters after send failure without calling `complete()` on an already unusable response, and `GlobalExceptionAdvice` treats `AsyncRequestNotUsableException` as a debug-level client disconnect instead of trying to serialize a JSON error onto a committed `text/event-stream` response.
- **Why:** The CLI must not risk silently turning a local working-tree task into a normal remote run. Fail-closed belongs in the server contract as well as the client. The live smoke also showed the worker over-scaffolding an empty local workspace despite an exact-file request, so local-hands needs stricter scope discipline than normal product BUILD runs.
- **Code:** `src/main/java/com/navneet/executespec/api/controller/RunController.java`, `src/main/java/com/navneet/executespec/api/dto/RunSummary.java`, `src/main/java/com/navneet/executespec/api/RunMapper.java`, `src/main/java/com/navneet/executespec/api/advice/GlobalExceptionAdvice.java`, `src/main/java/com/navneet/executespec/harness/ExecutionRequest.java`, `src/main/java/com/navneet/executespec/harness/SequentialExecutor.java`, `src/main/java/com/navneet/executespec/sse/SseBroadcaster.java`, `src/main/resources/db/migration/V241__seed_worker_local_hands_flag.sql`

### RL-2026-06-032 - CLI/VS Code agent-session protocol starts separate from runs
- **Change:** Add `agentsession/` with durable `agent_session`, `agent_turn`, `agent_action_event`, and `agent_usage_ledger` tables (V240), plus `/api/agent` endpoints for action catalog, sessions, streaming turns, context resolution, and gate decision cards. `POST /api/agent/sessions/{id}/turns/stream` records the turn, delegates the token/tool stream to `SpecChatService`, emits the same chat SSE event names as the legacy endpoint, and writes completed token/cost usage into `agent_usage_ledger`. The first intent router is deterministic and returns typed confirmation-required proposals for `create_run`, `local_code_task`, and `approve_run` instead of executing them.
- **Why:** The CLI and VS Code extensions need Claude/Codex-style open-ended input without turning every message into a hidden `pipeline_run`. Runs remain the deterministic, scored, plan-gated execution unit; sessions become the natural-language control plane over runs/projects/gates.
- **Billing guardrail:** Run credits remain charged only by the existing plan-approval path. Open-ended session usage has a separate ledger for future conversation billing/fair-use policy, currently marked `INCLUDED`, so local/cloud/local-hands discussion cannot silently consume run credits.
- **Code:** `src/main/java/com/navneet/executespec/agentsession/*`, `src/main/resources/db/migration/V240__agent_session_protocol.sql`, `src/test/java/com/navneet/executespec/agentsession/AgentIntentServiceTest.java`

### RL-2026-06-031 - Terminal-Bench Harbor submissions emit ATIF at source
- **Change:** Make the ExecuteSpec Harbor adapter leaderboard-compliant by declaring `SUPPORTS_ATIF=true` and writing `agent/trajectory.json` during every Terminal-Bench trial. The trajectory captures the task instruction, each ExecuteSpec `TOOL_CALL`/tool-result pair, and the terminal cost/status summary. `run-tb.sh` now defaults to `terminal-bench/terminal-bench-2-1` and passes the same dataset id to the in-app benchmark bridge. `submit-tb.sh` now performs an ATIF preflight before upload, then runs public Harbor upload and explicit `harbor leaderboard submit -l terminal-bench-2-1` with a required metadata yaml.
- **Why:** The previous TB 2.1 uploads were vulnerable to leaderboard rejection because trajectories were reconstructed or submitted separately after the public upload. Harbor static validation requires passing trials to have a trajectory path in the uploaded job, so the next back-to-back runs must produce that artifact during the original Harbor run and fail locally if it is missing.
- **Tradeoff:** Leaderboard submission is now the default in `submit-tb.sh`; upload-only experiments must opt out with `SUBMIT_LEADERBOARD=0`. This is intentional for publishable TB 2.1 runs but slightly stricter for ad-hoc public uploads.
- **Code:** `infra/benchmark/tb/es_harbor_agent.py`, `infra/benchmark/scripts/run-tb.sh`, `infra/benchmark/scripts/submit-tb.sh`, `infra/benchmark/TB-FULL89-RUNBOOK.md`, `infra/benchmark/EVAL-ENV-PLAN.md`, `src/main/java/com/navneet/executespec/terminalbench/CLAUDE.md`

### RL-2026-06-026 - Verified score trust caps and evidence ledger
- **Change:** Keep the additive `verifiedScore` formula, then cap the headline when verification signals show review/build/test risk; expose `verificationLedger[]` on validation reports; extend the SUPER_ADMIN backfill endpoint with `{runId, limit, dryRun}` and recompute both `verifiedScore` and `rubricScore`.
