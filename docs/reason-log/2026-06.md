per-run seq, persisted + re-broadcast via the shared `sse/SseBroadcaster` (keyed by the benchmark-run id → Redis

### RL-2026-06-010 — C1: read-only-batch parallel tool dispatch (vix-leverage W4.1) (2026-06-07)

vix-leverage plan **W4.1** (the C1 latency borrow). The V2 worker dispatched every tool call in a batch sequentially (`WorkerAgent.dispatchOne` in a `for` loop). Now a **pure read-only batch** — a single assistant turn whose every call is in {`readFile`,`searchFiles`,`listFiles`,`gitStatus`,`gitDiff`}, ≥2 calls, non-remote — pre-executes those tool bodies **concurrently on virtual threads** (`maybeParallelReadDispatch` → `{callId→envelope}` map); the existing sequential loop then consumes the cached envelopes, so every per-call state mutation (metrics, SSE, `toolResponses` ordering, the test/build/edit/verify gate-tracking) happens in **deterministic original order** — byte-identical output, just faster. The win is the read-heavy early exploration phase of a task.

**Why no flag.** It's behavior-NEUTRAL (same results, same order of observable mutations — only the tool *executions* overlap), so there's nothing to eval for quality. Instead of a migration + `WorkerTaskRequest` field + multi-site wiring, it ships with a **fail-safe fallback**: any batch containing a write/build/shell/`completeTask` (or a remote run) → fully sequential (avoids read-after-write / write-after-read hazards); a timeout (120s) or a partially-filled result → sequential; re-runs are idempotent reads. A kill-switch flag can wrap it later if needed.

**Safe-to-parallelize verification.** The read set has no ordering-sensitive shared state: `readFile`'s only side effect is `ReadFileStateStore` (a `Collections.synchronizedMap` over a `LinkedHashMap` with a `ConcurrentHashMap` inner — thread-safe); `searchFiles`/`listFiles`/`gitStatus`/`gitDiff` are pure reads; and `maybeCompact` (reached inside `dispatchOne` when compaction is ON) records via `RunCostTracker`, which is `ConcurrentHashMap` + `AtomicLong.addAndGet`. All metrics/SSE/`emitToolCallLog` stay on the main thread in the sequential loop.

**Verified.** New `pure_read_batch_parallel` test (`[readFile, searchFiles]` → COMPLETED, both logged in order) + the full 63-test `WorkerAgent*Test` suite green (every gate test unchanged), spotless clean. ### RL-2026-06-006 — Worker harness stages (verify / deliverable gate / critic) in COMMON space, not a TB fork (2026-06-07)

**Decision (founder, 2026-06-07): "implement in common space — i don't need forks of the same path."** So the stages were NOT left Terminal-Bench-gated. ### RL-2026-06-003 — Tiered codemap injection, Phase 1 (2026-06-03)

> **Staged, not deployed** (backend not restarted; the project-mode eval is running). Flag `codeintel.tiered.enabled`, V230 in the current worktree, default OFF → flag-OFF is byte-identical.

**Problem.** Large repos → large codemaps (matplotlib's 4363 files → a 58 KB map). Injection was a HEAD truncation to `CODEINTEL_PER_REPO_CAP = 6000` chars, which on a big repo runs out inside the flat `## Files (listing)` and cuts the `## Functions` per-file symbol map — the localization signal — 100%. We injected paths (noise), not symbols. Raising the cap is the wrong fix (58 KB × ~30 worker turns = cost blow-up + attention dilution). Empirically the project-mode-vs-blind DeepSeek eval, injecting paths-only, shows a ~flat lift — consistent with "a directory listing doesn't localize."

**Fix.** New `codeintel/TieredCodemapSelector` (pure, deterministic): parse the codemap into title + `## ` sections, split `## Functions` into per-file `### path` blocks, score each by lexical overlap with the run spec (path match ×3 over symbol-text), and assemble **T0 skeleton (title + top-level layout + routes/models) + the spec-relevant symbol blocks** within the same budget, dropping the flat file listing. `RunContextComposer.buildCodeIntelContext(…, specText, tiered)` calls it when the flag is ON; a `null` return (unparseable / blank spec) falls back to the original head-truncate. Both call sites (BUILD planner + PATCH) pass the spec (`userRequest` / `userRequestLive`). 5 unit tests pin select/fallback/budget. **Phase 2** swaps the lexical scorer for the pgvector semantic retriever (V223) behind the same call; **Phase 3** adds a `codemap_lookup` worker tool. Plan: [`docs/plans/tiered-codemap-architecture.md`](../plans/tiered-codemap-architecture.md).

### RL-2026-06-002 — Same-provider doc-gen: DeepSeek/OpenRouter as project providers (2026-06-03)

> **Staged, not deployed.** Code only, no migration.

**Problem.** Surfaced by the project-mode cost analysis: a project's codemap/architecture (the injected context) was generated by a DIFFERENT provider than its worker. DeepSeek couldn't be a project provider — `CreateProjectRequest` validation allowed only `ANTHROPIC|GEMINI|OPENAI`, and the arch generators dispatch through the legacy `FallbackLlmRouter`, whose provider switch has no `deepseek`/`openrouter` case. So a DeepSeek-worker run's arch had to come from gpt-5.4 (~25× more expensive per token + a cross-provider confound), and that arch-gen LLM cost was UNTRACKED (no `run=` context → never reached `RunCostTracker`).

**Fix.** (1) `CreateProjectRequest` regex now accepts `DEEPSEEK`/`OPENROUTER`. (2) New `codeintel/ArchLlmDispatch` routes those two native-only providers through the canonical `LlmRouter` (which has the `deepseek`/`openrouter` dispatch case + records cost via `RunCostTracker`), leaving `anthropic|openai|gemini` on `FallbackLlmRouter` byte-identical (zero regression). `RepoArchitectureGenerator` + `ArchitectureDocGenerator` both call the shared helper. Net: a project can be DeepSeek end-to-end (codemap+arch + worker on one provider), ~25× cheaper setup, and arch-gen cost is finally tracked. Compile/format/test-compile green; no test constructs the generators. A full product rollout would also need the UI provider picker + `AvailableProviderResolver` reviewed. Part of the eval-rebuild stream (RL-2026-06-001).
