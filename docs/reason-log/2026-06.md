### RL-2026-06-032 - OAuth callback state survives session-cookie loss
- **Change:** Add `CookieOAuth2AuthorizationRequestRepository` and wire Spring OAuth2 authorization requests through it. The repository stores each request in a 5-minute HttpOnly `SameSite=Lax` cookie keyed by a SHA-256 hash of OAuth `state`, signs the payload with `app.jwt.secret`, rejects tampering, and clears the cookie on callback.
- **Why:** Dev OAuth was failing with `OAuth2AuthenticationException: [authorization_request_not_found]` on the provider callback even though `/api/auth/oauth2/authorize/{provider}` issued correct Google/GitHub redirects. A controlled callback with a fresh single `ESDEVSESSION` reached token exchange, proving provider config was not the issue; the real browser path was losing or presenting the wrong session state. Persisting the authorization request by `state` makes login resilient to missing/stale/duplicate session cookies and parallel OAuth attempts.
- **Tradeoff:** The callback now carries one short-lived signed cookie per in-flight OAuth state. The payload is protected against client tampering but still bounded by browser cookie limits; current Google/GitHub request objects are small enough and covered by unit tests.
- **Code:** `src/main/java/com/navneet/executespec/auth/oauth/CookieOAuth2AuthorizationRequestRepository.java`, `src/main/java/com/navneet/executespec/auth/security/SecurityConfig.java`, `src/test/java/com/navneet/executespec/auth/oauth/CookieOAuth2AuthorizationRequestRepositoryTest.java`

### RL-2026-06-031 - Terminal-Bench Harbor submissions emit ATIF at source
- **Change:** Make the ExecuteSpec Harbor adapter leaderboard-compliant by declaring `SUPPORTS_ATIF=true` and writing `agent/trajectory.json` during every Terminal-Bench trial. The trajectory captures the task instruction, each ExecuteSpec `TOOL_CALL`/tool-result pair, and the terminal cost/status summary. `run-tb.sh` now defaults to `terminal-bench/terminal-bench-2-1` and passes the same dataset id to the in-app benchmark bridge. `submit-tb.sh` now performs an ATIF preflight before upload, then runs public Harbor upload and explicit `harbor leaderboard submit -l terminal-bench-2-1` with a required metadata yaml.
- **Why:** The previous TB 2.1 uploads were vulnerable to leaderboard rejection because trajectories were reconstructed or submitted separately after the public upload. Harbor static validation requires passing trials to have a trajectory path in the uploaded job, so the next back-to-back runs must produce that artifact during the original Harbor run and fail locally if it is missing.
- **Tradeoff:** Leaderboard submission is now the default in `submit-tb.sh`; upload-only experiments must opt out with `SUBMIT_LEADERBOARD=0`. This is intentional for publishable TB 2.1 runs but slightly stricter for ad-hoc public uploads.
- **Code:** `infra/benchmark/tb/es_harbor_agent.py`, `infra/benchmark/scripts/run-tb.sh`, `infra/benchmark/scripts/submit-tb.sh`, `infra/benchmark/TB-FULL89-RUNBOOK.md`, `infra/benchmark/EVAL-ENV-PLAN.md`, `src/main/java/com/navneet/executespec/terminalbench/CLAUDE.md`

### RL-2026-06-030 - PATCH/SWE-bench codegen routes through CodeGenEngine
- **Change:** Move active PATCH-style codegen policy out of `PatchAgent` and into `engine/CodeGenEngineImpl`: direct `WorkerAgent` request construction, patch prompt assembly, provider patch fragments, per-provider caps, source-scoped test-verification gate, and common critic/VBC flags. `RunOrchestrator.runPatchPipeline` now calls `CodeGenEngine.solve`; `PatchAgent` is deprecated with no active callers. Also fixed the local SWE-bench Pro harness shape: Pro Docker images now start with an explicit shell entrypoint, the instance loader parses Python-style string list fields, benchmark patch capture drains process output while the process runs, Redis `appendonlydir/**` runtime artifacts are excluded from benchmark diffs, interface-driven blind specs force caller/consumer search, and PATCH-mode workers get an early no-edit nudge before the normal stagnation window.
- **Why:** SWE-bench / SWE-Pro should exercise the same core codegen engine as product patch/autofix flows, not a separate scenario-specific agent path. The Pro Docker entrypoint and manifest parser fixes were required before spending on SWE-bench Pro mini runs.
- **Tradeoff:** `PatchAgent` remains temporarily as a compatibility shell instead of being deleted in this change; that keeps the refactor bounded while tests and docs prove the new active path. The early no-edit nudge is deliberately PATCH-only and non-terminal; BUILD and Terminal-Bench keep their existing thresholds.
- **Code:** `src/main/java/com/navneet/executespec/engine/CodeGenEngineImpl.java`, `src/main/java/com/navneet/executespec/engine/WorkerAgent.java`, `src/main/java/com/navneet/executespec/integration/RunOrchestrator.java#runPatchPipeline`, `src/main/java/com/navneet/executespec/agent/PatchAgent.java`, `src/main/java/com/navneet/executespec/benchmark/BenchmarkGenerationService.java`, `src/main/java/com/navneet/executespec/benchmark/BenchmarkRunService.java`, `src/main/java/com/navneet/executespec/swebench/SwebenchInstanceLoader.java`, `src/main/resources/prompts/patch-agent.md`

### RL-2026-06-027 - Console becomes the protected web shell
- **Change:** Mount `ConsoleShell` for all protected routes, remove the `localStorage es:console` opt-in path and `IdeWorkspace`, add `/decisions`, keep the existing `ide/` components as route-level surfaces, and lazy-load heavy admin/discovery/billing/org/legal chunks.
- **Why:** The browser app is a control plane, not the editing environment. Keeping a VS Code-style shell in the web app duplicated the VS Code extension metaphor and made mobile monitoring harder. Console gives the product a stable operator shell for runs, projects, decisions, billing, model settings, and benchmark monitoring.
- **Tradeoff:** This is a large visual/navigation change and must be visually QA'd before merge. The code-level route components remain mostly intact to keep the behavior risk bounded.
- **Code:** `frontend/src/App.tsx`, `frontend/src/console/ConsoleShell.tsx`, `frontend/src/console/ConsoleHome.tsx`, `frontend/src/console/ConsoleDecisions.tsx`, `frontend/src/stores/useUiStore.ts`

### RL-2026-06-026 - Verified score trust caps and evidence ledger
- **Change:** Keep the additive `verifiedScore` formula, then cap the headline when verification signals show review/build/test risk; expose `verificationLedger[]` on validation reports; extend the SUPER_ADMIN backfill endpoint with `{runId, limit, dryRun}` and recompute both `verifiedScore` and `rubricScore`.
- **Why:** A high internal score without visible evidence reads as self-scored proof. The score still needs to summarize routing quality, but the product surface must show which claims are deterministic, which are LLM assessments, and which are only the internal formula.
- **Tradeoff:** Strong partial work can no longer headline above the cap even if the weighted formula would be higher. This is intentional: unresolved review, build, or test signals should force operator/customer review before external use.
- **Code:** `src/main/java/com/navneet/executespec/report/ValidationReportService.java#computeVerifiedScore`, `src/main/java/com/navneet/executespec/report/ValidationReportService.java#buildVerificationLedger`, `src/main/java/com/navneet/executespec/report/VerifiedScoreBackfillService.java#backfill`
