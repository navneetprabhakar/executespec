## 2026-07-15 — DeepSeek route-order hardening

- **Decision:** DeepSeek requests use native `api.deepseek.com` as the healthy primary. OpenRouter and Fireworks are recovery hops only, in that order. A healthy native DeepSeek request must not be adaptively re-routed to Fireworks based on historical performance.
- **Reason:** The provider smoke intentionally exercised Fireworks as a separate explicit lane, but that evidence was easy to misread as the production route. Adaptive routing could also bypass the documented native-first policy when enabled.
- **Implementation:** `ModelResolver` disables adaptive provider replacement when the requested provider is `DEEPSEEK`; explicit `provider=FIREWORKS` remains supported. `ModelResolverAdaptiveOptInTest` now pins native retention even when Fireworks is reported as materially better. Existing `ModelRegistryDeepSeekFailoverTest` pins native → OpenRouter → Fireworks recovery ordering.

### RL-2026-07-15-050 - Contain Harbor Docker timeout cleanup leak

- **Finding:** Harbor 0.13.1 can cancel an adapter while its Docker environment is awaiting
  `docker compose exec`; the cancellation bypasses the subprocess timeout and can leave an idle
  verifier container after Harbor records `AgentTimeoutError`. The active TB2.1 run exposed this
  behavior on `pytorch-model-recovery`; Harbor continued, so the campaign was not mutated.
- **Action:** `infra/benchmark/scripts/run-tb.sh` now performs a bounded, job-scoped cleanup after
  Harbor exits. It derives task prefixes from the current job directory and removes only matching
  containers with `docker rm -f`; it never runs a global Docker prune or unscoped compose teardown.
- **Boundary:** This is containment until Harbor's Docker wrapper handles `CancelledError` with
  bounded terminate/wait/kill and `DockerEnvironment.stop` has a timeout. Future release-grade
  benchmark evidence must include cancellation-injection and no-leftover-container tests, while
  preserving the original timeout classification.
