### RL-2026-05-006 — Re-introduce coarse parallel task execution

- **Change:** _(in progress)_ Execute `dependsOn`-independent tasks concurrently again, and cap planner task count per complexity so we don't re-create the over-fragmentation that made v2's parallelism noisy.
- **Why:** v2 had parallel execution (~5× faster) but the planner decomposed too finely — many tiny tasks racing on shared files, high coordination cost, flaky merges. We dropped to fully-sequential to stop the noise, but that made HIGH runs 36–87 min (Gemini high = 87 min on an 11-task plan), which times out benchmarks and is unusable in production. The fix is BOTH levers together: fewer/coarser tasks (less to coordinate) + parallelism on the independent ones (recover the speed).
- **Tradeoff:** coarser tasks = each worker does more, slightly higher per-task failure blast radius; mitigated by keeping tasks single-responsibility, just not single-file.
- **Code:** `harness/SequentialExecutor.java`, `agent/OutlinePlannerAgent.java` (task-count band).

### RL-2026-05-005 — Unify the worker's six overlapping guardrails

- **Change:** _(in progress)_ Collapse Lever A (force-edit watchdog), Lever C (completion nudge), and the stagnation warn/force counters into one "are we making progress?" signal. Keep Lever B (salvage) and the budget cap. Soften the wall-clock + iteration caps (see RL-2026-05-004).
- **Why:** `WorkerAgent` grew six independent guardrails, each added after a specific bad run. They overlap and have collided — Lever A's force-edit nudge could never fire because the stagnation-force killed the worker first (the comment at the old `forceEditAtIter` line documented this). Six knobs that interact pairwise are unmaintainable; one progress signal is reason-able.
- **Tradeoff:** less granular control; accept that in exchange for a loop a human can hold in their head.
- **Code:** `agent/WorkerAgent.java#run`.

### RL-2026-05-004 — Soften wall-clock + iteration caps that force PARTIAL

- **Change:** _(in progress)_ Raise/relax the per-task wall-clock and iteration caps so a legitimately long task completes instead of being force-terminated into PARTIAL. Keep the dollar hard-cap (that's a real cost guard, not a heuristic).
- **Why:** the clock cap and iter cap were the two biggest sources of PARTIAL runs — they fire on slow-but-progressing work (especially Gemini, which is genuinely slow per turn) and tombstone a run that would have finished. PARTIAL is a worse customer outcome than "took a bit longer." Founder call (2026-05-20): minimise these two heuristic kills.
- **Tradeoff:** a genuinely stuck task burns more time/tokens before stopping; the budget cap still bounds the dollar exposure, so the worst case is bounded in $ even if not in minutes.
- **Code:** `harness/SequentialExecutor.java#tierConfigFor`, `agent/WorkerAgent.java#run` (wall-clock + iter checks).

### RL-2026-05-003 — UNKNOWN coverage damps the TESTS slot, doesn't drop it

- **Change:** in `computeVerifiedScoreAdditive`, treat `testCoverageLevel=UNKNOWN` as a conservative damped value (~50) rather than dropping the TESTS slot entirely.
- **Why:** the additive scorer drops unmeasured slots from the weighted average. UNKNOWN coverage was hitting that path → a run with NO confirmed tests could score 100. The rubric now tells the judge to say NONE (not UNKNOWN) when it sees no test files, but the structural hole stays open until real test execution lands (RL-2026-05-001); damping UNKNOWN closes it in the meantime.
- **Tradeoff:** a run whose tests genuinely couldn't be read (truncation) is scored slightly low; acceptable vs the inflation risk.
- **Code:** `report/ValidationReportService.java#computeVerifiedScoreAdditive`.

### RL-2026-05-002 — testCoverageLevel graded against explicit bands

- **Change:** added precise NONE/PARTIAL/GOOD/COMPREHENSIVE definitions to the accuracy-assessment prompt; "a test per spec-required target = GOOD".
- **Why:** the prompt had one vague line, so the judge defaulted to PARTIAL even when every endpoint was tested → TESTS slot damped to 40 → medium runs capped at ~85 despite a passing build + clean reviewer + full spec implementation. Calibration, not gaming: a run that wrote the spec's tests should grade GOOD.
- **Tradeoff:** none meaningful; reserves PARTIAL for genuine gaps.
- **Code:** `reviewer/AccuracyAssessmentService.java` (SYSTEM_PROMPT coverage section).

### RL-2026-05-001 — Execute tests in BUILD mode (the deterministic anchor)

- **Change:** _(in progress)_ After a BUILD run completes, execute the worker-written tests in the cleanroom container, produce a real `TestExecutionSummary` (passed/total), and feed it into the verifiedScore TESTS slot instead of the LLM-judged coverage grade.
- **Why:** BUILD mode never ran tests — `RunTestsTool` is patch-mode/Python-only. So verifiedScore "verified" that the build *compiled* + an LLM's *opinion* of coverage, never that the code *works*. That's why the score was inflatable (re-calibrating the judge moved 72→90+ with no code change) and why it varies run-to-run (the coverage grade is an LLM guess). Real execution makes the number mean something, removes the dominant variance source, and is the same machinery the BUILD benchmark needs.
- **Tradeoff:** adds a test-execution step (time + container) to every BUILD run; bounded by the existing cleanroom + a per-suite timeout.
- **Code:** `harness/SequentialExecutor.java` (post-run test stage), `report/ValidationReportService.java` (TESTS slot already prefers real passed/total).
