### RL-2026-05-008 — Conversation pinned to Anthropic Haiku (+ fix the bean ambiguity that hid it)

- **Change:** The pre-submit chat (`ConversationController`) and run copilot (`ConversationAgent.chat`) now call `FallbackLlmRouter.callDirect("anthropic", <lightweight model>, …)` — forcing Anthropic Haiku, bypassing the per-runId provider **pin store** (the shared `runId="conversation"` pin had stuck to Gemini) and the fallback chain. Also fixed the underlying bug: `FallbackLlmRouter.resolveModel` resolved `AnthropicChatModel` **by type**, but `AgentModelConfig` registers 4 such beans (planner/worker/reviewer + the auto-config default) → `NoUniqueBeanDefinitionException` on every system Anthropic call. Now resolves the system bean by name (`anthropicChatModel`).
- **Why:** The conversation was silently running on `gemini-3-flash-preview` (a thinking model whose reasoning tokens ate the output cap and truncated "Use as spec"). The bean bug meant the requested provider (Anthropic) could never actually run via FallbackLlmRouter — it always failed over to Gemini.
- **Blast radius:** the bean fix affects ALL FallbackLlmRouter system Anthropic calls (ConversationAgent, AccuracyAssessmentService, testgen/*, RunLedgerAgent…) — they now use Anthropic instead of failing over. Verified: `/api/conversation` returns 200 from `provider=anthropic model=claude-haiku-4-5-20251001`.
- **Status (2026-05-21):** Shipped on `feature/honesty-pass-2026-05-19`.

### RL-2026-05-007 — Anthropic WORKHORSE: Sonnet → Haiku (eval-driven)

- **Change:** `model-matrix.providers.anthropic.workhorse` flipped `claude-sonnet-4-6` → `claude-haiku-4-5-20251001`. LIGHTWEIGHT stays Haiku; PLANNING stays Sonnet. Anthropic now runs Haiku for LOW + MEDIUM, Sonnet only for HIGH.
- **Why:** A 6-model × 3-band code-gen eval (each cell a full pipeline with `RunRequest.modelName` forcing one model, scored by `verifiedScore`) showed Haiku **tied** Sonnet at a clean 100 on the MEDIUM band (Express to-do API; 50/50 vs 48/48 tests, both CLEAN) for **~32% less cost** ($0.67 vs $0.98) and ~20% faster. MEDIUM is the WORKHORSE tier's target complexity, so the Sonnet premium bought nothing there. Reverses the 2026-04-19 haiku→sonnet bump, which predated real-test-exec scoring (RL-2026-05-001) and was tuned against an LLM coverage guess.
- **Guard:** Haiku's cost edge **inverts** at HIGH (eval: $3.87 / 31m, score 91 vs Sonnet $2.86 / 23m, score 94 — the only clean HIGH). Safe because the tier ladder routes HIGH-complexity worker tasks to PLANNING (still Sonnet), so Haiku never sees HIGH. (Same eval: both Gemini models DNF'd the HIGH band — unrelated to this change but a matrix risk worth tracking.)
- **Status (2026-05-21):** Shipped on `feature/honesty-pass-2026-05-19`. Eval was N=1/cell (directional, not statistical). Not yet on dev/prod.

### RL-2026-05-006 — Re-introduce coarse parallel task execution

- **Change:** _(scoped — deferred to an eval-gated session; see "Status")_ Execute `dependsOn`-independent tasks concurrently again, and bound planner task count so we don't re-create the over-fragmentation that made v2's parallelism noisy.
- **Why:** v2 had parallel execution (~5× faster) but the planner decomposed too finely — many tiny tasks racing on shared files, high coordination cost, flaky merges. We dropped to fully-sequential to stop the noise, but that made HIGH runs 36–87 min (Gemini high = 87 min on an 11-task plan), which times out benchmarks and is unusable in production. The fix is BOTH levers together: fewer/coarser tasks (less to coordinate) + parallelism on the independent ones (recover the speed).
- **Tradeoff:** coarser tasks = each worker does more, slightly higher per-task failure blast radius; mitigated by keeping tasks single-responsibility, just not single-file.
- **Two blockers found on 2026-05-20 (why this is its own session, not a tail-end change):**
  1. **Shared-workspace file races.** `SequentialExecutor.execute` is one strict `for` loop calling `executeOne` per task; the workspace dir is shared and `dependsOn` is a *logical* graph, not a file-level one. Two `dependsOn`-independent tasks can still write the same file → lost updates / corrupted customer code. No unit test can prove the absence of these races — only a live multi-task run can. Parallel dispatch must therefore land behind a default-OFF flag (`harness.parallel-tasks.enabled`) and be validated by a live eval before it's ever the default. Also needs: thread-safe `outcomes` collection, cancel semantics that don't rely on `Thread.currentThread().isInterrupted()` at a single loop top, and final-task-smoke ordering that no longer assumes sequential indices.
  2. **Task-count band is coupled to the legacy classifier.** `{{MAX_TASKS}}` renders **"unlimited"** for `Classification.MULTI_TASK` (`Integer.MAX_VALUE`), and BOTH `PlanStrategy.LARGE` (15–50 tasks) and `LEGACY` (50+) collapse into MULTI_TASK. So a blanket finite cap would *under*-decompose genuine LEGACY specs and break them. Bounding fragmentation correctly means splitting MULTI_TASK into distinct LARGE/LEGACY caps along the `SmartClassifierAgent → PlanStrategy → Classification` chain AND relaxing the prompt's "single-file-per-task bias" toward "single-responsibility, multi-file OK" — a plan-shape change whose effect on completion rate is only measurable by the same eval.
- **Design (ready to execute):** (a) add a pure `dependsOn → execution waves` scheduler (Kahn topological levels) — unit-testable in isolation, the reusable core; (b) wire it into `SequentialExecutor` behind `harness.parallel-tasks.enabled` (default OFF), bounded concurrency `min(3, waveSize)` on the existing pipeline pool, thread-safe outcome aggregation; (c) split the task-count band per strategy; (d) flip the planner prompt from "no parallelism / single-file" to "single-responsibility / parallel-safe dependsOn"; (e) validate on `scripts/v2-eval.sh medium+high × 3 providers`, comparing wall-clock AND verifiedScore (now a *real* number thanks to RL-2026-05-001) sequential-vs-parallel before flipping the flag on.
- **Dependency:** RL-2026-05-001 (real test execution) is the prerequisite — it gives a deterministic score to measure parallel-vs-sequential against; without it we'd be tuning plan shape against an LLM's coverage guess.
- **Code (when built):** new `harness/TaskWaveScheduler.java`, `harness/SequentialExecutor.java#execute`, `agent/SmartClassifierAgent.java` + `agent/Classification.java` (per-strategy caps), `prompts/outline-planner*.md`.
- **Status (2026-05-20):** NOT shipped. Design recorded above. Deferred to a focused session because (1) the concurrency half can corrupt customer code and is unprovable without a live run, and (2) the task-count half is blind tuning until measured by eval — shipping either without validation would be a superficial fix. RL-2026-05-001 + RL-2026-05-005 (shipped this session) are the prerequisites that make it safe and measurable.

### RL-2026-05-005 — Unify the worker's six overlapping guardrails

- **Change:** Collapsed Lever A (force-edit watchdog), Lever C (completion nudge), and the stagnation warn/force counters into ONE signal: `itersSinceProgress` (consecutive iters with no `writeFile`/`editFile`) + one one-shot nudge at `progressWarnAfter` + force-terminate at `progressForceAfter`. The same nudge also fires on a premature text-only stop (the old Lever C trigger). Kept Lever B (salvage) and the dollar budget cap; wall-clock + iter caps already softened (RL-2026-05-004). State went from `{stagnantIters, stagnationWarned, forceEditNudged, forceEditAtIter, completionNudgeFired}` → `{itersSinceProgress, progressNudged}` (+ `totalWriteCalls`, still needed for the salvage gate).
- **Why:** `WorkerAgent` grew six independent guardrails, each added after a specific bad run. They overlapped and collided — Lever A's force-edit nudge could never fire because the stagnation-force killed the worker first (the comment at the old `forceEditAtIter` line documented this). Six knobs that interact pairwise are unmaintainable; one progress signal is reason-able.
- **Behavior changes (intentional):** (1) a text-only stop now ALWAYS gets one nudge before STOPPED_WITHOUT_COMPLETE — the old Lever C only nudged when writes>0 AND the text matched a summary keyword. The keyword heuristic (`looksLikeSummary`) is deleted; nudging on any text-only stop is more robust. (2) The per-tier warn/force thresholds (`req.stagnationWarnAfter`/`After`, set by `SequentialExecutor.tierConfigFor`) now drive BOTH the nudge and the force, so the nudge always precedes the force by construction (no more clamping math).
- **Tradeoff:** less granular control (one nudge instead of two differently-worded ones) + at most one extra LLM call on a turn-1 text-only bail; accepted in exchange for a loop a human can hold in their head.
- **Validation:** unit-tested (`WorkerAgentStagnationTest` 12/12, `WorkerAgentProgressNudgeAndWallClockTest` 7/7). Still wants a live eval to confirm completion-rate parity across providers — the guardrails' whole point is behavioral, and unit tests pin mechanics not outcomes.
- **Code:** `agent/WorkerAgent.java#run` + `#progressNudgeMessage`. Tests: `WorkerAgentProgressNudgeAndWallClockTest` (renamed from `WorkerAgentLeverCAndWallClockTest`).

### RL-2026-05-004 — Soften wall-clock + iteration caps that force PARTIAL

- **Change:** _(in progress)_ Raise/relax the per-task wall-clock and iteration caps so a legitimately long task completes instead of being force-terminated into PARTIAL. Keep the dollar hard-cap (that's a real cost guard, not a heuristic).
- **Why:** the clock cap and iter cap were the two biggest sources of PARTIAL runs — they fire on slow-but-progressing work (especially Gemini, which is genuinely slow per turn) and tombstone a run that would have finished. PARTIAL is a worse customer outcome than "took a bit longer." Founder call (2026-05-20): minimise these two heuristic kills.
- **Tradeoff:** a genuinely stuck task burns more time/tokens before stopping; the budget cap still bounds the dollar exposure, so the worst case is bounded in $ even if not in minutes.
- **Code:** `harness/SequentialExecutor.java#tierConfigFor`, `agent/WorkerAgent.java#run` (wall-clock + iter checks).

### RL-2026-05-003 — UNKNOWN coverage damps the TESTS slot, doesn't drop it

- **Change:** in `computeVerifiedScoreAdditive`, treat `testCoverageLevel=UNKNOWN` as a conservative damped value (~50) rather than dropping the TESTS slot entirely.
- **Why:** the additive scorer drops unmeasured slots from the weighted average. UNKNOWN coverage was hitting that path → a run with NO confirmed tests could score 100. The rubric now tells the judge to say NONE (not UNKNOWN) when it sees no test files, but the structural hole stays open until real test execution lands (RL-2026-05-001); damping UNKNOWN closes it in the meantime.
- **Tradeoff:** a run whose tests genuinely couldn't be read (truncation) is scored slightly low; acceptable vs the inflation risk.
- **Code:** `report/ValidationReportService.java#computeVerifiedScoreAdditive`.

- **Change:** added precise NONE/PARTIAL/GOOD/COMPREHENSIVE definitions to the accuracy-assessment prompt; "a test per spec-required target = GOOD".

### RL-2026-05-001 — Execute tests in BUILD mode (the deterministic anchor)

- **Change:** After a BUILD run completes, run the worker-written tests **in the code workspace**, produce a real `TestExecutionSummary` (passed/total), and feed it into the verifiedScore TESTS slot instead of the LLM-judged coverage grade. Flag `scoring.real-test-exec` (default ON, seeded by V203).
- **Why:** BUILD mode never ran tests — `RunTestsTool` is patch-mode/Python-only, and the existing `testgen` executors run a *separately generated* Maven project against a preview, not the worker's own tests. So verifiedScore "verified" that the build *compiled* + an LLM's *opinion* of coverage, never that the code *works*. That's why the score was inflatable (re-calibrating the judge moved 72→90+ with no code change) and why it varies run-to-run (the coverage grade is an LLM guess). Real execution makes the number mean something and removes the dominant variance source — the deterministic anchor under the #4 benchmark-predictability call (single run trustworthy; publish median-of-3).
- **Security:** generated tests are UNTRUSTED code, so execution never uses free-form worker text. The command is **resolver-derived** from on-disk markers (`TestCommandResolver`), **validated** through `ShellSandboxPolicy`, and dispatched inside the `--network none` cleanroom container **where one exists** (SWE-bench / ProgramBench). Plain BUILD mode has no cleanroom container, so tests run on the host shell — the **same trust boundary `buildProject` already crosses every run** when it compiles worker code; not a new boundary. The dispatch mirrors `BuildProjectTool` exactly (container routing + PATH/HOME/JAVA_HOME hardening + per-suite timeout), in a dedicated tool-layer service — NOT raw `ProcessBuilder` from the orchestrator.
- **Fail-safe:** no recognized runner, a sandbox-blocked command, a timeout, an IO error, or unparseable output all yield `Optional.empty()` → the scorer falls back to the (damped) LLM coverage path. Worst case = "no change vs today"; the headline can only get more honest, never break.
- **Tradeoff:** adds up to one per-suite timeout (360–600s cap) of latency to each BUILD run — latency is already the binding constraint (Gemini HIGH ~87 min). The cap is a ceiling not the expected time, it runs once at end-of-run (not per task), and the flag is the kill switch if a slow suite hurts the run-terminal-in-15min SLO.
- **Known limitation:** multi-repo runs resolve at the top workspace root; per-`repos/<name>/` execution is not yet wired (resolver returns empty there → coverage fallback, no regression).
- **Code:** `smoketest/TestCommandResolver.java` + `smoketest/TestOutputParser.java` (resolver + parser) + `smoketest/WorkspaceTestRunner.java` (sandboxed dispatch), wired into `integration/RunOrchestrator.java#generateValidationReport` (the `ReportInput` seam, replacing the 5-arg constructor). Flag seeded by `db/migration/V203__seed_real_test_exec_flag.sql`.
- **Status (2026-05-20):** SHIPPED + unit-tested (`TestOutputParserTest` 9/9, `WorkspaceTestRunnerTest` fail-safe contract). Compiles clean; threads a real `TestExecutionSummary` into the additive TESTS slot. Still needs a live full-pipeline run per provider to confirm the resolver picks the right command on real generated projects.
