### RL-2026-05-043 — CLI + VS Code clients: PAT auth (shipped) + local-execution architecture (decided)

- **Context:** founder call (2026-05-26) to invest in a CLI + VS Code extension. Hard constraints: (1) the secret sauce (prompts, planner/worker/reviewer loop, model matrix + routing, scoring) stays server-side; (2) the user's **code + artifacts stay local** — these clients work on the user's own codebase and publish **nothing by default** (push/PR is opt-in). A code-as-truth assessment confirmed the React frontend is already a pure REST+SSE presentation layer with zero sauce, so the new clients inherit the split for free.
- **Auth — Personal Access Tokens (THIS commit):** the one real gap. Browser auth is access-JWT (1h, bearer) + refresh-token (7d) delivered **only** as an httpOnly cookie scoped to `/api/auth` — unusable headless, and OAuth-only users have no password to type. New `PersonalAccessToken` (V215): a revocable, SHA-256-hashed (never-plaintext; the digest is the indexed lookup key) credential the user mints in-app and presents as `Authorization: Bearer es_pat_…`. `JwtAuthenticationFilter` routes the `es_pat_` prefix to `PersonalAccessTokenService.resolveUserId` and binds the **same `AppUserDetails`** a JWT produces (identical global + org roles, identical tenant), so every downstream access guard behaves identically. Purely additive — the JWT branch is byte-for-byte unchanged. `POST/GET/DELETE /api/auth/me/tokens`. `lastUsedAt` stamp throttled to ≤1 write/5min to keep auth off the write path.
- **Execution model — "local hands / remote brain" (decided, not yet built):** the proprietary agent loop keeps running server-side; **tool execution is proxied to the client** and runs against the local working tree. Single seam: `ToolRegistry.ContextBoundToolCallback.call()` branches to a new `RemoteToolDispatcher` **only** when a `LOCAL` remote session is bound to the run — the default `tool.execute(args, ctx)` path stays byte-identical, so the existing pipeline and output quality are provably unaffected (a guard test will pin this). Transport: **SSE down (`tool_call`) + POST up (`tool_result`)**, reusing `SseBroadcaster` (no new infra). In `LOCAL` mode there's no server-side clone/persistence and `ScmPushService` auto-push is OFF. Privacy boundary chosen: **SaaS, transient context** (code context reaches the hosted model during a run; nothing persisted or published).
- **Clients:** Node/TS shared core → CLI → VS Code (native UI + focused webviews). The client tool runtime must match the server `tool/*` contract exactly (arg schemas + `ToolResult` envelope + truncation limits readFile 8k / shell 6k / diff 5k) or output quality drifts — pinned by a parity test.
- **Tradeoff / scope:** existing-repo planner/codemap reads happen outside the tool layer, so v1 targets build-from-scratch + worker-edit flows where the proxy covers all I/O; client-sent repo context (snapshot/codemap) is a fast-follow. WebSocket transport deferred (revisit only if SSE+POST round-trip latency hurts on a real 50–150-call run).
- **Code (this commit):** `auth/entity/PersonalAccessToken` + `repository/PersonalAccessTokenRepository` + `service/PersonalAccessTokenService` + `dto/{CreatePatRequest,PatDto,CreatePatResponse}` + `security/JwtAuthenticationFilter` (PAT branch) + `controller/AuthController` (`/me/tokens`) + `db/migration/V215__personal_access_token.sql` + `PersonalAccessTokenServiceTest`.
- **Status (2026-05-26):** PAT written + unit-tested-by-reading only — the web sandbox can't run Maven (Central + Spring repos network-blocked, no warm cache), so it needs `mvn verify` in CI/local. The Node/TS **shared client core** (`clients/core` — typed REST/SSE client, PAT token store, SSE consumer, local `ToolRuntime`) is now built (also reasoned-not-compiled; the npm registry is 403-blocked too). Local build/verify steps are captured in `clients/VERIFY.md`. The additive **backend tool-proxy** has now landed **dormant**: `RunEvent.toolCall`, `tool/remote/RemoteToolDispatcher` (register/unregister/isRemote/dispatch-blocks-for-client/complete), `tool/remote/RemoteToolController` (`POST /api/runs/{id}/tool-results`, write-guarded), and the null/`isRemote`-guarded branch in `ToolRegistry.ContextBoundToolCallback.call()` — inert until a run registers a session, so the default server-executed pipeline is byte-identical (the one manual `new ToolRegistry(...)` test got the extra null arg). The **CLI** (`clients/cli` — `@executespec/cli`, bins `executespec`/`es`: auth login/status/logout, run submit/watch/list/view/approve/reject/cancel/report, + experimental local-hands `run local`) has now landed (Node/TS, zero-dep, on the shared core), as has the **VS Code extension** (`clients/vscode` — native MVP: SecretStorage-backed PAT, Runs TreeView, Submit Spec, live OutputChannel stream, plan-gate Approve/Reject modal; esbuild-bundled so the ESM core folds into the CJS extension). Remaining: the **activation wiring** in `RunOrchestrator` (register/unregister + skip server clone + skip `ScmPushService` auto-push for local runs; `RunRequest` is a positionally-built record, so carry the flag carefully — see `clients/VERIFY.md` §3), a rich run-detail webview, and the token-management web UI — all flag-gated. ### RL-2026-05-023 — Fix GitHub Contents-API path encoding (Next.js `[dynamic]` route segments)

### RL-2026-05-006 — Re-introduce coarse parallel task execution

- **Change:** _(scoped — deferred to an eval-gated session; see "Status")_ Execute `dependsOn`-independent tasks concurrently again, and bound planner task count so we don't re-create the over-fragmentation that made v2's parallelism noisy.
- **Why:** v2 had parallel execution (~5× faster) but the planner decomposed too finely — many tiny tasks racing on shared files, high coordination cost, flaky merges. We dropped to fully-sequential to stop the noise, but that made HIGH runs 36–87 min (Gemini high = 87 min on an 11-task plan), which times out benchmarks and is unusable in production. The fix is BOTH levers together: fewer/coarser tasks (less to coordinate) + parallelism on the independent ones (recover the speed).
- **Tradeoff:** coarser tasks = each worker does more, slightly higher per-task failure blast radius; mitigated by keeping tasks single-responsibility, just not single-file.
- **Two blockers found on 2026-05-20 (why this is its own session, not a tail-end change):**
  1. **Shared-workspace file races.** `SequentialExecutor.execute` is one strict `for` loop calling `executeOne` per task; the workspace dir is shared and `dependsOn` is a _logical_ graph, not a file-level one. Two `dependsOn`-independent tasks can still write the same file → lost updates / corrupted customer code. No unit test can prove the absence of these races — only a live multi-task run can. Parallel dispatch must therefore land behind a default-OFF flag (`harness.parallel-tasks.enabled`) and be validated by a live eval before it's ever the default. Also needs: thread-safe `outcomes` collection, cancel semantics that don't rely on `Thread.currentThread().isInterrupted()` at a single loop top, and final-task-smoke ordering that no longer assumes sequential indices.
  2. **Task-count band is coupled to the legacy classifier.** `{{MAX_TASKS}}` renders **"unlimited"** for `Classification.MULTI_TASK` (`Integer.MAX_VALUE`), and BOTH `PlanStrategy.LARGE` (15–50 tasks) and `LEGACY` (50+) collapse into MULTI*TASK. So a blanket finite cap would \_under*-decompose genuine LEGACY specs and break them. Bounding fragmentation correctly means splitting MULTI_TASK into distinct LARGE/LEGACY caps along the `SmartClassifierAgent → PlanStrategy → Classification` chain AND relaxing the prompt's "single-file-per-task bias" toward "single-responsibility, multi-file OK" — a plan-shape change whose effect on completion rate is only measurable by the same eval.
- **Design (ready to execute):** (a) add a pure `dependsOn → execution waves` scheduler (Kahn topological levels) — unit-testable in isolation, the reusable core; (b) wire it into `SequentialExecutor` behind `harness.parallel-tasks.enabled` (default OFF), bounded concurrency `min(3, waveSize)` on the existing pipeline pool, thread-safe outcome aggregation; (c) split the task-count band per strategy; (d) flip the planner prompt from "no parallelism / single-file" to "single-responsibility / parallel-safe dependsOn"; (e) validate on `scripts/v2-eval.sh medium+high × 3 providers`, comparing wall-clock AND verifiedScore (now a _real_ number thanks to RL-2026-05-001) sequential-vs-parallel before flipping the flag on.
- **Dependency:** RL-2026-05-001 (real test execution) is the prerequisite — it gives a deterministic score to measure parallel-vs-sequential against; without it we'd be tuning plan shape against an LLM's coverage guess.
- **Code (when built):** new `harness/TaskWaveScheduler.java`, `harness/SequentialExecutor.java#execute`, `agent/SmartClassifierAgent.java` + `agent/Classification.java` (per-strategy caps), `prompts/outline-planner*.md`.
- **Status (2026-05-20):** NOT shipped. Design recorded above. Deferred to a focused session because (1) the concurrency half can corrupt customer code and is unprovable without a live run, and (2) the task-count half is blind tuning until measured by eval — shipping either without validation would be a superficial fix. RL-2026-05-001 + RL-2026-05-005 (shipped this session) are the prerequisites that make it safe and measurable.
- **Update (2026-05-21):** lever (d), the planner prompt flip from "single-file" → "single-responsibility / fewest-cohesive-tasks", was carved out and shipped on its own as **RL-2026-05-011** (no concurrency, no cap-split, fully reversible). The risky concurrency half (levers a–c, e) and the cap-split (blocker #2) remain deferred here. RL-011 still owes the same wall-clock-vs-verifiedScore eval before either it or this is trusted in prod.

### RL-2026-05-005 — Unify the worker's six overlapping guardrails

- **Change:** Collapsed Lever A (force-edit watchdog), Lever C (completion nudge), and the stagnation warn/force counters into ONE signal: `itersSinceProgress` (consecutive iters with no `writeFile`/`editFile`) + one one-shot nudge at `progressWarnAfter` + force-terminate at `progressForceAfter`. The same nudge also fires on a premature text-only stop (the old Lever C trigger). Kept Lever B (salvage) and the dollar budget cap; wall-clock + iter caps already softened (RL-2026-05-004). State went from `{stagnantIters, stagnationWarned, forceEditNudged, forceEditAtIter, completionNudgeFired}` → `{itersSinceProgress, progressNudged}` (+ `totalWriteCalls`, still needed for the salvage gate).
- **Why:** `WorkerAgent` grew six independent guardrails, each added after a specific bad run. They overlapped and collided — Lever A's force-edit nudge could never fire because the stagnation-force killed the worker first (the comment at the old `forceEditAtIter` line documented this). Six knobs that interact pairwise are unmaintainable; one progress signal is reason-able.
- **Behavior changes (intentional):** (1) a text-only stop now ALWAYS gets one nudge before STOPPED_WITHOUT_COMPLETE — the old Lever C only nudged when writes>0 AND the text matched a summary keyword. The keyword heuristic (`looksLikeSummary`) is deleted; nudging on any text-only stop is more robust. ### RL-2026-05-003 — UNKNOWN coverage damps the TESTS slot, doesn't drop it

- **Change:** in `computeVerifiedScoreAdditive`, treat `testCoverageLevel=UNKNOWN` as a conservative damped value (~50) rather than dropping the TESTS slot entirely.

The rubric now tells the judge to say NONE (not UNKNOWN) when it sees no test files, but the structural hole stays open until real test execution lands (RL-2026-05-001); damping UNKNOWN closes it in the meantime.
- **Tradeoff:** a run whose tests genuinely couldn't be read (truncation) is scored slightly low; acceptable vs the inflation risk.
- **Code:** `report/ValidationReportService.java#computeVerifiedScoreAdditive`.

### RL-2026-05-001 — Execute tests in BUILD mode (the deterministic anchor)

- **Change:** After a BUILD run completes, run the worker-written tests **in the code workspace**, produce a real `TestExecutionSummary` (passed/total), and feed it into the verifiedScore TESTS slot instead of the LLM-judged coverage grade. Flag `scoring.real-test-exec` (default ON, seeded by V203).
- **Why:** BUILD mode never ran tests — `RunTestsTool` is patch-mode/Python-only, and the existing `testgen` executors run a _separately generated_ Maven project against a preview, not the worker's own tests. So verifiedScore "verified" that the build _compiled_ + an LLM's _opinion_ of coverage, never that the code _works_. That's why the score was inflatable (re-calibrating the judge moved 72→90+ with no code change) and why it varies run-to-run (the coverage grade is an LLM guess). Real execution makes the number mean something and removes the dominant variance source — the deterministic anchor under the #4 benchmark-predictability call (single run trustworthy; publish median-of-3).
- **Security:** generated tests are UNTRUSTED code, so execution never uses free-form worker text. The command is **resolver-derived** from on-disk markers (`TestCommandResolver`), **validated** through `ShellSandboxPolicy`, and dispatched inside the `--network none` cleanroom container **where one exists** (SWE-bench / ProgramBench). Plain BUILD mode has no cleanroom container, so tests run on the host shell — the **same trust boundary `buildProject` already crosses every run** when it compiles worker code; not a new boundary. The dispatch mirrors `BuildProjectTool` exactly (container routing + PATH/HOME/JAVA_HOME hardening + per-suite timeout), in a dedicated tool-layer service — NOT raw `ProcessBuilder` from the orchestrator.
- **Fail-safe:** no recognized runner, a sandbox-blocked command, a timeout, an IO error, or unparseable output all yield `Optional.empty()` → the scorer falls back to the (damped) LLM coverage path. Worst case = "no change vs today"; the headline can only get more honest, never break.
- **Tradeoff:** adds up to one per-suite timeout (360–600s cap) of latency to each BUILD run — latency is already the binding constraint (Gemini HIGH ~87 min). The cap is a ceiling not the expected time, it runs once at end-of-run (not per task), and the flag is the kill switch if a slow suite hurts the run-terminal-in-15min SLO.
- **Known limitation:** multi-repo runs resolve at the top workspace root; per-`repos/<name>/` execution is not yet wired (resolver returns empty there → coverage fallback, no regression).
- **Code:** `smoketest/TestCommandResolver.java` + `smoketest/TestOutputParser.java` (resolver + parser) + `smoketest/WorkspaceTestRunner.java` (sandboxed dispatch), wired into `integration/RunOrchestrator.java#generateValidationReport` (the `ReportInput` seam, replacing the 5-arg constructor). Flag seeded by `db/migration/V203__seed_real_test_exec_flag.sql`.
- **Status (2026-05-20):** SHIPPED + unit-tested (`TestOutputParserTest` 9/9, `WorkspaceTestRunnerTest` fail-safe contract). Compiles clean; threads a real `TestExecutionSummary` into the additive TESTS slot. Still needs a live full-pipeline run per provider to confirm the resolver picks the right command on real generated projects.
