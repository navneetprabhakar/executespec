## 0. Verdict in one screen

**The product is mature and the engineering quality is genuinely high.** Security, reliability infra
(transactional outbox, boot crash-recovery, cost attribution, sandboxing), and — critically — **the LLM
prompts are competitive with Codex/Claude Code.** The accuracy gap is **not** in prompt wording.

**The benchmark that matters** (latest `scripts/v2-eval-results/`, 2026-05-28, SWE-bench-shaped mixed10×3,
all on Claude Sonnet 4.6):

| System | Resolved | Notes |
|---|---|---|
| **Claude Code** | **20 / 30** | reference |
| **Codex** | **16 / 30** | reference |
| **ExecuteSpec (Anthropic)** | **15 / 30** | same model, same tasks |

ExecuteSpec ≈ Codex, ~5/30 (≈17 pp) behind Claude Code **on the same model**. Because the model is
identical, **the gap is harness mechanics**: context management, in-loop verification, multi-file
under-scoping, and the absence of cross-task/cross-attempt memory — every one of which already has a
**built-but-flag-OFF** lever in the codebase. The single highest-leverage move is to **validate and turn on
the work that's already written**, not to write new prompts.

**Cost headline:** the biggest single cost lever — `harness.v2.batch_enabled` (≈50% via provider batch
APIs) — is seeded **OFF** (V117). Several smaller cost leaks are catalogued in §B.

## A. ACCURACY levers (ranked) — closing the 15 → 20 gap

### A1. 🔵🔴 Turn on the four dormant TRANCHE-3 worker levers (after eval) — **the headline lift**
All built, all default-OFF, all explicitly designed to close this exact gap (~+8–12 pp combined per the
2026-05-28 roadmap):

| Flag (migration) | What it does | Why it helps accuracy |
|---|---|---|
| `worker.tool-compactor.enabled` (V216) | routes >3 KB tool output through Haiku/Flash before it lands in the WORKHORSE history | the V2 worker keeps **full, uncompacted history** today → long tasks blow the context window and degrade reasoning. This is the same pattern Claude Code uses internally. |
| `worker.build-tdd.enabled` (V217) | exposes `runWorkspaceTests` so BUILD-mode workers validate their own tests **in-loop** | today workers learn about test failures only in the post-completion scoring phase — too late to fix. TDD-in-loop is the largest single SWE-bench lever in the roadmap. |
| `worker.provider-prompt-tuning.enabled` (V219) | swaps in the per-provider fragments (cache discipline, batched edits, unique tool-call ids) | the fragments (`prompts/fragments/provider-*.md`) are excellent and already written — they're just not injected. |
| `worker.cross-provider-fallback.enabled` (V220) | on persistent task failure, retry on a different provider (hard ceiling) | a task one model can't crack often falls to another. |

**Action:** run the blind SWE-bench harness (`benchmark/`) with each flag on, in isolation then combined,
on `dev`; promote the winners. This is the P0 accuracy work and it's mostly *validation*, not *building*.

### A2. 🔵 Worker context compaction is the root accuracy constraint
`engine/WorkerAgent` keeps its **entire** conversation history (confirmed — CLAUDE.md: "the V2 worker keeps
its FULL conversation history (no sliding window)"). On MEDIUM/HIGH tasks (75–120 iters) this is the most
likely cause of late-iteration quality collapse. A1's tool-compactor is the first dose; a follow-up is a
genuine sliding-window / summarize-old-turns policy for the decision context (Claude Code does both).

### A3. 🔵 Multi-file **under-scoping** is the dominant benchmark miss
The `benchmark/` checkpoint identifies under-scoping of multi-file changes as the recurring failure. The
skeleton planner's "blast radius" rule (`prompts/outline-planner-skeleton.md` §7) is the right instinct but
only fires on existing-repo runs. Tighten the expander/coherence passes to enumerate **all** call-sites of a
changed shared mechanism, and add a reviewer-pass check that the diff touched every site the plan named.

### A4. 🔵 No interrupt check in the worker → runaway passes burn tokens *and* can't be cancelled
`WorkerAgent` never checks `isInterrupted()`; the reviewer's per-pass `future.cancel(true)` cannot stop a
runaway, and a timed-out reviewer pass keeps generating to completion (charged). This both wastes cost (§B)
and lets a stuck pass crowd out useful work. Add a cooperative interrupt check in the tool loop; pass
`wallClockSeconds` into the reviewer.

### A5. 🟡 Confidence gap: **`engine/WorkerAgent` + `CodeGenEngine` have ZERO unit tests**
The core codegen loop is tested only indirectly via integration runs. You cannot safely iterate on A1–A4
without a regression net. Scoring is well-pinned (6 `ValidationReportService*Test` files); the **loop** is
not. **Add unit tests for the worker tool-loop, prompt assembly, and LLM-output parsing (malformed/partial
JSON, not just happy-path fixtures) before flipping the A1 flags.** This is the highest-value test work and
a prerequisite for confident accuracy tuning.

### A6. 🔵 Two live scoring regressions modestly mis-score honest runs (measurement accuracy)
- The additive gaming-guard re-injects the LLM endpoint-coverage false-low into CODE_DELIVERED **without**
  the reviewer-CLEAN/FIXED trust-gate the legacy multiplicative path had (`report`).
- The dashboard `llmCoverageLevel` doesn't handle the GOOD/PARTIAL bands the accuracy prompt now emits
  (`scoring`).
Both make a correct run look worse than it is — which corrupts the eval signal you're tuning against.

## B. EFFICIENCY / COST levers (ranked)

### B1. 🔵 `harness.v2.batch_enabled` is OFF (V117) — **~50% cost** via provider batch APIs
Single biggest cost lever in the codebase, seeded `false`. The `batch/` package, however, is an **unbuilt P1
scaffold (every method throws `UnsupportedOperationException`, 0 client beans)** — so this is *build + flip*,
not just flip. Worth scoping: 50% on the LLM bill is the dominant line item.

### B2. 🔵 LLM calls that bypass `RunCostTracker` → under-counted spend
- `assessment/FeatureAssessmentService` calls the Anthropic bean **directly** (latent, flag-gated) — escapes
  cost tracking entirely.
- Usage-report emails **re-estimate** cost at stale blended-Haiku rates instead of summing the authoritative
  `pipeline_run.actual_cost_usd`.
Both under-report real spend; route every provider call through `LlmRouter`/`RunCostTracker` and sum the
persisted actuals for reporting.

### B3. 🔵 DeepSeek native client lands cost **and** latency
Roadmap-measured: `deepseek-v4-pro` native (`api.deepseek.com`) ≈ 8 min/instance vs ≈ 18 min routed through
OpenRouter for the same model. The native client is written (`feat/benchmark-codegen-harness`) and awaits a
local key for smoke — a cheap latency + per-call-overhead win for the BYOK/enterprise gateway.

### B4. 🔵 `findAll()-then-filter-in-heap` on hot paths
Recurs in: `project` dashboard (run + launch halves, ~2K + 2K rows, **hot path**), `state` admin analytics
(model-comparison + per-user), `referral.recordInvite`. Push `SUM`/filters into the query. The project
dashboard is the one users hit constantly — it loads all runs into the heap to compute cost.

### B5. 🔵 Polling instead of events for cross-lane status
The V3 Launch lane mirrors V2 run status via a **4h `Thread.sleep`-poll-per-launch** thread (and a 2h variant
in the legacy per-Solution executor), even though `IntegrationOutboundListener` already proves the
event-driven (`PipelineEvent`) path. One idle thread per launch is wasted; replace with a listener keyed by
`pipelineRunId`.

### B6. 🔵 Reviewer keeps burning tokens after a timed-out pass — see A4 (cost + accuracy overlap).

> Already-good cost discipline worth preserving: cache-aware `RunCostTracker` across all 3 providers, Gemini
> all-Flash tiers (real implicit-cache hits), `readFile`/`shell` truncation budgets, per-phase cost
> attribution, the `lint` pre-reviewer formatter pass (token saver). The foundations are solid; the leaks
> above are the deltas.

## E. The 4 founder-reported UI bugs (all confirmed in code, frontend-only — see [`ui-bugs-2026-05-29.md`](ui-bugs-2026-05-29.md))

1. **No Approve button on `/result/{id}`** — `IdeRunResult.tsx` computes `terminal/canPause/canResume` but
   **no `canApprove`**; an `AWAITING_APPROVAL` run opened at `/result/:id` shows Pause, no Approve (the gate
   lives only on `/plan/:id`). Fix: redirect/ inline-gate when `status==='AWAITING_APPROVAL'`.
2. **No notification bell** — `IdeWorkspace` renders no bell; the inbox (`IdeSystem.IdeNotifications` +
   `getUnreadCount`) is reachable only by URL. The `Bell` icon already exists in `signal/icons/icons.tsx`.
   Fix: add a bell with an unread-count poll to the activity bar + Console shell.
3. **Two different run views** — `/live/:id` (SSE console) vs `/result/:id` (file-tree + tabs); same run
   "changes UI" on completion. Larger UX item; aligns with the control-plane reframe.
4. **Live log dumps raw JSON** — `IdeRunResult.logMessage()` falls through to `d.payload` (the entire
   `RUN_DETAIL` JSON) and the Logs `.map()` has no type filter; the live path (`useSse.ts`) already skips
   `RUN_DETAIL`. Cleanest fix: mirror that skip in the replay renderer.

Minor UI consistency: `IdeRunResult` + `IdeProjectTabs.RunDetailPanel` use a local `≥90` "Shippable"
threshold that drifts from the canonical `verdictFor` (`≥85`); the public `PublicPricingPage` advertises a
fictional **"SOLO $29" tier** that maps to the HIDDEN/unbuyable PRO tier (marketing divergence, also on the
website).

You are **one tranche of validation-and-flip away from the Codex tier and within reach of Claude Code** — on
the *same* model — because the levers that close the gap are **already written and sitting behind flags**.
The prompts are not the problem; they're a strength. Spend the next cycle on: (1) a test net for the worker
