# Audit: `finding/` + `prreview/` (+`inbox/`) + `codereview/` — the autofix chokepoint + the two paid review agents

Status: **DONE** · Updated 2026-05-29 · 27 files / ~2,900 lines · all substantive files read in full

## What it does
The customer-facing review + autofix surfaces. `finding/FindingPatchSubmitter` is the **single chokepoint** every "Fix this" affordance routes through (PR-review autofix, tech-debt fix, code-review autofix, CI-failure autofix → all adapt to a `Finding` record → `submitRun(runMode=PATCH, source="finding:<TYPE>")`). `prreview/` is the per-PR senior-review agent (PLANNING tier, single `submitReview` tool call) + the inbound PR-comment inbox. `codereview/` is the whole-repo two-stage scan (semgrep static + LLM augmentation/triage → severity-grouped markdown report + autofix-per-severity).

## Findings — uniformly well-built + properly gated; two real defects worth fixing.

### 🟡 Real bug — `SemgrepRunner` silently drops ALL static findings whenever semgrep is present
`codereview/SemgrepRunner.scan` ([SemgrepRunner.java:117-163](../../../src/main/java/com/navneet/executespec/codereview/SemgrepRunner.java)) captures the subprocess stdout/stderr into **`ThreadLocal<String>` instance fields** (`capturedStdout`/`capturedStderr`). But the `set()` runs on the spawned `semgrep-stdout`/`semgrep-stderr` threads while the `get()` runs on the **calling** (`code-review-dispatch`) thread — and ThreadLocal storage is per-thread, so the calling thread's `get()` always returns null → `stdout=""` → `parse("")` → **empty findings, every time**. The author's comment ("keyed off the current Thread so concurrent scans don't overwrite each other") reveals the wrong mental model: the isolation they wanted is already provided by `scan()` being a fresh stack frame; ThreadLocal is exactly wrong here.
- **Impact today: masked.** semgrep isn't installed in the prod GCE container (CLAUDE.md "outstanding: semgrep auto-installation"), so `available=false` short-circuits before this code. The LLM-only pass carries the feature.
- **Impact when the planned semgrep-in-prod work lands:** the static half of the headline "two-stage" review silently contributes **zero** findings, and the SSE log even prints a reassuring `✓ Semgrep: 0 findings across 0 files` — looks like a clean repo, not a broken capture. A paid feature degraded invisibly.
- **Fix (trivial):** replace the two ThreadLocal fields with two effectively-final local holders captured by the lambdas (`AtomicReference<String>` or `String[1]`). ~4 lines. (Worth a unit test that feeds a known semgrep JSON through a stubbed process.)

### 🟡 Privilege inconsistency — PR-review autofix is `assertCanRead`, code-review autofix is `assertCanWrite`
Both `POST /api/pr-reviews/{id}/autofix` and `POST /api/code-reviews/{id}/autofix` dispatch a PATCH run that **pushes commits** (PR-review → onto the PR head branch via `branchOverride`; code-review → a fresh draft PR). `CodeReviewController.autofix` ([line 110](../../../src/main/java/com/navneet/executespec/codereview/CodeReviewController.java)) correctly calls `projectAccessGuard.assertCanWrite` with an explicit "PROJECT_VIEWER must not be able to trigger this" note. `PrReviewController.autofix` ([line 112](../../../src/main/java/com/navneet/executespec/prreview/PrReviewController.java)) calls only `assertCanRead` — so a read-only `PROJECT_VIEWER` (the cross-org V175 member role) **can dispatch a code-pushing autofix run on a PR**. It slips past `AccessGuardCoverageTest` because that ArchUnit pin only inspects URLs containing `/projects/{`,`/runs/{`,… — `/api/pr-reviews/{id}` matches none. One-line fix: `assertCanRead` → `assertCanWrite`. (Mirror of the RL-2026-05-040 read→write hardening that already swept `project/`.)

### 🟢 Everything else is clean
- 🟢 **Tier+quota gating is a single chokepoint per surface.** `PrReviewService.assertTierAndQuota` / `CodeReviewService.assertTierAndQuota` — FREE→403 (`TierBlockedException`), monthly cap via `tier_config.{pr,code}_review_monthly_quota` (-1 unlimited / 0 blocked) counted by `countByUserSince(userId, monthStartUTC)` → 429 (`QuotaExhaustedException`). Controller maps both cleanly.
- 🟢 **Cost attribution is correct (no bypass).** Both agents route through `LlmRouter` (not the deprecated `FallbackLlmRouter`, not a direct provider call) and `costTracker.record(...)` into a per-review/`code-review-{id}` synthetic bucket, snapshot→persist→`finalizeRun` (frees the bucket). This is the *right* pattern — contrast the [codeintel.md](codeintel.md) `RunCodeMapService` + [assessment.md](assessment.md) direct-`anthropicModel.call` bypasses.
- 🟢 **Idempotency by SHA** — PR review keyed `(repo, pr, head_sha)`, code review `(project, repo, scanned_sha)`; COMPLETE/RUNNING short-circuits, FAILED/stalled re-queues. `FindingPatchSubmitter` dedupes against any active run for the same `findingKey` (`REUSED_ACTIVE`) so impatient operators / duplicate webhooks can't double-PR.
- 🟢 **No shell-injection surface.** `SemgrepRunner` uses `ProcessBuilder(argv-list)` + `--metrics=off`/`SEMGREP_SEND_METRICS=off` (no telemetry egress), concurrent stdout/stderr drain (the *intent* behind the buggy ThreadLocal), 600s timeout + `destroyForcibly`, tolerant of exit 0/1, warns on 2+.
- 🟢 **Bounded LLM payloads.** Code-review file sampling caps total walk at 5,000 files, 20 files in-prompt, 12 KB/file, risk-scored (controllers/auth/sql/config boosted, tests/md/tiny penalised, semgrep-hot files +50). Autofix prompts cap 25 issues + 600-char suggested-fix each.
- 🟢 **Inbox is `RunAccessGuard`-gated + id-fuzz-defended.** `PrCommentInboxService.findForRun` re-checks the comment belongs to the run; ingest silently drops comments on non-ExecuteSpec PRs (no `PullRequestRecord` match); status transitions one-way. `PrCommentInboxController` apply path dispatches `ApplyService` async on a 2-thread pool, draining on `@PreDestroy`.
- 🟢 **`Finding` record validates its own invariants** (id non-blank + no `:` separator collision, projectId/userId/userPrompt required) so a malformed finding can't produce a corrupt `triggered_by_finding` key.

### 📝 Minor / notes
- 📝 PR-review provider is hardcoded `"anthropic"` ([PrReviewService.java:261](../../../src/main/java/com/navneet/executespec/prreview/PrReviewService.java) — "default for now; PROJECT-aware override in slice 3") and code-review agent request hardcodes `.provider("anthropic")`. Coincidentally right (Anthropic is the project default now) but should read the project's configured provider. Same stale-default shape as the [codeintel.md](codeintel.md) OPENAI-default notes, just landed on the right answer.
- 📝 Both services persist via **drop-and-replace** comments/issues on re-run (cheaper than diffing for a single review) — fine, but means an in-flight reader during `completeReview` could see a momentary empty set. Low risk (single review, fast).
- 📝 `CodeReviewService.completeScan` re-persists STATIC findings the agent neither dropped nor rewrote as first-class `source=STATIC` rows — good for dashboard honesty, but entirely downstream of the SemgrepRunner bug (today the static set is always empty when semgrep runs).
