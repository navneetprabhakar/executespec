# Audit: `chat/` + `specchat/` + `folder/` — copilots + CLI chat skeleton + `.executespec/` writer

Status: **DONE** · Updated 2026-05-29 · 15 files / ~3,180 lines · all read in full

## What it does
- **`chat/`** (4) — the live post-run copilot. `ChatService` = read-only Q&A over a terminal run's workspace + validation report (LIGHTWEIGHT tier, manual 4-round tool loop, `RunChatTools` read-only `list_run_files`/`read_run_file`). `ApplyService` = the write-path "Apply to Run" surface: a single `WorkerAgent` session with full tools against an existing terminal-run workspace → `PostEditFormatter` → `ScmPushService.pushApplyChanges` (fast-forward to the PR branch). `ApplyResultStore` = Redis (1h TTL) so the UI can poll the apply outcome after the POST stream dies.
- **`specchat/`** (4) — the **CLI/VS-Code chat endpoint** `POST /api/spec/chat` (JWT or `es_pat_` PAT). `ProjectChatActionTools` = write-capable tool factory (submit_run/approve/reject/cancel/list/report). `SpecChatAudit` = audit-only row (no message content, V218).
- **`folder/`** (7) — `ExecutespecFolderWriter` is the single chokepoint for all `.executespec/`-folder writes to customer repos (PR-mode / DIRECT_PUSH, content-hash pre-flight to skip empty PRs). `BootstrapService` opens the initial setup PR on repo-link (PAT scope pre-flight). `ProjectConfigPathResolver` (confidential-project DATABASE opt-out). `ExecutespecMigrationController` (SUPER_ADMIN one-shot backfill).

## Findings — well-built; the one notable thing is a dormant skeleton + a latent gap behind it.

### 📝 `specchat/SpecChatController` is a Phase-1 SKELETON — the chat loop is not implemented
`POST /api/spec/chat` validates the request, upserts the audit row, and returns a **placeholder SSE stream** (`token` event literally emits `"[Phase 1 skeleton — chat loop lands in follow-up commit]"`) — there is **no `LlmRouter` dispatch and no tool execution yet**. Consequently `ProjectChatActionTools` (the 6 write-capable tools) is fully built but **bound by nobody** — another "built, not yet wired" instance, though here it's an explicitly phased rollout (RL-2026-05-052), not abandonment.
- 🟡 **Latent gap to close when Phase 2 wires the loop:** `ProjectChatActionTools.submit_run` calls `runOrchestrator.submitRun(...)` directly with the **user's free-text spec**, but — unlike `api/RunController` — it does **not** run `inputSanitizer.scan(spec)` and does **not** call `tierEnforcementService.assertAndIncrementRunCount`. So once activated, the CLI chat path would be a **prompt-injection-sanitization + run-quota bypass**. (It DOES correctly force `skipApproval=false` so the plan gate always runs, and every tool re-checks `runAccessGuard.requireRunAccess` inside its body — the tenant story is fine; the sanitize+quota story is the hole.) Flag this the moment the loop lands. Same shape as the api.md note that the *finding* path re-sanitizes but this one wouldn't.
- 🟢 Privacy: `SpecChatAudit` stores **no message content** (audit-only: session/user/org/ip-hash/turn-count/cost) per the LOCAL-ONLY chat-persistence decision. IP is SHA-256-hashed. Good.

### 🟢 `chat/` is clean
- 🟢 **`ChatService` + `RunChatTools` are genuinely read-only** — no write/shell/push/re-run tool exists; routed through `LlmRouter` (cost-tracked, run-scoped `ExecutionContext`), bounded (50 user-msg cap, 120-line tree, 4 tool rounds, 8 KB/file read, 1200-token reply). Injects the validation-report block so score questions are grounded, not hallucinated. The right design for an advisory copilot.
- 🟢 **`ApplyService` is the correct write-path** — terminal-runs-only, worker prompt explicitly forbids formatters/tests/git-mutations (push happens out-of-band via `ScmPushService` fast-forward-only), runs `PostEditFormatter` post-worker (fixes the "CI turns red on unformatted apply" incident), persists lifecycle to `ApplyResultStore` so a severed POST stream doesn't lose the outcome. Deliberately NOT `@Transactional` (would pin Hikari across the worker loop — same reasoning as `codeintel`/`project`). Iter cap 60, ×2 for project-scoped.
- 📝 `ApplyService.tryGitCommit` + `runCmd` are **dead** (`@SuppressWarnings("unused")`, retained as a documented escape hatch after "Fix L" moved to per-repo push). Small dead code — honest about itself.

### 🟢 `folder/` is clean + well-built
- 🟢 **`ExecutespecFolderWriter` enforces its own invariant** — every write/read path passes through `requireFolderRoot` (rejects anything not under `.executespec/`), so it can't be coerced into writing arbitrary repo paths. Content-hash (SHA-256) pre-flight skips no-op PRs (the empty-PR-cycle fix), idempotent branch create (tolerates 422 "already exists"), per-user PAT, project-namespaced config paths.
- 🟢 **`BootstrapService` PAT scope pre-flight** — one cheap `GET /user`, reads `X-OAuth-Scopes`, rejects read-only PATs with an actionable message *before* attempting the PR; tolerates fine-grained tokens (no scope header) by deferring to the real call. `@Async`, never crashes the link response.
- 📝 **Stale "system PAT fallback" comments** in `ExecutespecFolderWriter` javadoc (`@param actorPat … falls back to system PAT`) and `ExecutespecMigrationController` (`falls back to system PAT inside the writer`). There is **no system PAT** (removed 2026-05-23) — the code correctly returns null when no actor PAT (`BootstrapService.effectivePat` even *says* "no system fallback" in its error). Behaviour right; 2-3 comments lie. Trivial doc drift.
- 🟢 `ExecutespecMigrationController` is `@PreAuthorize("hasRole('SUPER_ADMIN')")` + idempotent (skips BOOTSTRAPPED/PR_OPEN, re-attempts only FAILED).
