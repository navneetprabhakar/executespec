## Integration framework (inbound webhook hub + outbound listener)
### Findings
- 🟡 **Integration-triggered runs submit with NULL user/org attribution — the E#36 fix was documented but never wired.** `IntegrationManager.submitIntegrationRun` stamps `runnerUserId`/`runnerOrgId` from `resolveIntegrationRunnerUserId`/`resolveIntegrationRunnerOrgId`, but **both are hardcoded `return null` stubs** with a TODO ([IntegrationManager.java:100-108](../../../src/main/java/com/navneet/executespec/integration/IntegrationManager.java)). So every webhook-triggered run (Jira/PagerDuty/ServiceNow/Confluence/Bitbucket inbound) runs with no billing attribution, no tenant scoping, and no project memory — AND submits as `executionMode="PROTOTYPE"` + `autoMerge=true` (bypasses the plan-approval gate, auto-merges). Blast radius is limited to orgs that have wired an inbound integration, but for those it's uncharged + untenanted auto-executing runs. The javadoc presents this as a "legacy dev path" fallback, but the stubs make it the *only* path.
- 🟢 **Inbound webhook security is otherwise solid**: `handleWebhook` does `adapter.verifySignature` first, then idempotency via `IntegrationEventLog.existsBySourceTypeAndEventId` (persisted *before* submit to win webhook-retry races), then `sanitizeAndCap` on all external Jira/Confluence content before it reaches the planner — strips `SYSTEM:`/`ASSISTANT:`/`<|…|>`/`###system` prompt-control seeds + 4K-caps each field (audit D#31 prompt-injection defense). Good.
- 🟢 `IntegrationOutboundListener` is cleanly separated (reacts to `PipelineEvent` only, no orchestrator dependency), listens to `MergeCompleted` (not `RunCompleted`) so the review report exists, and wraps the virtual-thread task in `ContextSnapshotFactory.captureAll().wrap()` for traceId propagation (the CLAUDE.md MUST pattern). 
- 🟢 `PerkyMessenger` is a harmless cosmetic SSE heartbeat (encouraging phase messages + keeps the stream warm past proxy idle timeouts); daemon scheduler with graceful shutdown.

### Security (integration-subsystem, to confirm wiring)
- 🟡 **`ReferenceExtractorService` is UNWIRED (dead) — and carries a latent self-SSRF.** `grep extractAndEnrich src/main` = **zero callers** — the Jira/Confluence spec-enrichment service is never invoked on any path (not in RunOrchestrator's 5,300 lines, not anywhere). So it's another built-but-unwired service (cf. the dead `validator/` + scoring-revamp scaffolds in Tiers 1-2). The latent issue if revived: org-admin-configured `jiraBaseUrl`/`confluenceBaseUrl` flow directly into `integrationRestTemplate.exchange(url, …)` ([lines 264-327](../../../src/main/java/com/navneet/executespec/integration/context/ReferenceExtractorService.java)) with no host allowlist — a self-SSRF (org's own creds + own run context, so low severity) that should get a host denylist before wiring. Issue-key/page-id path components are regex-constrained. Inert today.
- 🟢 `ReferenceExtractorService` is otherwise careful: non-fatal fetches, Basic-auth from org creds, ADF→text + HTML-strip, 4K content cap, vague-mention → clarification-signal instead of a bad fetch.

## RunOrchestrator.java — the V2 pipeline conductor (5,300 LOC)
The single most central backend file. `submitRun` persists the `pipeline_run` row + dispatches `runPipeline` on a daemon pool; `runPipeline` is the ~950-line sequential conductor: BYOK key resolve → `RunModelOverrides` bind (org overrides + ENTERPRISE per-run pin) → workspace init + multi-repo clone → **PATCH dispatch** OR build-mode [codemap → assessment → classify(`runClassifierShadow`) → plan(`runOutlinePhase`/`runLargePipeline`) → plan gate → execute → CODEGEN_ONLY-stop → lint → review → enterprise enforcement → README → `resolveTerminalStatus` → validation report (+ `synthesiseReviewIssues`) → testgen/CLI-smoke → commit → memory ledger → terminate → auto-push]. Also owns cancel / pause / resume / crash-resume / retry-task / re-review / halt-all / force-fail.

### Findings

#### Correctness / reliability
- 🔵 **cancel / pause cannot stop in-flight LLM work — confirms the engine no-interrupt finding.** Both `cancel` ([line 2250-2254](../../../src/main/java/com/navneet/executespec/integration/RunOrchestrator.java)) and `pause` ([line 2317-2321](../../../src/main/java/com/navneet/executespec/integration/RunOrchestrator.java)) do `future.cancel(true)` but the code itself states "the pipeline is not cancellation-aware at every step, so it may continue briefly" and "the in-flight LLM round-trip is NOT cancelled." Since `WorkerAgent` has no `isInterrupted()` check ([engine.md](engine.md)), a cancelled/paused run keeps burning **charged** LLM tokens until the next cooperative task/iteration boundary (or natural completion). Terminal-write correctness is preserved (the `terminate` guard at [line 3341](../../../src/main/java/com/navneet/executespec/integration/RunOrchestrator.java) won't clobber CANCELLED), but the spend is real. Same root cause as the reviewer-timeout leak ([reviewer.md](reviewer.md)).
- 🟡 **LARGE-pipeline expansion can starve its own thread pool.** `runPipeline` runs *on* a `pool` thread (size `clamp(4,16,cores)`); `runLargePipeline` then submits N `CompletableFuture.runAsync(..., pool)` expansion tasks **to the same pool** and blocks on `allOf().get(20min)` ([line 4906-4951](../../../src/main/java/com/navneet/executespec/integration/RunOrchestrator.java)); `expandEpic` nests another `.get(10min)` on the same pool. Under concurrent LARGE load (≥`poolSize` runs all blocked awaiting expansion), the expansion subtasks can't get a thread → every LARGE run stalls until its 20-min timeout fires, then degrades to SINGLE_SHOT. Not a permanent deadlock (timeout breaks it) but a real throughput/latency cliff. Fix: a separate bounded pool for expansion, or cap concurrent LARGE runs.
- 🟢 Per-phase token attribution is meticulous — `costTracker.snapshot` deltas around classifier / outline / expansion / coherence / planner / worker / reviewer, each persisted to its own `pipeline_run.*_tokens/_cost_usd` column. This is the backbone that makes per-phase cost honest ([cost.md](cost.md)). Strong (cost-priority positive).
- 🟢 `resolveTerminalStatus` is a clean authoritative state machine (build-pass + CLEAN/FIXED ⇒ COMPLETE; build-fail ⇒ PARTIAL/FINAL_BUILD_FAILED; etc.) and is reused by every terminal path (normal / resume / retry / re-review) — the consistency the R-09 reconcile in [report.md](report.md) depends on.
- 🟢 Crash-resume (`resumeAfterCrash`) restores the workspace from a GCS checkpoint before failing WORKSPACE_GONE (RL-2026-05-041 #2), caps resume attempts, and refunds via `RunFailed`. Durability is real.

#### Accuracy / scoring tie-ins
- 🔵 `synthesiseReviewIssues` ([line 4046](../../../src/main/java/com/navneet/executespec/integration/RunOrchestrator.java)) is the **source of the `SYNTH-*` issues** the Tier-2 scoring checkpoints reference: SYNTH-BUILD (×2), SYNTH-REV, SYNTH-FIX (visibility-only), SYNTH-ACC-MISS/PART/EP (from the accuracy LLM, capped 5 each), SYNTH-CONTRACT. Confirms the `countUnfixedCritical` SYNTH-ACC filter chain in [report.md](report.md): the accuracy LLM's missing/partial/endpoint findings are fabricated into CRITICAL issues here, then filtered out of the headline penalty downstream. The cap-at-5 bounds the blast radius.
- 🔵 `generateValidationReport` runs `AccuracyAssessmentService.assess` **inline with an empty issues list** ([line 3669-3675](../../../src/main/java/com/navneet/executespec/integration/RunOrchestrator.java)) — the reviewer emits no structured issues, so accuracy scores with no reviewer-issue context, then its output is fabricated back into issues. Circular but functional.

#### Tech-debt
- 🟡 **The defining god class — now 5,300 LOC** (CLAUDE.md says 4,828; it grew), ~70 methods, ~40 injected dependencies. **6 `submitRun` overloads** (13→20 args) + **6 `runPipeline` overloads** form a telescoping-constructor chain; **4 near-duplicate orchestration tails** (`runPipeline` / `runPipelineFromExecuteCheckpoint` / `retryTask` / `reReview` each re-resolve provider+model, rebuild `ExecutionContext`, call executor→reviewer→report→terminate). Extracting a `PipelineStageRunner` + a parameter object for submit would cut this materially. Highest-value backend refactor target.
- 📝 **Inconsistent + stale fallback-provider defaults.** `DEFAULT_PROVIDER = "openai"` ([line 124](../../../src/main/java/com/navneet/executespec/integration/RunOrchestrator.java)) and the fallbacks in `reReview` / `runClassifierShadow` / `providerForAccuracy` all default to OpenAI, while `runPipelineFromExecuteCheckpoint` + `retryTask` default to "anthropic". CLAUDE.md says the platform default is **Anthropic since 1.0.0-M1**. Only fires when `aiProvider` is null with no project default (the API layer normally supplies one — verify in Tier 7 `api/`), so latent, but the constant is stale and the inconsistency is a footgun.
- 🟡 Density of swallowed exceptions: almost every stage is `try/catch-log-continue`. Appropriate for pipeline resilience, but failure diagnosis becomes log-archaeology and silent degradation (e.g. accuracy-assess failure → null → score path) is easy to miss.

## scm/ScmPushService.java — multi-repo branch + PR push (764 LOC)
### Findings
- 🟢 **No system GitHub PAT** — `resolvePat` is run-PAT → owner-PAT (fresh re-read) → `null` (skip push, no platform token). Matches the CLAUDE.md "every GitHub op uses the caller's own PAT" guarantee.
- 🟢 **Orphan-branch cleanup saga** — when the branch pushes but PR-create returns null, `enqueueOrphanBranchCleanup` enqueues a `COMPENSATE_GITHUB_BRANCH` side-effect (RL-2026-05-041 #16) so a half-finished push doesn't leave a dangling branch. Good durability hygiene.
- 🟢 Multi-repo push isolates per-repo failure, skips CLEAN (no-diff) repos, writes per-repo commit messages with a 30-line-capped changed-file list (guards the b171fa52 9605-file-leak class), cross-links sibling PR bodies, and persists a representative `github_pr_url` so the UI "Open PR" button shows. `pushApplyChanges` is fast-forward-only to the existing PR branch (no force-push / no PR reopen) and fixes the nested-`.git` submodule no-op (run a076c876).
- 🟢 Bitbucket path honours `Project.branchNamingPattern` (audit P#78 parity).
- 🟡 Minor: `CO_AUTHOR_TRAILER` hardcodes `admin@executespec.ai` (self-noted "can be made org-configurable later").

## Outbound-notification subsystem (Slack + 5 source adapters)
All gated by `agent.integrations.enabled` (master, default false) + per-adapter `enabled` (default false) — so every finding below is **latent unless an operator opts in and configures credentials**. Slack is outbound-only (OAuth bot + event-driven Block Kit posts); Jira/PagerDuty/ServiceNow/Confluence/Bitbucket are bidirectional (inbound webhook → run, outbound comment/transition on status).

### Findings
- 🟡 **Inbound webhook-signature quality is inconsistent across adapters — two are weak.** Of the 5 inbound adapters:
  - **ServiceNow, Confluence, Bitbucket** — proper HMAC-SHA256 over the raw body + **fail-CLOSED** (reject when a secret is configured but the signature header is missing). Correct.
  - **PagerDuty** — proper HMAC-over-body, but **fail-OPEN**: `if (signatureHeader == null || webhookSecret == null) return;` ([PagerDutyAdapter.java:46](../../../src/main/java/com/navneet/executespec/integration/pagerduty/PagerDutyAdapter.java)) — an attacker who simply omits the `x-pagerduty-signature` header bypasses verification entirely.
  - **Jira** — weakest: compares the `x-hub-signature` header **directly against the shared secret** (constant-time, but NOT an HMAC-over-body, so it's a bearer-secret-in-header, not a body signature — replayable across bodies, secret transmitted every request), AND fail-open (blank secret → skip), AND the Atlassian JWT path is an explicit no-op that throws ([JiraAdapter.java:38-59](../../../src/main/java/com/navneet/executespec/integration/jira/JiraAdapter.java)).
  Combined with the null-attribution + PROTOTYPE+autoMerge submit path, a forged inbound webhook to an *enabled* Jira/PagerDuty integration → an uncharged, untenanted, auto-merged run. Fix: make PagerDuty + Jira fail-closed and move Jira to real HMAC-over-body (or Atlassian QSH/JWT). The shared `util/HmacUtil.hexSha256` (used by Confluence) should be the single helper — PagerDuty/ServiceNow/Bitbucket each reimplement the Mac inline (DRY).
- 🟡 **Third-party credentials are stored plaintext in the DB.** `OrgSlackIntegration.bot_token` is a plain `TEXT` column ([OrgSlackIntegration.java:33](../../../src/main/java/com/navneet/executespec/integration/slack/model/OrgSlackIntegration.java)) — a long-lived `xoxb-…` token granting workspace posting. Likewise the `Org` Jira/Confluence API tokens + Bitbucket app password (read by `ReferenceExtractorService`/`ScmPushService`) are plaintext. A DB compromise leaks every connected org's third-party credentials. (PATs are SHA-256 hashed per CLAUDE.md, but those are verify-only; OAuth/API tokens must be reversible — so they want envelope/KMS encryption, not hashing. Check whether `crypto/` is applied here — Tier 5.) Cloud-SQL at-rest encryption may mitigate, but app-level they're cleartext.
- 🟡 `SlackOAuthService`'s OAuth-state HMAC secret is `@Value("${app.jwt.secret:executespec-default-secret}")` ([IntegrationConfig.java:145](../../../src/main/java/com/navneet/executespec/integration/IntegrationConfig.java)) — a **known default** if `app.jwt.secret` is unset. CSRF protection on the Slack install flow collapses to a public secret in that case. Fine *iff* prod hard-requires `app.jwt.secret` (it's also the JWT signing key) — verify that requirement in Tier 5 `auth/`.
- 🟢 **Otherwise the subsystem is well-built**: `SlackOAuthService` uses HMAC-signed state + 5-min TTL + constant-time compare (audit C#24); `SlackNotificationService` is tier-gated (PRO/ENTERPRISE), verbosity-filtered, rate-limited (1.1s/workspace), async, and self-heals on `token_revoked`; outbound adapters are pure comment/transition posters with per-call try/catch; idempotency log + Slack log both have retention-cleanup crons. Clients are thin REST wrappers (Basic/Bearer/Token auth). Webhook payloads are `@JsonIgnoreProperties(ignoreUnknown=true)` records.
- 🟡 Minor: `SlackRateLimiter` has a check-then-put TOCTOU (could let 2 concurrent sends slip through → occasional Slack 429, handled) + an unbounded `lastSendTimestamps` map (one entry/workspace, never evicted). Outbound adapters use the **deprecated env-var credentials** (`config.getEmail()/getApiToken()`) not per-org DB creds — a single Jira/Confluence account drives all orgs' outbound writes.
