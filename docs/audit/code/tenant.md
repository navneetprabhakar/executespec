Status: **DONE** · Updated 2026-05-29 · 4 files / 199 lines · all read in full

## Headline finding (closes the open question from [state.md](state.md))
- 🔴 **`@EntityListeners(TenantInterceptor.class)` does NOT scope queries — it only stamps `tenantId` on INSERT.** `TenantInterceptor` is a single `@PrePersist` hook that fills the `tenantId` column from `TenantContext` at write time. There is **no read-side enforcement**: grep-confirmed **zero** `@Filter` / `@FilterDef` / `session.enableFilter` anywhere in `src/main/java`, and **nobody reads `TenantContext.getTenantId()` outside the `tenant/` package** (only the prePersist stamp + the tracing accessor consume it). So any repository query that doesn't *manually* add `WHERE tenant_id/org_id/user_id = ?` returns cross-tenant rows, and nothing at the ORM layer catches it. Only **10 entities** even carry the listener, and for those it's still write-only.
  - **Consequence:** tenant isolation rests **entirely** on the application layer — the per-controller `RunAccessGuard`/`ProjectAccessGuard` + repository methods that explicitly filter by `orgId`/`userId`/`projectId`. There is **no ORM safety net**. A single controller method that forgets its access guard, or a repo finder that filters by the wrong column, is a direct cross-tenant data leak. This is exactly why `AccessGuardCoverageTest` (the ArchUnit pin, Tier 9) is load-bearing rather than belt-and-suspenders — it is *the* tenant boundary, not a backup to one. And it's why the [standards.md](standards.md) `orgId`-param leak + any guard gap are real exposures, not ORM-caught near-misses.
  - **Not necessarily wrong** — app-layer-only multi-tenancy is a legitimate (common) choice. The problem is the **naming**: `@EntityListeners(TenantInterceptor.class)` + a `tenantId` column strongly *imply* row-level isolation that does not exist, which can lull a future contributor into trusting it. Either add a Hibernate tenant `@Filter` enabled per-request from `TenantContext` (real defense-in-depth), or rename/document the interceptor as "tenant-stamp, not tenant-filter" so nobody assumes read protection.

## Other findings
- 🟢 **`TenantFilter` itself is well-hardened** (audit 2026-05-12 B#19/#20): validates `X-Tenant-Id` against `^[A-Za-z0-9_\-]{1,64}$` (refuses traversal / shell-metachar / oversized), **cross-checks the header against the authenticated principal's `orgId`** so a client can't spoof another tenant via the header (403 on mismatch), SUPER_ADMIN bypass for the operator dashboard, and always clears the ThreadLocal in `finally` (no cross-request leakage). Clean. The irony: this careful header→principal check protects a `TenantContext` that then isn't used to filter any read.
- 🟡 **`TenantContext.getTenantId()` silently falls back to `"default"`** for async/internal paths (no ThreadLocal set). Combined with `TenantInterceptor` treating `"default"` as "overwrite me", an entity persisted on an un-propagated async thread gets stamped `tenantId="default"` rather than the real tenant. The Micrometer `TenantContextThreadLocalAccessor` mitigates this *only* when the async work is wrapped with `ContextSnapshotFactory.captureAll().wrap(...)` (the CLAUDE.md-mandated pattern) — any virtual thread spawned without that wrap stamps `"default"`. Low blast radius today (the 10 listener entities are mostly request-thread writes), but a latent mislabeling.
