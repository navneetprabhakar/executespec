## Findings

### 🔴 / 🟡 Real issues
- 🔴 **`GET /api/auth/generate?password=…` is a PUBLIC, unauthenticated bcrypt oracle.** `AuthController:666` (`@GetMapping("generate")`) bcrypt(12)-hashes an arbitrary query-param and returns it. It is NOT in SecurityConfig's authenticated allowlist (`/api/auth/me`, `/settings/**`, `change-password`) so it falls through to `.requestMatchers("/api/auth/**").permitAll()` — **reachable with no auth** (grep-confirmed). Two harms: (1) **CPU-amplification DoS** — bcrypt-12 is deliberately ~250 ms/call; trivially spammed to saturate CPU; (2) password-in-querystring → access logs / proxy logs. It's a leftover dev utility. **Delete it or SUPER_ADMIN-gate it.** Highest-priority finding in this package.
- 🟡 **SSRF in integration-credential validation.** `AuthController.validateJira` / `validateConfluence` (and the GitHub PAT validate, and the settings-save preflight) issue a server-side `GET` to a **user-supplied `baseUrl`** via `validateExternalConnection`. An authenticated user can point `baseUrl` at internal addresses (`169.254.169.254`, `localhost`, internal services) and use the returned status-code as an oracle (blind-ish SSRF / internal port scan / cloud-metadata probe). Authenticated + status-code-only limits it, but it's a real SSRF. Add an egress allowlist / block private + link-local ranges before the fetch.
- 🟡 **Refresh-token cookie is `setSecure(false)` hardcoded** (`AuthController.setRefreshCookie:660`) with an un-actioned `// set true in production (HTTPS)` comment. HttpOnly is set + path-scoped to `/api/auth`, but without `Secure` the refresh cookie can ride a downgraded HTTP request. Cloudflare HTTPS-only mitigates in practice; still a latent gap (and `SameSite` is not set explicitly). Drive it from a prod profile/property.
- 🟡 **`forgotPassword` emails a temp PLAINTEXT password** rather than a tokened reset link (`AuthService.forgotPassword`) — passwords in email get logged/cached/forwarded. `mustChangePassword` forces a change at next login (mitigates), and the separate token-based `resetPassword(token)` exists — but no code path here *issues* a `PASSWORD_RESET` token, so the safer tokened flow appears to have no issuer (possible dead path; verify the controller wiring). Prefer the reset-link flow.
- 🟡 **OAuth auto-links to any existing email account.** `findOrCreateFromOAuth` step 2 links the OAuth identity to an existing `AppUser` with the same email **"regardless of current provider"**, sets `emailVerified=true` + `status=ACTIVE`, with no explicit account-linking confirmation. Safe *because* Google/GitHub verify email ownership — but it's an account-takeover vector if any future provider asserts an unverified email, and an email/password account silently becomes OAuth-linked. Add a confirmation step or restrict to providers with verified-email guarantees.

### 🟢 Strong / correct
- 🟢 **Auth primitives are solid.** bcrypt(12) password hashing; strong password policy (10–128 chars, upper/lower/digit/special, no whitespace); `JwtSecretValidator` fail-fast on short/placeholder secret (≥32 chars, prod profile); JSON 401 entry point (fixed the Finding-2 302→HTML-that-clients-read-as-ok); STATELESS session repo (fixed the Finding-8 JSESSIONID leak); login distinguishes unverified/suspended/bad-creds; anti-enumeration on forgot/resend.
- 🟢 **Token lifecycle is careful.** Refresh tokens carry a `jti` + are revocable via a **blocklist** (`RefreshTokenBlocklistRepository`); `/refresh` **rotates** (blocklists the old jti, issues new); global **force-logout epoch** + **per-user `token_invalidated_at`** both enforced in `JwtUtil.isTokenValid`; SSE uses a **5-min run-scoped token** (`scope=sse`+`runId`) instead of the full JWT.
- 🟢 **PAT design is correct.** `es_pat_` prefix routes without a DB hit; 32-byte `SecureRandom`; **SHA-256 hash stored** (correctly justified — a 256-bit random secret doesn't need bcrypt, and a salted hash would break the indexed lookup); `lastUsedAt` write throttled to ≤1/5 min to keep auth off the write path; revocation via query filter; expiry enforced; resolves to the **same `AppUserDetails`** as a JWT.
- 🟢 **`RunAccessGuard` + `RunVisibilitySpec` are the consistent app-layer run boundary** (the real tenant enforcement, given [tenant.md](tenant.md)'s no-ORM-filter finding): SUPER_ADMIN all / ORG_ADMIN+BILLING_ADMIN+DEVELOPER same-org / FREE own-only; `requireRunWriteAccess` is stricter (owner or ORG_ADMIN, B#18). Single-run guard and list-Specification mirror each other.
- 🟢 **`TierEnforcementService` quota is TOCTOU-safe** — `assertAndIncrementRunCount` uses `findByIdForUpdate` pessimistic locking in one TX (no concurrent-submit double-pass), billing-cycle-aware reset evaluated in **IST** (matches the 00:00-IST contract), complexity gating (HIGH-majority plans blocked for FREE/non-BYOK), project/repo caps. `SuperAdminController` is `@PreAuthorize("hasRole('SUPER_ADMIN')")` (defense-in-depth over the URL rule) and **audits every mutation** (force-fail needs ≥10-char reason).

### 🟡 / 📝 Notes
- 🟡 **Per-request uncached identity load.** `JwtAuthenticationFilter` → `UserDetailsServiceImpl.loadUserById` runs **2 DB queries (user + orgMember) on every authenticated request** — no cache. Ensures fresh role/status but is a per-request cost on every `/api/**` call. Candidate for a short-TTL cache.
- 🟡 **`?token=` query-param auth is accepted globally**, not just on SSE. `extractBearerToken` falls back to `request.getParameter("token")` for *every* request, so a full access JWT works in any URL (→ logs/history/referrer leakage). The intent (per comment) was SSE-only (EventSource can't set headers); scope it to the SSE routes + prefer the 5-min scoped token.
- 📝 **JWT access-token TTL drift:** `JwtUtil` defaults `app.jwt.access-token-expiry-minutes:15`, but root CLAUDE.md says "access 1h". Whichever `application.yml` sets wins; the doc/code defaults disagree.
- 📝 **`FALLBACK_FREE=5` is stale** vs the V200 bump to 15 runs/month (CLAUDE.md). Only fires if the `tier_config.FREE` row is missing, so latent; the in-code comment even says "free tier will always remain 5", contradicting the shipped 15.
- 📝 **PATs are `scopes="full"` only** — every PAT is full account authority; no granular/read-only scopes yet.
- 🟢 **CORRECTION — most integration creds ARE encrypted at rest** (revises an earlier read of the controller setters). `AppUser` + `Org` apply `@Convert(crypto/EncryptedValueConverter)` to `bitbucketAppPassword`, `openAiApiKey`/`anthropicApiKey`/`geminiApiKey`, `openRouterApiKey` (org), `jiraApiToken`, `confluenceApiToken` → AES-256-GCM at the JPA layer (key from GCP Secret Manager; see [crypto.md](crypto.md)). The controller setters handle plaintext but the column is encrypted on write. **Two real caveats remain:** (a) **`github_pat` is the deliberate plaintext outlier** — `AppUser.github_pat` carries no converter (comment: "Stored as plaintext"), and the per-run `pipeline_run.github_pat` + `bitbucket_app_password` are plaintext too ([state.md](state.md)); (b) the converter **silently degrades to plaintext passthrough** when no key loads and `executespec.crypto.require-encryption=false` (the default) — see [crypto.md](crypto.md). `security/KeyEncryptor` is a *separate* primitive (Redis BYOK, JWT-secret-derived) — not the one guarding these columns; I conflated them earlier.
- 🟢 **Input-validation hardening is thorough across the DTOs** — `RegisterRequest` tightens `@Email` with an RFC-5321-lite `@Pattern` (closes the quoted-local-part SQLi vector, Finding 18); `CreateProjectRequest`/`RegisterRequest` reject `<>` in names (XSS defense-in-depth, Finding 6); `CreatePat`/`Login`/`Invite` carry `@NotBlank`/`@Email`/`@Size`. All secret-bearing DTOs (`UserDto`/`OrgDto`/`PatDto`) expose has-flags only, never raw secrets.
- 📝 **`OrgController.cancelInvitation` (DELETE `/me/invitations/{id}`) is a broken no-op** — it looks up the invite via `listByOrg("").stream().filter(...).findFirst()` but never deletes/expires it, then returns 204. Dead handler.
- 📝 **OAuth callback delivers access AND refresh token via URL query params** (`OAuthSuccessHandler` → `/auth/callback?token=…&refresh=…`) — the password-login path uses an HttpOnly cookie for the refresh token; the OAuth path is weaker/inconsistent (refresh-token-in-URL → logs/history). `OAuthUserMapper` does correctly filter to verified GitHub emails, mitigating the auto-link concern above.
- 🟡 **ActivityAudit hash-chain integrity is single-node only** — `ActivityAuditService.record` is JVM-`synchronized`; the chain (`prev_hash`/`row_hash`/`chain_seq`) would race under multi-node writes (documented; needs a Postgres advisory lock before horizontal scale — fine on today's single GCE VM).
