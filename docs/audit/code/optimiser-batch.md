# Audit: `optimiser/` + `batch/` — self-improving prompts (dev-only) + batch execution (unbuilt scaffold)

Status: **DONE** · Updated 2026-05-29 · 13 files / ~850 lines · all read in full

## What it does
- **`optimiser/`** (5) — a closed-loop "self-improving prompts" system. After a completed run, `PromptOptimiserAgent.runIfDue` (virtual thread) fires every `run-interval=10` completed runs OR when the trailing-20 failure rate ≥ `0.20`. `PromptPatternAnalyser` mines recent runs for failure patterns (LLM loops, file-lock/boundary violations, planner over-decomposition, reviewer false-approvals) → `PromptOptimiserAgent` asks an LLM for a *surgical* prompt edit → writes the updated prompt file + a `PromptAuditEntry` (versioned, with auto-rollback-if-degraded). **Default ON** (`agent.optimiser.enabled: true`).
- **`batch/`** (8) — V2 provider-batch execution (Anthropic/OpenAI/Gemini batch APIs) for `executionMode=BATCH`. **Entirely P1 scaffolding** behind `harness.v2.batch_enabled`.

## Findings — two more dormant subsystems; the optimiser is the more interesting one.

### 🟡 `batch/` is unbuilt scaffolding that throws (no behaviour to assess yet)
Every entry point is a stub: `BatchCoordinator.submit` → `throw UnsupportedOperationException("not yet implemented … P2")`; `BatchResumeService.resume` → same; `BatchPollService.pollInFlightJobs` → `@Scheduled(30s)` + ShedLock but body is `log.debug("no-op scaffold")`. `BatchClientRouter` is wired to collect `List<BatchClient>` beans but **there are zero `BatchClient` implementations** (only the interface) — `forProvider` always throws. Flag-gated default OFF; CLAUDE.md "Current state" already lists batch as "not started". So this is honest, loud scaffolding (it throws rather than silently mis-behaving) — nothing to fix, but ~290 LOC of dead weight until P2. (Joins the dormant-subsystem list: [contracts.md], [standards.md], [arch.md] InvariantChecker, [chat-specchat-folder.md] spec-chat loop.)

### 🟡 `optimiser/` — a runtime-prompt-mutation loop that is effective ONLY in a dev checkout, inert (but not free) on a prod JAR
The design is genuinely clever (mine failures → surgical LLM prompt edit → versioned audit → auto-rollback on degradation), and the scariest foot-guns are already defanged:
- 🟢 **Auto-commit was REMOVED** (audit F #44): the agent used to run `git add src/main/resources/prompts && git commit` on the developer's working tree from a Spring scheduled task — co-opting in-flight edits. Now it only writes files; `commitToMain` is `@Deprecated(forRemoval=true)` + no-op. Good catch, correctly neutered.
- 🟢 **Non-tool agent → `FallbackLlmRouter` is the *sanctioned* exception** (CLAUDE.md: legacy router survives for non-tool agents). Tokens are attributed to the triggering run via `stateStore.addTokensToRun`, so its spend isn't invisible.
- 🟡 **But it writes to a RELATIVE source path** — `Path.of("src/main/resources/prompts", promptFile)` ([PromptOptimiserAgent.java:243](../../../src/main/java/com/navneet/executespec/optimiser/PromptOptimiserAgent.java)). On the prod GCE VM the app is a JAR; prompts are served from the classpath *inside* the JAR, and the JVM working dir has no `src/main/resources/prompts/` tree. `optimisePrompt` guards with `Files.exists(promptPath)` **before** the LLM call, so on prod it short-circuits: pattern analysis runs (cheap DB reads), file-not-found, return — **no LLM spend, no write**. So the feature is **effective only in a dev checkout** and harmlessly (but pointlessly) ticks on prod. Net: a default-ON subsystem doing a non-trivial DB read-burst (`getRecentCompletedRuns(20)` × per-run `getTasksForRun`/`getReviewReportV2`/recovery lookups) every 10 completed runs to then no-op. Either point it at the classpath/an artefact store and make it real, or flip it OFF in prod config.
- 🟡 **Even in dev, the analyser still partly targets V1 legacy** — it emits worker patterns against `worker.txt` (V1 archive; V2 worker is `PromptAssembler`-composed from fragments, so the optimiser "only meaningfully targets the planner+reviewer", per its own comment). Planner→`outline-planner.md` + reviewer→`reviewer-general.md` ARE the live V2 files (corrected in audit F #42/#43), so those two edits would land; worker edits hit a legacy archive that doesn't drive the pipeline.
- 🟢 `PromptPatternAnalyser` reads V1 `StateStore` surfaces (`getReviewReportV2`, `RunRecoveryRepository`) — couples the optimiser to the dual-lifecycle V1 state ([state.md](state.md)); works, but inherits that coupling.

**Net optimiser read:** not dangerous (auto-commit gone, prod-inert), but it's a default-ON, dev-only-effective, partly-legacy-targeted loop. Decide: productionise (classpath-aware write target + human-review gate) or disable in prod.
