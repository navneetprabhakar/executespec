# Audit: `api/` — REST controllers (run lifecycle, preview, deploy, integrations, advice)

Status: **DONE** · Updated 2026-05-29 · 47 files / 5,570 lines · `RunController` read in full; rest scanned for gating + read where substantive

## What it does
The primary REST surface: `RunController` (1407 — the run lifecycle), `PreviewController`/`DeploymentController` (preview/deploy proxies), `SlackIntegrationController`, `IntegrationController`, conversation/feasibility/model/metrics/admin-analytics controllers, the global `ValidationAdvice`/`GlobalExceptionAdvice`, and the run DTOs/`RunMapper`.

## Findings — well-built + consistently access-guarded.
- 🟢 **`RunController` is the model for the access-guard discipline.** Submit (`POST /api/runs`): `inputSanitizer.scan(userRequest)` → `tierEnforcementService.assertAndIncrementRunCount` (atomic, TOCTOU-safe quota) → `submitRun` with `createdByUserId`/`orgId`/`projectId` stamped **before** the async thread. List: `RunVisibilitySpec` tenant filter (scope=mine → own; else org). **Every** single-run endpoint (get/approve/clarify/merge/retry/fork/pause/resume/push-github/sync/push-scm/project/delete/archive/soft-delete) calls `guard.requireRunAccess(runId, userDetails)`. The `/fork` + finding-sourced submits re-sanitize + re-check quota. This is exactly what `AccessGuardCoverageTest` pins.
- 🟢 **No gating gaps among the guard-less controllers** (grep-flagged but verified): `AdminAnalyticsController` is `/api/admin/analytics` (URL-gated SUPER_ADMIN by SecurityConfig); `UserRunsController` scopes via `guard.getOrgIdOrNull`; `EntitlementsController`/`ReferralController`/`SignupClaimController`/`AnonymousRunController`/`HealthController` are public/self-scoped by design; `ConversationController`/`IntegrationController`/`FeasibilityController` are principal-scoped under `/api/**` (auth-required). `IntegrationController.{source}/webhook` is signature-verified.
- 🟢 `ValidationAdvice` + `GlobalExceptionAdvice` emit a stable canonical error envelope (`{timestamp, status, error, message, …}`) — the shape the rate-limiter + frontend parser depend on.
- 🟡 **Run mutations are org-scoped, not owner-scoped.** The POST/DELETE run endpoints use `requireRunAccess` (admits any org member — DEVELOPER sees+acts on all org runs) rather than the stricter `requireRunWriteAccess` (owner/ORG_ADMIN only, which exists per B#18 but isn't used here). So any in-org developer can approve/retry/push/delete a teammate's run. Matches the documented "runs are shared org-wide" model + the coarse-in-org-write theme from [project.md](project.md)/[auth.md](auth.md) — intentional, but worth confirming against least-privilege intent (esp. for `push-github`/`delete`).
