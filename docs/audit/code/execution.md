## What it is
A **third orchestration layer above the V2 pipeline.** An `ExecutionRun` (a "Launch") goes SETUP → ANALYSING → ARCH_REVIEW → PLANNING → (plan approve) → EXECUTING → COMPLETE/FAILED/ABORTED. It's the shared engine behind the Execution View **and** `readymade/` (templates) + `migration/` (recipes) — `ExecutionRun` carries `migration_recipe_id` / `readymade_solution_id` links. Tier+flag gated (`execution.view.enabled` + `TierConfig.isExecutionViewEnabled`).

**Mid-migration — two dispatch paths:**
- **V188 unified (default ON, `execution.unified-dispatch.enabled`):** `kickoffPlanning` → `dispatchUnified` submits **one** V2 run for the whole requirement (all repos), polls to AWAITING_APPROVAL, mirrors `pipeline_run.planJson` → `executionPlan`; user's V3 approve → `gateStore.tryClaimPlanGate` resumes V2 → polls to terminal → `mirrorV2Terminal`. V3 becomes a thin proxy over a single V2 run.
- **Legacy per-Solution (flag OFF / in-flight rows):** `ExecutionPlannerService` LLM-splits the requirement into per-repo `ExecutionSolution` rows; `executeApprovedPlan` dispatches them in dependency-layers (each Solution = a V2 run via `SolutionExecutionService`), then opens per-repo final PRs.

## Findings

### Efficiency / cost (the priority)
- 🔵 **Polling-thread-per-launch, up to 4h.** `dispatchUnified` + `pollAndMirrorV2` (and legacy `pollUntilTerminal`) are `@Async` methods that `Thread.sleep(5–10s)` loop on the DB until the V2 run terminates — **`UNIFIED_MAX_WAIT_MS = 4h`** ([ExecutionOrchestrator.java:84](../../../src/main/java/com/navneet/executespec/execution/service/ExecutionOrchestrator.java)). Every in-flight launch holds an async thread sleeping + re-querying `pipeline_run` every 5s for up to 4 hours. The platform **already has the event-driven alternative** — `IntegrationOutboundListener` mirrors run status by listening to `PipelineEvent.RunCompleted/Failed` ([integration.md](integration.md)) — so V3 could mirror via a listener instead of polling. Also fragile across restarts (the sleeping thread dies → handled by the boot-resume re-arm in `onApplicationReady`). Recommend: replace the poll loops with a `PipelineEvent` listener keyed by `pipelineRunId`.
- 🟢 **Smart retry-gating saves wasted spend (legacy path).** `SolutionExecutionService.onV2Partial` will NOT auto-retry when the V2 `statusReason` is `FINAL_BUILD_FAILED`/`TESTS_FAILED` **and** every worker task ended COMPLETE — because retrying re-runs a deterministic task and produces identical code ($0.10–0.30 wasted/retry, observed on exec 85778e63). It pauses for a user SKIP/RETRY/FIX decision. Plus a same-`statusReason`-twice short-circuit. Good cost discipline.
- 🟢 **`ExecutionCostAggregator` recompute-from-source** sums every linked `pipeline_run.actual_cost_usd` (all attempts, not just COMPLETE), replacing a per-Solution incrementer that under-reported **6.8×** ($0.81 vs $5.55). Idempotent + CAS-persisted. Strong cost-accuracy fix.

### Correctness / concurrency
- 🟡 **`ExecutionRun` is a JPA `@Version` concurrency footgun — band-aided everywhere with CAS.** Long `@Async` phases (planner LLM ~30s, the 4h poll loops) hold a stale in-memory `ExecutionRun` across concurrent writes (SSE-update path, abort callback, sibling crons), so the naive `save()` throws `ObjectOptimisticLockingFailureException` on an `@Async` thread with no `@RestControllerAdvice` to catch it → the row wedges in a non-terminal state. Fix shipped as `ExecutionRunCasUpdater` (refetch+mutate+save, 3 retries) wrapping **every** status write — the file is littered with "2026-04-26 hotfix" comments documenting the bug class. The wrapper works, but the root cause (one `@Version` row mutated from many concurrent async phases) remains; an event-driven, single-writer mirror (above) would also dissolve most of these races.
- 🟢 **`cancel`/abort caveat:** `abortExecution` → `cancelActiveV2Runs` calls `v2Orchestrator.cancel(...)`, which (per [integration.md](integration.md)) flips status but does **not** stop in-flight LLM work (worker has no interrupt) — so abort is prompt at the V3 level but the underlying V2 run keeps burning until its next cooperative checkpoint. Same token-leak root cause.
- 🟢 `mirrorV2Terminal` collapses V2 PARTIAL → V3 COMPLETE (documented: the PR is still raised; per-Solution skip/retry granularity is moot under unified dispatch). Propagates V2 `statusReason`/`failureReason` up so the dashboard shows a real reason.

### Tech-debt / drift
- 🟡 **Legacy `ExecutionPlannerService` uses the abandoned patterns.** It outputs **text-JSON** (not native tool calls — "migrating to a `submitExecutionPlan` native tool call is a follow-up"), runs on the **deprecated `FallbackLlmRouter`** (RL-2026-05-041 migration target), and resolves `modelResolver.resolve("PlannerAgent", …)` — **`PlannerAgent` was deleted** (CLAUDE.md says "agent name is now OutlinePlannerAgent; PlannerAgent was deleted"), so this is a stale agent name (same drift class as the `ReviewerAgentV2` refs in Tiers 2/3). Only runs when the unified flag is off — it's the deprecation target, so the drift is contained, but it's dead-path-bound.
- 🟡 **`ExecutionRun` is NOT `@EntityListeners(TenantInterceptor)`-scoped** (unlike the `state/` entities) — it relies on explicit `orgId`-equality checks in the controller. Functionally correct (every endpoint org-scopes), but it's a second, hand-rolled multi-tenancy enforcement path divergent from the interceptor model.

### Good
- 🟢 `ExecutionController` is consistently guarded: `requireFeatureEnabled` (flag + tier) + `requireRunAccess`/`requireProjectAccess` (org-scoped) on every endpoint; SSE via scoped token OR JWT; single-active-launch-per-project guard (409); early-plan-approve rejection (409).
- 🟢 The unified path is the right architectural direction — collapses the dual-orchestration into "one V2 run, reuse V2's planner/gate/multi-repo push."

### Legacy per-Solution path — half-implemented features (deprecation target)
The flag-off per-Solution path carries several scaffolded-not-finished features (consistent with it being retired by the unified path):
- 🟡 `ExecutionBranchService` **records git-tag marker names but never creates the tags** ("actual git ops deferred to follow-up") — so the advertised surgical-rollback-per-solution capability doesn't exist; only the marker strings are stored.
- 🟡 `CrossRepoContextService` implements only **layer 1 of 3** (interface contracts as free-form markdown from title+description+PR); diff-codemap + test-anchor layers "arrive when the diff inspector lands." The structured `InterfaceContract` record is defined but unused (the live path uses raw markdown).
- 🟡 `IncrementalCodeMapService` does a **full regen, not incremental** ("true diff-based refresh is a follow-up").
- 🟡 **`ExecutionSolutionRepo.repo_id` is `nullable=false`, but `ExecutionPlannerService.persistPlan` can build a mapping with `repoId=null`** when the LLM returns an unmatchable repo name (after the fuzzy-match fallback misses) → a constraint-violation on insert that aborts the legacy planning step. Latent (legacy path only).
- 🟡 `ExecutionTotalsBackfillJob` is a **3rd boot-time job** in the package (`@PostConstruct`; joins `ExecutionOrchestrator.onApplicationReady` resume + `AdminReconciliationService.onApplicationReady` sweep) and backfills from `solution.actualTokens` (the *under-reporting* source) rather than the newer source-of-truth `pipeline_run` recompute — so it can re-bless stale low totals on historical rows.

### Good (legacy path)
- 🟢 `SolutionDependencyResolver` — clean Kahn-style topological layering + cycle detection (pure logic, no DB/LLM). `AdminReconciliationService` — boot + 15-min `@SchedulerLock` orphan sweep, correctly excludes EXECUTING (resumed elsewhere). `ProjectLaunchController` access guards mirror `ExecutionController`. Repos use `@EntityGraph` to avoid N+1 on the launches list (with a documented MultipleBagFetchException Set/List tradeoff).
- 🟡 `ProjectLaunchController` doc says "ENTERPRISE or MAX tier" — **MAX was removed** (renamed TEAM, V165); stale tier ref. Its launches-list/overview/PR-rollup also do `findAll`-style scans (up to 500 `pipeline_run` rows merged in-memory, merge-then-paginate, N+1 on solutions in `overview`).
