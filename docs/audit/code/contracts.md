## What it does
The enterprise cross-repo contracts feature (plan E2.x). Auto-detects API contracts (OpenAPI/Proto/GraphQL/JSON-Schema/AsyncAPI) by filename+content sniff → versions them in `contract_registry`/`contract_version` (git-authoritative at `.executespec/contracts/produced/`) → lets a consumer repo *declare* it consumes a contract → detects drift between the snapshot and live source → at the **plan-approval gate**, classifies whether the plan's intended contract changes are BREAKING (deterministic CLIs: oasdiff/buf/graphql-inspector, plus a pure-Java JSON-Schema differ) and gates approval (typed "BREAKING" ack) **only when a breaking change hits a declared consumer**. `ContractInjectionService` feeds a `{{CONTRACTS}}` block into the planner.

## Headline: high-quality, well-architected — but gated OFF + one auto-detection wiring gap

### Live-wiring status (the thing that matters for prioritisation)
- 🔵 **The breaking-change gate + planner injection ARE wired into `RunOrchestrator`** — both `PlanBreakingChangeReport` and `ContractInjectionService` are referenced there, behind `featureFlagService.isEnabled("contracts.breaking-change.enabled")` ([RunOrchestrator.java:1550](../../../src/main/java/com/navneet/executespec/integration/RunOrchestrator.java)), default **OFF** (V213). `ContractInjectionService.compose` result lands in `PlannerRequest`'s `{{CONTRACTS}}`. So unlike the dead `validator/` island, this is *dormant-by-flag, not orphaned* — flip the flag and it activates. It's the `feature/enterprise-readiness-eval` track: built, integrated, unproven in prod.
- 🟡 **Auto-detection is NOT wired — contracts only populate via the manual `/rescan` button.** `ContractDetectionService.runForRepo` has **zero callers outside `ContractCoverageController.rescan`** (grep-confirmed). Yet `ContractCoverageController`'s own javadoc claims "detection runs asynchronously on the post-merge cascade" — that post-merge wiring **does not exist**. Consequence: unless a user manually clicks Rescan per repo, `contract_registry` stays empty → the breaking-change gate (even if flag-on) has nothing to classify against and the `{{CONTRACTS}}` block is empty. The feature's value proposition is silently inert until that auto-detect hook is added. This is the single most important finding for the package: the gate is wired but its *input* isn't auto-populated.

### Engineering quality (🟢 — genuinely strong)
- 🟢 **Clean strategy pattern, testable by design.** Both `FileBasedContractDetector` and `BreakingChangeClassifier` are Spring-auto-collected lists indexed by `type()` for O(1) dispatch; detection injects GitHub via `FileLister`/`ContentLoader` callbacks so the service has **no network dependency** and is unit-testable cold. Constructor injection throughout (no `@Autowired` fields — conforms to CLAUDE.md).
- 🟢 **Detectors content-sniff, not just filename-match** — `openapi.yaml` must actually contain `openapi:`/`swagger:`, `.schema.json` must contain `"$schema"`, `.proto` must contain `syntax`/`message`/`service`, GraphQL must contain `type Query`/`schema {`. Avoids registering unrelated YAML/JSON as contracts.
- 🟢 **Breaking-change classification is deterministic-first + degrades gracefully.** `JsonSchemaBreakingChangeClassifier` is pure-Java (no CLI) with precise JSON-pointer paths; OpenAPI/Proto/GraphQL wrap industry-standard CLIs (oasdiff/buf/graphql-inspector) and return `UNCLASSIFIED` (never throw) when the CLI isn't on PATH — so a missing CLI is a visible "install hint", not a crash. `CliBreakingChangeRunner` uses `ProcessBuilder(argv)` (no `/bin/sh` → no shell injection), bounded timeout with `destroyForcibly`, temp-file cleanup in `finally`. Correctly does NOT treat oasdiff/buf non-zero exit as failure (those tools exit non-zero *because* they found breaking changes).
- 🟢 **The gate is designed against warning-fatigue.** `PlanBreakingChangeReport` only raises `requiresTypedAck` when a change is (1) plan-intended AND (2) BREAKING AND (3) hits a *declared consumer in this project* — the ~10-50× friction collapse called out in the plan. Breaking-but-unconsumed changes are recorded as metadata, not gate friction. Smart.
- 🟢 **Cost-bounded planner injection.** `ContractInjectionService` inlines full bodies only ≤15 contracts (`contracts.injection.full-body-threshold`), else emits an INDEX_ONLY list. Tenant-gated controllers throughout (`ProjectAccessGuard.assertCanRead`/`assertCanWrite`); drift-dismiss requires a ≥10-char rationale (audit trail). Forward-compat String enums everywhere (`typeEnum()`/`resolvedActionEnum()` fall back, never crash on an unknown value a newer node wrote).
- 🟢 `ContractCoverageController` honestly surfaces a hardcoded **known-gaps** list (gRPC-in-code, runtime-served OpenAPI, external schema registries, monorepo package scoping) so the customer sees what *isn't* auto-detected rather than silently missing it.

### Gaps / deferrals (📝)
- 🟡 **INDEX_ONLY mode references a `getContract` tool that isn't registered.** When a project has >15 contracts, `ContractInjectionService.composeIndexOnly` instructs the planner to "use the getContract(id, version) tool to fetch bodies on demand" — but the code comment admits "tool registration deferred to a follow-up". So a >15-contract project would tell the planner to call a tool that doesn't exist. Only bites large-contract projects (rare), and the feature is flag-off, so latent.
- 📝 `ContractCoverageController.detectorNameFor` maps `EVENT_SCHEMA → "EventSchemaDetector"`, but no such detector exists (only 5 detectors: OpenAPI/Proto/GraphQL/JSON-Schema/AsyncAPI). The GET coverage panel will list "EventSchemaDetector — SCANNED, 0 found" for a detector that never runs. Cosmetic.
- 📝 Several explicit `§13` deferrals acknowledged in-code: LLM verifier for ambiguous contract-repo classification, cross-repo producer matching, multi-file `$ref` OpenAPI bundling, GCS `contentPointer` path for >256KB contracts (column exists, writer always uses `inlineContent` today). All honest, all logged.
- 🟢 No security or correctness defects found. No stale-OPENAI default (this package does no direct LLM calls — classification is CLI/structural, not LLM).
