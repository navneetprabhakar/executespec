## What it does
Two related subsystems: **(1) Project memory** — `RunLedgerAgent` writes a compressed LIGHTWEIGHT-LLM digest of every completed project-scoped run into `project_run_ledger` (idempotent by runId); `MemoryCompactionService` rewrites a versioned `project_memory_snapshot` every 10 runs (from R20); `ProjectMemoryProvider.buildPlannerContext` renders `snapshot + last-10-uncompacted` into the planner's `{{PROJECT_MEMORY}}`. **(2) Project chat** — `ProjectChatService` is the tool-enabled copilot over project context (memory + arch doc + RAG), running its own manual tool loop; `ProjectChatTools` exposes 13 project-scoped tools. ENTERPRISE/TEAM premium, BYOK ("users bring their own tokens via project provider").

## Findings — well-built; the issues are consistency/pattern-drift, not correctness.

### Security / tenancy
- 🟢 `ProjectChatTools` is **fail-safe by construction** — every tool returns a JSON envelope (`{"ok":true|false}`) and **never throws out of `call()`** (a throw would surface as a 500 and abort the whole chat turn); the `SimpleToolCallback` adapter centralises JSON-parse + exception → error-envelope. Tools are correctly scoped to **project-level reads + gated writes** only (no run mutations, no settings access — per the user's explicit 2026-05-02 direction). The one paid action, `run_code_review`, enforces `assertTierAndQuota` before submitting. The tools trust `ctx.projectId()` — which is sound because the controller gates access before binding.
- 🟡 **Two different tenancy models inside one package.** `ProjectMemoryController` uses `ProjectAccessGuard` (admits cross-org `project_member` collaborators per V175); `ProjectChatController.requireChatAccess` uses a **raw `project.orgId == user.orgId` match** + tier flag, which *excludes* invited cross-org collaborators from chat entirely. So a V175 external collaborator can read project memory but not the chat over it. Chat is stricter than the rest of the project surface — probably acceptable for a premium feature, but it's an inconsistent access model that will surprise (and the raw match also skips the SUPER_ADMIN bypass the guard provides). Worth converging on `ProjectAccessGuard`.
- 🟢 `ProjectMemoryController.compact` correctly hardened to `assertCanWrite` (audit 2026-05-12 B#11 — it triggers a paid LLM call + irreversible ledger merge; was `assertCanRead`, so a `PROJECT_VIEWER` could drain the budget). Good least-privilege fix.

### Pattern drift (📝 — against documented CLAUDE.md rules)
- 📝 **`RunLedgerAgent` + `MemoryCompactionService` load prompts via `new ClassPathResource("prompts/*.txt").getContentAsString()` directly** — violates the CLAUDE.md MUST: *"Never use `Resource.getContentAsString()` directly in agents; assemble via `PromptAssembler.assemble`."* They do manual `{{VAR}}` string-replace and get no `{{include:fragment}}` support. Not a bug (these are simple .txt templates), but it's the documented anti-pattern, live in two agents.
- 📝 **Stale-OPENAI default, 3 occurrences in this package.** `MemoryCompactionService.callLightweightLlm` hardcodes `LlmProvider.OPENAI` (explicit + commented "provider-agnostic at this layer"); `ProjectChatService.compactHistory` + `compileToSpec` both default to `OPENAI` when `project.aiProvider` is null — *while `ProjectChatService.send` in the same file defaults to `ANTHROPIC`*. So one file picks two different default providers depending on the method. CLAUDE.md says Anthropic is the platform default. Latent (project usually has a provider set), same theme as [integration.md](integration.md)/[state.md](state.md)/[codeintel.md](codeintel.md).

### Cost / correctness
- 🟢 **Memory generation can never break a run** — `RunLedgerAgent` + `MemoryCompactionService` wrap everything in try/catch and log-and-continue; idempotent (`existsByRunId`), compaction is an atomic `@Transactional` swap (delete-range + insert-summary + mark-tail) so a mid-write crash can't leave a half-compacted ledger. `ProjectChatService.compactHistory` likewise does the delete+insert inside one tx and has a deterministic first/last-user-message fallback when the LLM call dies. Solid resilience hygiene.
- 🟡 **Project-chat dollar spend is uncosted.** `ProjectChatService.send` records `tokensIn/tokensOut` on the `ProjectChatMessage` row but routes through `LlmRouter` without `RunCostTracker` attribution, and the [project.md](project.md) dashboard `CostBreakdown` does NOT include a project-chat line — so chat LLM dollars are invisible to every cost rollup. Mitigated by BYOK (premium tiers use their own provider keys), so it's the user's spend, not the platform's; still, no dollar visibility anywhere. Tokens-on-row is partial telemetry. (Same uncosted-spend family as [codeintel.md](codeintel.md) `RunCodeMapService`, [project.md](project.md) `EmbeddingService`, [assessment.md](assessment.md) `FeatureAssessmentService`.)
- 🟢 `ProjectChatService` manual tool loop (`MAX_TOOL_ROUNDS=6`) correctly mirrors `WorkerAgent` because `LlmRouter` hardcodes `internalToolExecutionEnabled(false)` — without it the model's `tool_use` turn would be saved as just the pre-call narration and the follow-through lost. History window 20; RAG query = most-recent user turn. Sensible.
- 📝 `ProjectMemoryProvider.MAX_MEMORY_TOKENS = 12000` is a **stat, not an enforced cap** — `buildPlannerContext` always emits `snapshot + last-10-entries` regardless of size (each entry capped 2 KB by `RunLedgerAgent.LEDGER_CHAR_CAP`, snapshot uncapped). In practice bounded (~10×2KB + one snapshot), but the "token budget" is advisory only.
- 📝 `ProjectChatTools.requireProject` is `@SuppressWarnings("unused")` "kept for parity" — acknowledged dead helper.
