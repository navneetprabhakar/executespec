## Findings (payment-security + quota)

### 🟢 Payment-webhook security is correct (matches the CLAUDE.md claim)
- 🟢 **Both gateways verify signatures fail-closed before touching state.** Razorpay: `BillingWebhookController` rejects missing `X-Razorpay-Signature` (401), and `WebhookSignatureVerifier.verifyWebhookSignature` does `HMAC-SHA256(rawPayload, webhookSecret)` compared with **`MessageDigest.isEqual` (constant-time — no timing leak)**. Stripe: `Stripe-Signature` required, validated via the Stripe SDK's `Webhook.constructEvent` (rejects on `SignatureVerificationException`); rejects outright when the webhook secret isn't configured. Razorpay payment/order signatures use the correct Razorpay payloads (`payment_id|subscription_id`, `order_id|payment_id`) with `key_secret`.
- 🟢 **Idempotent + audited.** Webhook events deduped by `(gateway, eventId)` in `webhook_event_log` (duplicate → marked IGNORED); raw payload + SHA-256 hash stored for replay/audit; both endpoints return 200 *after* the signature check so the gateway doesn't retry-storm on a downstream processing error (the raw payload is persisted for reprocessing). Stripe checkout/subscription/seat-quantity/cancel-at-period-end all go through the SDK with proration handled correctly.
- 📝 Minor asymmetry: only the Stripe path calls `logWebhookEvent` in the controller (Razorpay's dedup/audit must live inside `processRazorpayWebhook` — verify when reading `BillingService`). Stripe's `eventId` is recovered by string-replacing the `WebhookResult.message()` ("Event validated: …") — fragile but functional. The payment-signature-mismatch log prints 8-char prefixes of expected/actual HMAC — negligible exposure.

### 🟡 Quota-system multiplicity (the architecture finding — reinforces [entitlements.md](entitlements.md))
- 🟡 **`UsageTrackingService` is a THIRD parallel run-counting system.** It maintains `billing_usage` metric rows (per user/org/metric/calendar-month, IST period boundaries) with `assertWithinLimits`/`increment`/`decrement`. This is distinct from **(1)** `auth/TierEnforcementService` (`app_user.personal_run_count` + `org.monthly_run_count`, pessimistic-locked) and **(2)** `credit/LifetimeCreditService` (v3 `lifetime_run_credit_balance`). So there are at least **three** independent "can this user run / how many runs left" ledgers, plus the cost-credit charge at plan approval. `assertWithinLimits` itself patches over the divergence for the RUNS metric — it deliberately reads `tier_config` via `EntitlementResolver.resolveTier` (higher-of org/user) instead of `billing_plan_limit`, with an in-code comment that the legacy `billing_plan` path "produced false positives when org.tier had been promoted past billing_subscription.billing_plan_id." That comment is direct evidence of the sources-disagree bug class. **Which ledger is authoritative for run-submit is genuinely hard to reason about** — this is the single biggest billing-area tech-debt and a correctness risk (double-charge / double-count / quota-bypass depending on which path a surface calls). Worth an explicit consolidation decision.

### 🟢 The rest is well-built (read in full)
- 🟢 **`BillingService` (1441) is comprehensive + secure**: lifecycle-gated subscribe (rejects HIDDEN/SUNSETTING plans), upgrade/downgrade by tier-rank, **anti-gaming prorated refund** (`min(runs-based, time-based)`), gateway-routed (Stripe checkout / Razorpay), idempotent signature-verified webhooks for *both* gateways with full sub-lifecycle handling, and the tier-bridge writes **both `user.tier` AND `org.tier`** (BUG-009 fix — they had diverged). `verifyAndActivate` checks the subscription **belongs to the authenticated user** (IDOR guard). 📝 Stripe prorated-upgrade refunds are NOT implemented (Razorpay only — "Stripe via dashboard/future").
- 🟢 **Invoicing is GST-compliant + correct**: `InvoiceService` does FY-numbered invoices (`ES-YYYY-NNNN`, pessimistic-locked sequence), CGST/SGST/IGST via `GstCalculationService` (18%, SAC 998314, reverse-charge/export), double-entry `AccountingService` (REVENUE/GST_OUTPUT/AR/BANK/REFUND), credit notes, dedup by `gatewayPaymentId`. `RunTopupService` FIFO bonus consumption is atomic (`decrementRemaining` JPQL). `FounderPricingService` allocation is concurrency-safe.
- 🟢 **Controllers fully gated**: `InvoiceController` user endpoints enforce `requireOwnership(principal, invoice)` (no invoice-by-UUID IDOR); admin endpoints `requireInvoiceAdmin`/`requireSuperAdmin`. `AccountingController` (`/api/accounting`, not `/api/admin`) is method-gated via `TierPermissionService` to FINANCE/SUPER_ADMIN (`canViewAccounting`/`canExportGstr`). `PaymentAuditController` `@PreAuthorize` SUPER_ADMIN / BILLING_ADMIN.
- 📝 **In-memory `findAll()` for accounting reports**: `AccountingService.getGstSummary`/`exportGstr1` + `AnalyticsService.getBillingOverview` load full tables and filter in heap ("For now, filter in memory") — admin-frequency, so acceptable now (same theme as [state.md](state.md) but low blast radius). `AnalyticsService` has a `TODO` to wire `model_task_metric` for accurate per-model cost breakdown.
