# UI bugs observed on dev — fix AFTER audit

> Reported by founder 2026-05-29 from `dev.executespec.ai/result/71f8f3ac-…` (a terminal TodoApp run, IDE chrome). **Do not fix during the line-by-line audit** — these are queued for the post-audit action pass. Root-cause diagnoses below are being confirmed against the `ide/` components as the audit reaches them.

| # | Bug | Status | Likely root cause (to confirm in code) |
|---|-----|--------|----------------------------------------|
| 1 | **No Approve button on `/result/{id}`** | ✅ confirmed in code | `IdeRunResult.tsx` L407-419 computes `terminal`/`canPause`/`canResume` but **no `canApprove`** — `AWAITING_APPROVAL` is only treated as *pausable*, never offers an approve CTA. The gate Approve lives solely on `/plan/:runId` (`IdePlan`) + the status-bar `PlanGateIndicator`. So a run at `AWAITING_APPROVAL` opened at `/result/:id` shows Pause but no Approve. **Fix:** when `status==='AWAITING_APPROVAL'`, `IdeRunResult` should redirect to `/plan/:id` or render the inline approve gate. |
| 2 | **No notification icon** | ✅ confirmed in code | `IdeWorkspace.tsx` (read in full): activity bar (Workspace/New-spec/All-runs/Projects/sidebar/Account) + status bar (Commands/theme/Try-Console) render **no bell**. The inbox exists — `/notifications` (`IdeSystem.IdeNotifications`) + `getUnreadCount`/`getNotifications` — reachable only by URL. (`IdeMore` has notification *preferences*, not the inbox.) **Fix:** add a bell (unread badge polling `getUnreadCount`) to `IdeWorkspace` + `ConsoleShell`. |
| 3 | **Two different views for runs** | ✅ confirmed (architectural) | Separate surfaces: `/live/:id` (`IdeSurfaces.IdeLive`, in-progress SSE console) vs `/result/:id` (`IdeRunResult`, terminal file-tree + 9 tabs). Same run "changes UI" when it finishes; plus the flag-gated Console vs IDE chrome. **Fix:** one adaptive run-detail surface (RL-2026-05-052 reframe direction) or a seamless live→result transition. |
| 4 | **Live log (Logs tab) dumps full raw JSON** | ✅ confirmed in code (exact) | `IdeRunResult.tsx` `logMessage()` L106-120 does `d.message ?? d.line ?? d.payload ?? …`; a `RUN_DETAIL` replay event's `payload` **is the entire run-detail JSON**, and the Logs `.map()` (L1017) renders **every** event with **no type filter**. The live path `hooks/useSse.ts` L92-102 early-`return`s on `RUN_DETAIL` (never logs it) — the persisted-replay renderer is missing that parity skip. **Fix:** in the Logs `.map()` (or `logMessage`), drop `RUN_DETAIL` + condense `TOKEN_USAGE` to a one-liner, mirroring the live console. Small, well-scoped. |

## Notes

- #3 is the larger UX item (run-detail unification) — aligns with the in-flight web-control-plane reframe (RL-2026-05-052).
