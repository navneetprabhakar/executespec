# ExecuteSpec Investor Outreach — Next-Phase Handoff

Status: internal scoping note. No investor claims, list building, contact, fundraising terms, or external commitments are authorized by this file.

## Proposed core narrative

ExecuteSpec's investor story has three layers that must remain distinct:

1. Present wedge: ExecuteSpec Core, a spec-to-reviewable-PR product with approval, execution, validation, and evidence.
2. Platform expansion: a software foundry spanning code generation, Data Pipeline generation, and Pilot/Virtual SRE for observability, alerting, issue formation, and reviewable remediation.
3. Research moat: an owned language-focused coding model plus a software-engineering world model.

The story is credible only if the present wedge proves demand and generates proprietary, permissioned learning loops. Ambition alone does not connect these layers.

## Pillar 1 — Software foundry

Current:

- code-generation/control-plane product exists;
- repository tools, execution, validation, project context, evidence, and PR delivery form reusable infrastructure.

Roadmap:

- Data Pipeline generation;
- Pilot/Virtual SRE integrating observability, alerts, incident evidence, and remediation into the PR workflow.

Investor framing hypothesis:

> Start with controlled software changes. Extend the same approval, execution, evidence, and remediation substrate into data workflows and production operations.

Hard question to answer:

> Why do these product lines belong in one company and one control plane rather than becoming three unrelated products?

Required evidence:

- shared primitives and data model;
- customer pull for adjacent workflows;
- sequencing and staffing plan;
- a narrow entry use case for Data Pipeline and SRE;
- explicit non-goals preventing product-line sprawl.

## Pillar 2 — Owned coding LLM

Desired language coverage:

- React and TypeScript/JavaScript;
- Java;
- Python;
- C++;
- Rust;
- Go;
- Kotlin and Android;
- Swift/iOS.

Adversarial boundary:

This list is not a narrow language-specific model strategy. It is a broad multilingual software model program covering several programming paradigms, build systems, runtime ecosystems, mobile platforms, and validation harnesses. It will be capital- and data-intensive.

Before investor outreach, define:

- whether the first model is trained from scratch, continued-pretrained, distilled, or fine-tuned;
- first language/ecosystem wedge;
- target parameter range and serving economics;
- task class: planning, patch generation, code review, test generation, tool use, or all of them;
- licensed and consented training-data strategy;
- repository/customer-data policy and opt-in boundaries;
- evaluation suites and independent holdouts;
- quality/cost/latency target versus third-party models;
- why an owned model is necessary rather than a routing/verification advantage.

Safer investor framing:

> ExecuteSpec intends to develop owned, task- and ecosystem-specialized coding models where proprietary evaluation and permissioned execution data show a clear quality or cost advantage. The first model and training route remain to be selected.

Do not yet claim an owned model, proprietary dataset, training advantage, or frontier parity.

## Pillar 3 — Software-engineering world model

Working definition needed:

> A model of repository state, intended change, dependencies, build/test behavior, tool actions, and likely downstream outcomes that can predict whether a proposed engineering action will satisfy the acceptance contract before or during execution.

This definition must be distinguished from:

- a code embedding/index;
- project memory or RAG;
- an LLM reviewer;
- a dependency graph;
- a verified-score formula;
- a generic coding model with a larger context window.

Candidate initial use cases:

- predict task decomposition risk;
- predict likely files and dependency surfaces;
- predict build/test failure before expensive execution;
- choose model, tools, and budgets per task;
- identify incomplete or false-done changes;
- estimate whether another agent/model attempt is rational;
- rank verification actions by expected information gain.

Required research proof:

- precise state/action/outcome representation;
- training labels and lawful data source;
- offline predictive task with a baseline;
- held-out evaluation preventing repository leakage;
- measurable lift to quality, cost, latency, or failure detection;
- ablation showing value beyond ordinary retrieval and reviewer models.

Safer investor framing:

> ExecuteSpec's long-term research thesis is to learn predictive models of software-engineering actions and outcomes from permissioned execution trajectories and objective build/test evidence. Today the product supplies the instrumentation and verification substrate; the world model itself is not yet a shipped or proven asset.

## Narrative order for investors

1. Pain: code generation is abundant; trustworthy delegation and software-change outcomes remain difficult.
2. Present product: controlled spec-to-PR execution with approval and evidence.
3. Traction: real repositories, accepted PRs, repeat use, paid accounts, and retention.
4. Insight: the execution system observes structured state/action/outcome trajectories.
5. Platform: the same foundry substrate expands into data workflows and SRE remediation.
6. Research moat: specialized coding models and a predictive engineering world model, gated by data rights and measurable lift.
7. Use of funds: milestones, team, compute, evaluation, security, and go-to-market.

Do not lead with the model or world model before demonstrating why ExecuteSpec can acquire differentiated data and why customers will permit its use.
