# ExecuteSpec — August 2026 GTM Validation Sprint

Status: internal operating brief; nothing in this file authorizes publication, outreach, advertising, repository access, or external commitments.

Prepared: 2026-07-24

## Executive verdict

The defensible August test is not whether the market wants a broad software foundry. It is whether a narrow group of engineering teams will delegate one bounded change to an existing repository, inspect the returned evidence, and then voluntarily bring a second task or pay.

The current product supports a credible workflow: requirement → plan and usage estimate → approval → repository execution → build/test/reviewer evidence → pull request. The repository does not currently prove that customers consistently save time, merge the output, repeat, or pay.

August should therefore optimize for:

1. qualified conversations with repository-owning buyers,
2. trials on real, non-critical repositories,
3. customer-accepted or merged output,
4. a second task within 14 days,
5. collected revenue.

Impressions, likes, followers, raw signups, internal run counts, and ExecuteSpec's own verified score are diagnostic only.

## Narrow ICP

Primary ICP:

- technical founder, CTO, engineering manager, or hands-on tech lead;
- B2B SaaS company with approximately 5–30 engineers;
- GitHub-based development;
- already uses Cursor, Copilot, Claude Code, or another coding agent;
- has an existing TypeScript/Node, Python, Java/Spring, Go, React, Kotlin, or mobile repository with a working build or objective checks;
- can authorize a bounded repository trial inside 14 days;
- experiences review capacity, incomplete maintenance work, or cross-file implementation as a bottleneck.

Best starting work:

- reproducible bug fixes;
- dependency or framework migrations;
- internal APIs with explicit acceptance criteria;
- test-backed refactors;
- CI, logging, validation, and other repetitive engineering-enablement work.

Exclude initially:

- buyers asking for an entire product from one prompt;
- regulated or procurement-heavy enterprises requiring SOC 2, SAML enforcement, regional hosting, or physical isolation;
- repositories without a reproducible build or acceptance contract;
- ambiguous product-design work, large rewrites, or production infrastructure mutations;
- prospects who will not allow a second task even if the first trial succeeds.

## Painful job and positioning hypothesis

Painful job:

> I can generate code quickly, but I still have to supervise the implementation, reconstruct what happened, run the validation, and decide whether the diff deserves review.

Positioning hypothesis:

> ExecuteSpec is for engineering teams that already generate code with AI but do not trust unstructured agent output. Delegate one bounded repository change, approve the plan and spend, and get back a PR with the validation trail attached.

Do not lead with multi-agent architecture, provider count, model research, the software-foundry roadmap, or a broad feature inventory in customer acquisition.

## Proof available now

Defensible product proof:

- the plan/approval/execution/reviewer/report/PR workflow exists;
- the approval gate exposes planned work and estimated usage before execution;
- runs retain task, tool, token, cost, build, test, reviewer, and evidence-ledger data;
- GitHub repository and PR paths exist;
- project context, multi-repository execution, BYOK, and model controls exist;
- current product media demonstrates UI surfaces using explicitly synthetic data;
- local source and contract tests provide engineering evidence.

Missing market proof:

- consented customer repository results;
- customer-measured time saved;
- merge rate;
- human correction required;
- repeat usage;
- paid conversion;
- publishable external benchmark evidence;
- production reliability across representative customer repositories.

The first valuable proof packet must contain:

1. original issue and acceptance criteria;
2. approved plan;
3. final diff and PR;
4. build and test evidence;
5. human review outcome;
6. corrections required;
7. merged/accepted/rejected decision;
8. second-task decision;
9. explicit permission for every item made public.

## Claims to avoid

Do not claim:

- “PRs your team actually merges”;
- guaranteed production-ready or mergeable code;
- universal success rates, model parity, or benchmark leadership;
- universal language/framework reliability;
- guaranteed cost savings or estimate accuracy;
- customer adoption inferred from platform aggregates;
- SOC 2 completion, enforced SAML, dedicated region, or physical tenant isolation;
- fully automated GDPR erasure;
- shipped Data Pipeline Builder, Pilot/Virtual SRE, owned coding LLM, or software-engineering world model;
- that the internal score independently proves correctness.

Safer language:

> ExecuteSpec returns a reviewable change with the build, test, reviewer, and usage evidence available for that run. Its internal score summarizes evidence; it is not a correctness or merge guarantee.

Primary CTA:

Cap delivery at two concurrent trials per week. Decide separately whether the first three are free, require a refundable deposit, or are paid.

## Funnel definitions

- Qualified conversation: ICP fit, a real repository, an identifiable bounded task, a decision-maker or direct user, and willingness to test inside 14 days.
- Trial: repository access completed and the plan approved. A signup is not a trial.
- Activated account: ExecuteSpec returns a PR or reviewable patch with evidence.
- Accepted output: the customer says the output deserves review/use or merges it. ExecuteSpec's own score does not count.
- Repeat account: starts a second real-repository task inside 14 days.
- Pilot: named owner, at least three planned tasks, and an explicit evaluation date.
- Paying customer: payment collected, not verbal intent or a promised procurement process.

## Stop/go scorecard

Minimum volume before interpreting the experiment:

- 50 researched ICP accounts;
- 40 personalized outbound messages;
- 10 warm-introduction requests;
- 8 discovery attempts;
- 4 real-repository trials attempted.

Strong go:

- at least two paying accounts;
- at least one is Team, BYOK, or a paid pilot rather than two low-intent Pro subscriptions;
- at least three activated real repositories;
- at least two repeat accounts;
- at least two customer-accepted or merged outputs.

Narrow continuation:

- one paying account plus two active pilots;
- repeat usage exists;
- at least one output is customer-accepted;
- buyers identify a common narrow use case.

Reposition message or ICP:

- qualified conversations occur but fewer than 25% start a trial;
- objections cluster around unclear use case, lack of urgency, or an unattractive offer.

Product-fix before more acquisition:

- at least half of started trials fail because of setup, repository compatibility, validation, PR creation, access, or trust gaps.

Stop:

- after minimum volume, zero paying accounts, fewer than two repeat accounts, and fewer than two customer-accepted outputs.

## Adversarial findings

### 1. The original “two paying customers” threshold was too easy to game

Two $20 Pro subscriptions do not validate a business customer or founder-assisted sales motion. The revised threshold requires at least one Team, BYOK, or paid-pilot account plus repository activation and repeat behavior.

### 2. “PR opened” is not value

The product can produce a PR and still create more review work than it removes. Capture correction time, acceptance, merge decision, and second-task intent.

### 3. Warm-network results can create a false positive

Friends and former colleagues may trial the product as a favor. Label every lead warm, referred, or cold. A strong go requires at least one activated account outside Forge's first-degree network or explicit evidence that the warm account would pay without the relationship.

### 4. Founder assistance can hide onboarding defects

Track every step Forge performs for the customer. If a trial succeeds only because Forge manually repairs setup, rewrites the specification, fixes repository state, or interprets evidence, mark it assisted and do not count it as self-serve activation.

### 5. Repository access is the largest conversion cliff

A generic “start free” CTA avoids the hard trust decision. The repository trial surfaces it immediately, which is useful. Measure access refusal separately from lack of product interest. Offer a customer-controlled sandbox or public repository where private access is blocked, but do not count that as equivalent proof.

### 6. The current website overstates the evidence

Phrases such as “actually merges,” “merge-able PR,” universal stack support, and library completion times are ahead of customer proof. Do not drive paid traffic until the website promise is reconciled with the August offer.

### 7. Region breadth can dilute learning

India, UK/Ireland, and Singapore are three distinct sales contexts. Use one message and one offer, record region, and do not add more regions until the first 25 researched accounts reveal signal.

### 8. Content can attract peers instead of buyers

Technical posts about models and architecture may generate developer engagement without repository trials. Every week must include at least one buyer-problem post and one direct repository-trial CTA. Track qualified conversations per post, not impressions.

### 9. The trial can become unpaid consulting

Bound scope to one issue, one repository unless multi-repo is essential, one run plus one bounded correction, and one review call. Anything beyond that is a paid pilot or a product defect to log.

### 10. August cannot validate the software-foundry thesis

Code generation is current product scope. Data Pipeline generation and Pilot/Virtual SRE are roadmap lines. An owned coding LLM and a software-engineering world model are research/capital theses. Customer messaging should not combine all four; investors may hear the ambition only when the present wedge, sequencing, data rights, capital requirement, and falsifiable milestones are clear.

## Week-one approved-draft content

### LinkedIn 1 — the review bottleneck

AI coding has made generating a diff cheap.

Reviewing an unfamiliar diff is still expensive.

The difficult questions have not changed:

- What exactly did the agent decide to change?
- Did it run the repository's real checks?
- Which failures are deterministic and which are model judgment?
- How much did the attempt cost?
- Is the result worth a human review?

I have been building ExecuteSpec around that gap.

You give it a bounded repository change. It creates a plan and usage estimate. You approve both. It executes the work and returns the PR with build, test, reviewer, and model-usage evidence attached.

That evidence is not a merge guarantee. It is a way to make the handoff inspectable.

For August, I am looking for a small number of engineering teams willing to test this on one real, non-critical issue.

If you have a task that is tedious to implement but expensive to review, send it to me.

### LinkedIn 2 — score honesty

A 92/100 score from an AI system should not make anyone trust a pull request.

The useful question is: what produced the 92?

In ExecuteSpec, the headline score is only a summary. The report keeps the underlying signals separate:

- Was code actually changed?
- Did the build pass?
- Which tests ran, and how many passed?
- What did the reviewer find?
- Are there unresolved critical issues?
- Which parts are deterministic and which rely on model judgment?

If those signals are missing, the score has less authority. If the build or concrete tests fail, the headline is capped.

This still does not prove correctness. It does make it harder for a coding agent to hide behind a confident completion message.

I am testing whether that distinction matters to teams evaluating AI-authored pull requests. If you own code review quality for a small engineering team, I would like to compare notes.

### X drafts

1. AI made generating diffs cheap. Reviewing unfamiliar diffs is still expensive. The interesting problem is not “can the model write code?” It is “can it return a bounded change with enough evidence that a human knows whether review is worth starting?”

2. An AI-generated “92/100” means nothing by itself. Show the inputs: actual diff, build result, tests executed, reviewer findings, unresolved criticals, and provider usage. The score should summarize evidence—not replace it.

3. I am looking for a few non-US engineering teams to test ExecuteSpec on one real, bounded GitHub issue. Plan and usage estimate first. Human approval. Then implementation, checks, and a PR with the evidence attached. Nothing is published without explicit consent.
