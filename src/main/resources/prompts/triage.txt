## SINGLE_SHOT criteria (ALL must be true):
- The request involves creating or modifying 1-5 files total
- It is a single, self-contained feature, fix, page, or change
- Does NOT involve both a backend AND a frontend (see MULTI_TASK rule below)
- Can be completed by one developer in one sitting
- Examples: "Add a /health endpoint", "Fix the NPE in UserService", "Create a landing page", "Build a portfolio website", "Create a static HTML site with navbar, hero, contact form", "Add form validation to the signup page"

## Static websites are SINGLE_SHOT:
- Static websites (HTML + CSS + JS) with no backend server — regardless of how many sections or features
- Single-page applications or landing pages, even with multiple UI sections
- A single API endpoint, service, or component addition
- Examples: "Create a lawyer/restaurant/business website", "Build a responsive landing page"

## Console apps and algorithm tasks are ALWAYS SINGLE_SHOT regardless of language:
- Any request that asks to print output, return a value, or implement an algorithm with NO HTTP server / NO web framework
- Fibonacci, sorting, data structures, math problems, CLI scripts, programs that run and exit
- The presence of a build file (pom.xml, Cargo.toml, go.mod) does NOT make a console app MULTI_TASK
- Keywords that force SINGLE_SHOT: "fibonacci", "factorial", "sorting", "algorithm", "CLI", "command line", "console app", "print output", "no HTTP", "no server", "no web", "script that", "function that returns"
- Examples: "Write a fibonacci program in Java", "Implement quicksort in Rust", "Build a CLI calculator", "Write a script that reads CSV and prints stats"

## MULTI_TASK criteria (ANY of these):
- The request involves BOTH a backend (Express, FastAPI, Spring Boot, etc.) AND a frontend (React, Vue, etc.)
- Multiple backend services, APIs, or data models that need separate implementation phases
- Requires coordinated changes across different technology layers (e.g., DB schema + API + frontend + auth)
- The request mentions a database, API server, or backend framework alongside UI/frontend work
- Examples: "Build a todo app with Express and React", "Create a blog platform with CMS, comments, and RSS", "Build a user management system with auth, roles, and admin panel", "Add admin dashboard with analytics and reporting", "Implement shopping cart with checkout, payments, and inventory", "Build a full-stack CRUD app", "Create a REST API with a React frontend"

## CRITICAL RULE — Full-Stack Detection:
If the request mentions ANY of these patterns, it is ALWAYS MULTI_TASK:
- "full-stack", "fullstack", "MERN", "MEAN", "backend + frontend"
- A backend framework (Express, Fastify, Flask, FastAPI, Django, Spring Boot, Rails, NestJS, Hono) AND a frontend framework/library (React, Vue, Angular, Svelte, Next.js)
- "API" or "REST" or "server" combined with "UI" or "frontend" or "dashboard" or "page"
- "todo app", "task manager", "blog", "e-commerce", "chat app" — these ALWAYS need backend + frontend separation
- Database mentions (MongoDB, PostgreSQL, MySQL, SQLite, Prisma, Mongoose) alongside frontend work

## MEDIUM criteria (simplified planner — 2-4 tasks max):
- The request clearly spans 2-3 related files in ONE layer (e.g., add a service method + controller endpoint)
- Not as broad as a full feature, but too coupled for a single worker to do atomically
- Examples: "Add search to the existing product API", "Add login endpoint to existing Spring Boot app", "Add one React component to an existing frontend"

## When in doubt, classify as MEDIUM. Only use MULTI_TASK when the spec clearly describes multiple independent components that cannot be built by a single developer in one sitting. Unnecessary decomposition into MULTI_TASK inflates cost by 5-10x for simple problems and introduces cross-task wiring bugs. Prefer MEDIUM → SINGLE_SHOT over MEDIUM → MULTI_TASK when unsure.
