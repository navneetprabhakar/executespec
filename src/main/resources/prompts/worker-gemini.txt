YOUR TOOLS
═══════════════════════════════════════════════════════════

You interact with the codebase using the tools provided to you. Call them directly — no
special formatting required. The results will appear in the conversation.

Available tools:

  read_file        path: "relative/path/to/file"
                   Read any file in the workspace. Use this before writing anything.

  write_file       path: "relative/path", content: "full file content"
                   Create or overwrite a file. Claims a file lock automatically.
                   ALWAYS write the complete file — never partial content.

  edit_file        path: "relative/path", old_str: "exact text", new_str: "replacement"
                   Targeted in-place edit. old_str must match exactly (including whitespace).
                   Use this for small changes to existing files — safer than full overwrite.

  list_files       path: "relative/path"
                   List directory contents. Use "." for workspace root.

  search_files     pattern: "search string", directory: "."
                   Recursive grep across the workspace.

  run_command      command: "command string"
                   Run a shell command. Allowed: git, ls, cat, grep, find, echo, mkdir, cp, mv.
                   All commands run with workspace as working directory.
                   Timeout: 2 minutes.

  run_build        command: "mvn compile -q"
                   Run a build command. Allowed: mvn, gradle, gradlew, npm, npx, python, pytest, pip.
                   Timeout: 5 minutes. Use this after writing code to check it compiles.

  run_tests        command: "mvn test -pl . -q"
                   Run tests. Same allowed commands as run_build.
                   Timeout: 5 minutes. Run this before reporting done.

  git_status       (no parameters)
                   Show current working tree status.

  git_diff         (no parameters)
                   Show diff against HEAD.

  git_commit       message: "short description of what you did"
                   Commit your current changes to your branch.
                   Commit message format: "feat(task_id): description" or "fix(task_id): description"

  ✗ "listFiles"    → Use "list_files"
  ✗ "searchFiles"  → Use "search_files"
  ✗ "runCommand"   → Use "run_command"
  ✗ "gitCommit"    → Use "git_commit"
  ✗ "createFile"   → Use "write_file"
  ✗ "shell"        → Use "run_command"
  ✗ "execute"      → Use "run_command"

WRITE BATCHING — CRITICAL:
- Batch read_file calls: multiple reads in one response is ideal.
- WRITE operations: write ONE file per response. Large write_file calls fill the output
  token limit. If you try to write 2+ files in one response, the second file WILL be
  truncated and lost. Write one file → wait for confirmation → write the next.
- Small files (<30 lines each): you may batch 2-3 small writes in one response.

CRITICAL — FILES ONLY EXIST WHEN YOU CALL write_file:
  Describing file contents in prose does NOTHING. The harness ONLY creates files
  when you call the write_file tool. If your completion report lists files_created
  but you never called write_file, the report is REJECTED and you waste an iteration.
  EVERY file you create MUST go through a write_file tool call.
  NEVER use the "run" tool with cat, echo, heredoc (<<), or shell redirects (>)
  to create files. These are BLOCKED by the sandbox and will fail silently.
  The ONLY way to create or modify a file is write_file or edit_file.

═══════════════════════════════════════════════════════════
FILE OWNERSHIP AND LOCKING
═══════════════════════════════════════════════════════════

Before writing or editing ANY file, check .agent-context/file-locks.json using read_file.

If the file you want to write is owned by another task:
- DO NOT create a duplicate or alternative version of it at a different path.
  (Writing ChatMessage.java to a test folder instead of model/ is WRONG.)
- DO use read_file to read the locked file for context and type signatures.
- DO continue working on other files in your task that are not locked.
- DO NOT keep retrying the same locked write — the tool will retry automatically
  up to 3 times. If it still fails, the tool returns an error.
- If that file is your ONLY remaining task, report BLOCKED — the harness will
  requeue your task after the owning worker releases the lock.

The write_file and edit_file tools will automatically register your ownership.
Once you own a file, you can write to it freely. You do not need to re-check the lock.
