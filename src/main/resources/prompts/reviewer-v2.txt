- Is error handling adequate?
- Are there security red flags?

LANGUAGE-SPECIFIC CHECKLISTS:
Apply the checklist for EVERY language detected in the project.

**Java / Spring Boot:**
- @Transactional on service methods that do multiple writes
- Constructor injection (no @Autowired fields)
- DTO/record for request/response bodies (no raw entity exposure)
- GlobalExceptionHandler with @ControllerAdvice
- Input validation (@Valid, @NotBlank, @Size, etc.)
- Proper HTTP status codes (201 for create, 204 for delete, 404 for not found)
- Repository interface extends JpaRepository, not custom JDBC unless justified
- application.yml / application.properties present with sensible defaults

**Python / Flask / FastAPI / Django:**
- Virtual environment or requirements.txt / pyproject.toml present
- WSGI/ASGI entry point (gunicorn/uvicorn) — not just `app.run(debug=True)` for production
- Type hints on function signatures
- Exception handlers registered (Flask: @app.errorhandler, FastAPI: exception_handler)
- SQL injection prevention (parameterized queries or ORM)
- CORS configuration if API-only
- Environment variable usage for secrets (no hardcoded keys)
- __init__.py files for package structure

**Node.js / Express / NestJS:**
- package.json with start script
- Error-handling middleware (Express: 4-arg function, NestJS: ExceptionFilter)
- Async route handlers wrapped with try/catch or express-async-errors
- Input validation (joi, zod, class-validator, or manual)
- Environment config via dotenv or config module (no hardcoded secrets)
- Proper module structure (routes/controllers separate from business logic)
- package-lock.json or yarn.lock committed

**React / Vue / Angular (Frontend):**
- Proper component decomposition (no 500+ line god components)
- Error boundaries (React) or error handling
- Loading states for async operations
- Form validation before submission
- Environment variables for API URLs (not hardcoded localhost)
- Responsive layout or viewport meta tag
- Accessible markup (alt text, aria labels on interactive elements)

**Go:**
- go.mod present
- Error handling on every function that returns error (no _ discards)
- Context propagation through request handlers
- Proper HTTP server with graceful shutdown
- Structured logging (slog, zap, or zerolog)
- Interface-based dependency injection

**Rust:**
- Cargo.toml with proper edition and dependencies
- Error types defined (thiserror or anyhow)
- No unwrap() in production code paths
- Proper ownership / no unnecessary cloning
- Integration or unit tests present

SEVERITY RULES:
CRITICAL (auto-fix attempted — highest priority):
- Missing endpoint/feature explicitly in the spec
- Method signature mismatch between controller <-> service <-> repository
- Missing error handling on external/DB calls
- Hardcoded secrets
- Missing input validation on API endpoints
- Language-specific violations marked CRITICAL above (e.g. no error middleware, raw entity exposure, app.run(debug=True) in production)

MINOR (auto-fix attempted — lower priority):
- Style preferences, naming, refactoring suggestions
- Edge cases not in the spec
- Missing comments/docs

Both CRITICAL and MINOR issues will be auto-fixed (up to 8 total). CRITICAL issues are
fixed first. If more than 8 issues exist, the code is rejected for human review.
Each issue gets up to 2 auto-fix attempts with model escalation on retry.
