You are a principal engineer making an architecture decision. A fintech startup (12 engineers, Series A, 18 months runway) needs to rebuild their payment processing system. Current state: a monolithic Django app processing $2M/month in transactions, experiencing ~3 outages/month due to tightly coupled payment flows.

Evaluate these three architectural approaches and recommend ONE with detailed justification:

OPTION A — Microservices (event-sourced)
- Separate services: PaymentGateway, LedgerService, FraudDetection, NotificationService, ReconciliationEngine
- Event sourcing with Apache Kafka for the ledger (complete audit trail, point-in-time replay)
- CQRS: separate read models for dashboards (Elasticsearch) vs write models (PostgreSQL)
- Saga pattern for distributed transactions (payment → fraud check → ledger entry → notification)
- Kubernetes deployment with service mesh (Istio)
- Estimated build time: 9-12 months

OPTION B — Modular monolith (domain-driven)
- Single deployable with strict module boundaries (Java modules or Gradle subprojects)
- Modules: payments, ledger, fraud, notifications, reconciliation
- Inter-module communication via in-process event bus (no network hops)
- Shared PostgreSQL with schema-per-module isolation
- Transaction boundaries at the module level (no distributed transactions)
- Can be decomposed into microservices later if needed
- Estimated build time: 4-6 months

OPTION C — Serverless (AWS-native)
- AWS Lambda functions per payment flow step
- Step Functions for orchestrating payment processing pipeline
- DynamoDB for transaction state, SQS for async processing
- API Gateway with WAF for external-facing endpoints
- EventBridge for cross-service events
- Vendor lock-in but minimal ops overhead
- Estimated build time: 3-5 months

CONSTRAINTS:
- Team has strong Python/Django experience, limited Java/K8s experience
- Must maintain PCI DSS Level 2 compliance
- Current p99 latency is 800ms, target is <200ms
- Must support multi-currency (USD, EUR, GBP initially, expansion to APAC in 12 months)
- Audit trail must be immutable and queryable for 7 years (regulatory requirement)
- The system processes idempotent payment intents — duplicate requests must return the same result
