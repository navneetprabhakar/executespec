# be-orchestration — raw findings

Scope: `src/main/java/com/navneet/executespec/integration/` (51 files, 10,833 LOC, branch `benchmark` working tree — no uncommitted changes inside this package) + `src/test/java/com/navneet/executespec/integration/` (7 files, 677 LOC). Every main file read in full; conclusions grep-verified against the whole repo (src/main, src/test, frontend/). No docs consulted.

## 1. Inventory — per sub-area

### 1a. Run orchestration core (the RunOrchestrator god-class split)
- **`RunOrchestrator.java` (2,637)** — implements `RunControlPort`. Owns: `submitRun` (8-deep overload pyramid, 13→20 args), the async `runPipeline` (6-deep private overload pyramid), the PATCH-mode branch `runPatchPipeline`, `terminate` (public 4-arg → private 5-arg), `persistEstimate`/`clampHardCap`, `resolveTerminalStatus`, breaking-change detection, the `activeRuns` ConcurrentMap (cancel handle), and workspace final-commit. ~45 injected collaborators. BUILD flow: BYOK key bind → org/run model-override bind (ThreadLocal) → workspace init → optional multi-repo clone → codemap/assessment → classify → plan (SMALL/MEDIUM/LARGE/SINGLE_SHOT routing with circuit-breaker degrade) → persist plan/tasks/estimate → plan gate (`GateStore.awaitPlanGate`, blocking) → `SequentialExecutor.execute` → code-gen-only / LOCAL early stops → lint → reviewer → standards/contracts → README → validation kickoff → final git commit → terminate → auto-push.
- **`RunLifecycleService.java` (884)** — extracted control plane: `cancel`, `pause`, `haltAllActiveRuns`, `forceFailTask`, `resume`, `resumeAfterCrash` (+ `runPipelineFromExecuteCheckpoint`, `finalizeRunAfterResume`), `retryTask`, `retryValidation`, `reReview` (+ `runReReviewBlocking`). Reaches the orchestrator through `RunControlPort`.
- **`RunControlPort.java` (32)** — package-private seam: `putActiveRun`/`removeActiveRun`/`runPipelineForResume`/`terminate(4-arg)`.
- **`PipelineExecutorPool.java` (85)** — fixed daemon pool `clamp(4..16, cores×1)`, `@PreDestroy` 30s graceful shutdown. Shared by: pipeline submission, resume/retry/re-review resubmits, AND the LARGE-planner fan-out via `executor()`.
- **`RunPlanningCoordinator.java` (558)** — classifier shadow run, outline phase, LARGE pipeline (skeleton → parallel `TaskExpanderAgent` expansion on the shared pool → coherence pass), `expandEpic` depth-2 recursion. Per-phase token/cost attribution onto `pipeline_run` columns.
- **`RunPersistenceWriter.java` (291)** — thin DB writes: persistPlan/persistTasks/applyExecutionResultToTasks/persistReview(+Failure)/updateStatus (blind)/persistRunTitle/reconstructExecResultFromTasks/writeRunCostLog.
- **`RunContextComposer.java` (451)** — prompt-block builders: run-meta README, `.agent-context/project.json`, design block, code-intel block (caps 3k/1.5k), arch block (cap 800), `normalizeProvider`, `defaultModelFor`, multi-repo workspace summary + language-parity block.
- **`RunStandardsEnforcer.java` (170)** — deterministic standards run at run-end; bounded walk (6k files), capped persist (200 rows).
- **`RunValidationKickoff.java` (400)** — assembles `ReportInput` (worker reports from task outcomes, review verdict mapping, accuracy LLM call, real test exec behind `scoring.real-test-exec`, verifyBoot behind flag), synthesises `ReviewIssue`s.
- **`RunPipelineSupport.java` (249)** — static helpers (repo-id (de)serialisation, status mapping, truncate, workspace walk, provider coercion, language hints).
- **`PerkyMessenger.java` (116)** — 15s-interval SSE "encouragement" heartbeat per phase; 2-thread scheduler, `@PreDestroy` shutdown.
- **`scm/ScmPushService.java` (764)** — push + PR creation: Bitbucket vs GitHub dispatch, single-repo branch+PR, `pushMultiRepo` (per-subdir branch+PR+cross-link+representative URL), `pushApplyChanges` (fast-forward to existing PR branch), orphan-branch saga compensation, per-repo commit messages.

## 2. Findings

### Real bugs first

- **[BUG] `terminate()` NPEs on every `startedAt=null` call site — and skips RunCompleted/RunFailed publication.** `RunOrchestrator.java:2305` does `Duration.between(startedAt, Instant.now())` with no null guard (`Metrics.recordRunLatency(String, Duration)`). Null is passed by `RunLifecycleService.java:349-350` (resume-cap EXHAUSTED), `:379` (WORKSPACE_GONE), `:418`/`:430` (PLAN_MISSING), and `:693`/`:697` (retryTask terminal + its own catch). The NPE fires *after* the status write/SSE but *before* `eventPublisher.publishEvent(RunCompleted/RunFailed)` at `:2311-2318` — so quota refund, in-app notifications, GCS workspace upload, and activation tracking are silently skipped on those paths. In `retryTask` the catch block calls `terminate(...null)` again → second NPE swallowed by the pool `Future`. Every task retry that finishes hits this.

- **[BUG] Cancellation is resurrected by blind phase-status writes; a cancelled run can end COMPLETE/PARTIAL and auto-push a PR.** Chain: `RunLifecycleService.cancel():117-133` writes CANCELLED + `future.cancel(true)`; `SequentialExecutor.execute` (harness/SequentialExecutor.java:328-333) detects the interrupt at the loop top, **breaks and returns a normal `ExecutionResult`** (no exception); `runPipeline` marches on; `RunPersistenceWriter.updateStatus:249-258` blindly writes "REVIEWING" (`RunOrchestrator.java:1478`) over CANCELLED; the reviewer fails fast on the interrupt and is caught non-fatally (`:1532-1537`); `terminate`'s CANCELLED guard (`:2252`) reads the already-clobbered status (now REVIEWING) → writes PARTIAL/COMPLETE; the auto-push gate (`:1707-1743`) fires on COMPLETE/PARTIAL → **a PR is opened for a run the user cancelled**, `RunCompleted` (not `RunFailed`) is published → no credit refund (RunQuotaRefundListener listens only on RunFailed — billing/service/RunQuotaRefundListener.java:43-44). `cancel`'s own comment ("its terminal writes are no-ops because the run is already terminal") is false: only `terminate` guards, and only for CANCELLED, and only against the current (clobbered) status.

- **[BUG] PAUSED is clobbered the same way — pause is structurally broken.** `RunLifecycleService.pause():148-181` writes PAUSED + interrupts. The pipeline unwinds exactly as above; `terminate`'s guard (`RunOrchestrator.java:2252`) protects **only** CANCELLED, so the run lands PARTIAL/COMPLETE; `resume()` (`:277`) then returns NOT_PAUSED forever. (Flag `v2.pause.enabled` default OFF mitigates exposure; cancel above is always-on.)

- **[BUG] Crash-resume of a PLANNING-status PRODUCTION run silently skips the plan-approval gate.** `RunOrchestrator.RunPipelineRequest.fromPausedRow:2179` hardcodes `skipApproval=true` ("already approved before the original execution started" — untrue for a run that crashed *during planning*, pre-gate). `RunLifecycleService.resumeAfterCrash:385-408` uses it for PLANNING runs → on JVM restart the run replans, executes, and auto-pushes with **no human approval and no credit charge** (credits are charged at the approve endpoint, which is never hit). Bonus field-confusion at `:2178`: `approvedExecutionMode` ("REALTIME" — the realtime/batch axis, stamped at submit `RunOrchestrator.java:631`) is passed as `executionMode` (the PRODUCTION/PROTOTYPE axis); masked only because skipApproval is already true.

- **[BUG] The 4-arg `RunControlPort.terminate` silently drops the status reason.** Signature is `(runId, status, note, startedAt)` → forwards `statusReason=null` (`RunOrchestrator.java:2220-2223`). `RunLifecycleService.finalizeRunAfterResume:587` and `retryTask:692-693` pass `terminal.reason()` (e.g. CLEAN_COMPLETION / FINAL_BUILD_FAILED) into the **note** slot → crash-resumed and retried runs never get `status_reason` persisted, and the SSE complete event carries null reason. The port's javadoc (`RunControlPort.java:31`, "persists status + status_reason") describes the 5-arg private method, not itself.

- **[BUG] `runPatchPipeline` writes terminal state without the CANCELLED guard, never finalizes the cost tracker, never closes SSE, never records run metrics.** `RunOrchestrator.java:1949-1970` sets status unconditionally (a cancelled PATCH run gets clobbered to COMPLETE/FAILED — the guard exists only in `terminate`, which patch mode bypasses); `costTracker.finalizeRun` is never called (only `snapshot` at `:1948` — tracker accumulator entry leaks per patch run, vs `terminate:2232`); `broadcaster.complete(runId)` is never called (`:2031-2037` and the error path `:1906` only `emit`) → SSE emitters stay registered until client timeout, counting against the 500-emitter global cap; `metrics.recordRunOutcome/recordRunLatency` never fire → patch runs invisible in run-outcome metrics.

- **[BUG] Jira webhook "signature" verification compares the raw shared secret against the header — not an HMAC of the body.** `jira/JiraAdapter.java:57-62`: `received = headers["x-hub-signature"]`, `expected = config.getWebhookSecret().getBytes()`, `MessageDigest.isEqual(expected, actual)`; `rawBody` is never used. Jira/Atlassian automation sends an HMAC digest in that header, which can never equal the static secret → real signed Jira webhooks are always rejected; conversely the accepted scheme is a static token (replayable, body unauthenticated) wearing a signature header's name. Constant-time comparison of the wrong thing.

- **[BUG] Confluence `page_updated` dedupe swallows all subsequent edits of a page for 7 days.** `confluence/ConfluenceAdapter.extractEventId:79-88` returns `"page_updated-{pageId}"` with no version component; `IntegrationManager.handleWebhook:136` dedupes on it; rows live 7 days (`IntegrationEventLogCleanupJob:26-27`). Editing a labelled page twice in a week silently drops the second trigger as "duplicate". Same shape: `bitbucket/BitbucketAdapter.extractEventId:72-84` (`"bb-pr-{id}"` — one event per PR per week, across *different* event kinds).

- **[BUG] ServiceNow idempotency is defeated the opposite way.** `servicenow/ServiceNowAdapter.extractEventId:70-80` appends `System.currentTimeMillis()` when `eventId` is missing → every webhook *retry* mints a fresh id → duplicate runs (each an LLM spend). The `UUID.randomUUID()` fallback on parse failure (also Jira `:71`, Confluence `:87`, Bitbucket `:80-83`) has the same effect for malformed payloads.

- **[BUG] Slack token-revocation cleanup can't work — derived deletes without a transaction.** `slack/SlackNotificationService.handleSlackError:215-223` calls `channelRepo.deleteByOrgId(orgId)` + `integrationRepo.delete(...)` on the async `slack-notif-` executor with no `@Transactional` anywhere on the path; `ProjectSlackChannelRepository.deleteByOrgId` / `OrgSlackIntegrationRepository.deleteByOrgId` are plain derived methods (no `@Modifying`/`@Transactional`, unlike `SlackNotificationLogRepository.deleteByCreatedAtBefore` which has both) → `TransactionRequiredException` at runtime, swallowed by the caller's catch (`:201-210`) → a revoked integration is never removed and every subsequent event repeats the failure. (`SlackOAuthService.disconnect:119-131` is `@Transactional` and fine — the inconsistency is the tell.)

- **[BUG] `commitWorkspaceOutputs` can hang the pipeline thread forever.** `RunOrchestrator.java:2055-2072`: both `git` processes use `redirectErrorStream(true)` but **stdout is never consumed**; `git commit` output beyond the OS pipe buffer (~64KB — plausible: non-quiet commit prints a create-mode line per new file) blocks the child, and `commitPb.start().waitFor()` is **unbounded** → run stuck (status REVIEWING) + pool thread leaked. The `git add` timeout result (30s, `:2062`) is ignored — on timeout the commit proceeds against a partially-staged index with the add still running.

- **[BUG] `PipelineEvent.MergeCompleted` is never published — integration "run complete" notifications are dead code.** Grep: only the record definition (`harness/event/PipelineEvent.java:27`) and two listeners (`IntegrationOutboundListener.java:59`, `PostMergeOrchestrator.java:34`); zero publishers. So `onRunComplete` for Jira/Confluence/ServiceNow/PagerDuty/Bitbucket (comments, status transitions, output pages, auto-resolve) can never fire. Started/failed notifications work (RunStarted `:669`, RunFailed from `terminate`).

### Risks

- **[RISK] One fixed pool (4–16 threads) hosts three classes of long blockers → platform-wide stalls.** (a) A PRODUCTION run at the plan gate blocks its pool thread **up to 24h** (`GateStore.MAX_GATE_WAIT`, harness/GateStore.java:55; wait at `RunOrchestrator.java:1354`). (b) `runLargePipeline` blocks `.get(20, MINUTES)` (`RunPlanningCoordinator.java:291-294`) on expansion futures scheduled on the **same** pool (`:289` `pool.executor()`); (c) `expandEpic` nests a second blocking layer (`:538-541`). On a 4-core box, 4 runs sitting at approval gates (or 1 LARGE run + a few EPICs) starve every other run — including resumes and retries — for up to the gate/timeout duration. `PipelineExecutorPool.java:17-21`'s sizing rationale ("can't saturate Hikari") doesn't account for the pool feeding on itself.

- **[RISK] `activeRuns` registration race → leaked map entries / no cancel handle.** `RunOrchestrator.java:694-716`: `pool.submit(...)` runs the task whose `finally{activeRuns.remove}` can execute **before** the submitting thread's `activeRuns.put(runIdFinal, future)` → the put re-inserts after removal and the entry leaks forever (done-Future; cancel becomes a no-op but the map grows). Same submit-then-put ordering in `RunLifecycleService.resume:311-320`, `resumeAfterCrash:398-407/:453-462`, `retryTask:659-702`.

- **[RISK] No optimistic locking + pervasive read-modify-write on `PipelineRun`.** Entity has no `@Version` (state/entity/PipelineRun.java). Concurrent writers — `cancel` (lifecycle), `terminate`/`updateStatus` (pipeline thread), `runPatchPipeline`'s save of a stale entity loaded ~800ms earlier (`RunOrchestrator.java:1005` probe → `:1831` save), classifier/outline persists, `keySource` write `:858-861` — interleave as full-row lost updates. The cancel-clobber bug above is one concrete instance; the patch-mode `runRepo.save(run)` at `:1831` can also undo a concurrent cancel.

- **[RISK] `resume`/`retryTask`/`reReview` are check-then-act with no claim — double dispatch possible.** `RunLifecycleService.resume:273-302` reads PAUSED, saves WORKING, submits; two concurrent calls both pass the check → two pipelines on one workspace (second `putActiveRun` overwrites the first future — first becomes uncancellable). The plan-approve path got an atomic claim (`GateStore.tryClaimPlanGate`); these didn't.

- **[RISK] Idempotency row saved before submit → a failing submit permanently eats the event.** `IntegrationManager.handleWebhook:150-154` persists the dedupe row, then `submitIntegrationRun` — which **throws today** in every tracked config (C8 fail-closed: `agent.integrations.run-on-behalf-of-user-id` absent from application.yml; `:84-91`) → 500 to the caller, but the retry hits the dedupe (`:136`) and returns "duplicate". One delivery attempt, event lost. The comment ("avoid race on webhook retries") trades a real loss-mode for the race.

- **[RISK] Reviewer-null defaults to APPROVED in the validation report.** `RunValidationKickoff.java:136-140`: when the reviewer never ran, `ReviewVerdict.APPROVED` + "Review did not run." feeds the REVIEWER scoring slot an approval for an unreviewed run.

- **[RISK] `resolveTerminalStatus(result, null)` on the retry path downgrades good status reasons.** `RunLifecycleService.retryTask:692` passes `review=null` → fallback reason NO_REVIEW_RESULT (`RunOrchestrator.java:2515`) replaces a previously meaningful `status_reason`… except it doesn't even get persisted (4-arg terminate bug above) — the run keeps the *stale* pre-retry reason alongside a new status.

- **[RISK] Crash-resume path loses run context the normal path has.** `runPipelineFromExecuteCheckpoint` (RunLifecycleService.java:472-561) never rebinds `RunModelOverrides` (F3 org overrides + ENTERPRISE pin → resumed runs silently fall back to YAML models), never re-registers programbench/local-hands state, runs with `designBlock=null` (`:516`), and skips all token attribution (`afterExec` captured `:528` then never used).

- **[RISK] LOCAL-hands flag is consumed before the PATCH branch but only acted on after it.** `RunOrchestrator.java:966-968` consumes `runLocalExecutionFlag` (Redis one-shot), PATCH dispatch returns at `:1004-1011`, remote-dispatcher registration happens later at `:1019` — a LOCAL+PATCH submission would consume the flag yet run with server-side tools. Also: resume of a LOCAL run can't re-consume the flag → resumes as a *server* run against an empty workspace (gated OFF today).

- **[RISK] `SequentialExecutor` smoke tests disabled for LOCAL runs but resume re-enables them.** `runPipeline:1380` passes `enableSmokeTests(!localRun)`; `runPipelineFromExecuteCheckpoint:515` hardcodes `true` (resume doesn't know about localRun — consistent with the flag being one-shot, but another way resume diverges).

- **[RISK] `RunStarted` published synchronously on the submit thread before the pool submit.** `RunOrchestrator.java:669` — a throwing `@EventListener` aborts `submitRun` *after* the run row is persisted (`:642`) → run stuck in PLANNING with no pipeline thread. Listeners are best-effort by convention, not by enforcement.

- **[RISK] ServiceNow + Bitbucket webhook verification fail OPEN when unconfigured.** `servicenow/ServiceNowAdapter.java:37` (`if (signatureHeader == null && secret == null) return;`) and `bitbucket/BitbucketAdapter.java:44` accept unsigned posts when no secret is set; Jira (`:39-43`), PagerDuty (`:46-50`), Confluence (`:73-75`) fail closed. Endpoints are `permitAll` (`SecurityConfig.java:176`).

- **[RISK] `SlackRateLimiter.acquire` is racy.** `slack/SlackRateLimiter.java:27-43` get-sleep-put without atomicity — 2–4 executor threads for the same team can all pass and burst-send; also sleeps swallow interrupt (flag re-set, then proceeds to send anyway).

### Inconsistencies / smells / duplication / layering / perf

## 7. Security notes (parked)

- Plaintext credentials at rest on `pipeline_run`: `github_pat` (PipelineRun.java:382) and `bitbucket_app_password` (`:410`); `ScmPushService:83-87` actively copies the user's Bitbucket app password onto the run entity, persisted by any subsequent `save`.
- Jira "signature" = static token compare, body unauthenticated, replayable (`JiraAdapter:57-62`).
- ServiceNow + Bitbucket webhook verification fail OPEN when no secret configured (`ServiceNowAdapter:37`, `BitbucketAdapter:44`) on `permitAll` endpoints (`SecurityConfig:176`).
- `sanitizeAndCap` doesn't strip `SYSTEM: <payload>` lines — external Jira/Confluence content reaches the planner prompt nearly raw (`IntegrationManager:249-258`).
- Slack OAuth state HMAC keyed on `app.jwt.secret` with literal default `executespec-default-secret` (`IntegrationConfig:133`) — forgeable state if the property is ever unset.
- `IntegrationController.webhook` catch-all returns `e.getMessage()` in the 500 body (`IntegrationController:55`) — internal detail leak to unauthenticated callers.
- Confluence legacy fallback accepts the **API token itself** as a webhook bearer (`ConfluenceAdapter:62-71`) — credential doubling as inbound auth.
- `OrgSlackIntegration.botToken` stored plaintext (TEXT column, `OrgSlackIntegration.java`).
- GitTool pushes used by this package force-push (`GitTool.java:592/:639`) — run re-push can obliterate manual commits on the run branch (acknowledged for apply-path in `ScmPushService:666-668`, not for re-running `push()`).
