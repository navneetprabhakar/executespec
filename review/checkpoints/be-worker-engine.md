## 2. Findings

### Real bugs first

- **[BUG] `persistTaskStatus`'s `@Transactional` + `@Retryable` never apply — Spring self-invocation.** `SequentialExecutor.persistTaskStatus` (3 overloads, `harness/SequentialExecutor.java:1342-1474`) is annotated `@Transactional @Retryable(DataAccessException, 3 attempts)`, but every one of its 11 call sites is an internal `this.persistTaskStatus(...)` call from `execute`/`executeOne` (L563, 705, 750, 780, 805, 842, 956, 1002, 1034, 1087, 1134; repo-wide grep confirms zero external callers). `@EnableRetry` (`ExecutespecApplication.java:40`) is proxy-mode; no AspectJ/exposeProxy anywhere — so the annotations are decorative. The exact incident the L1356-1362 javadoc says this fixes ("dev run 3b739e94 task stuck in WORKING for 90+ min on a swallowed transient DataAccessException") is **still possible**: a transient failure inside the method is caught by the local `catch (Exception e)` at L1471 and logged at WARN, with no retry. `SuperAdminController.java:140-141` further documents the protection as real ("The @Retryable on persistTaskStatus prevents the original cause") — a false belief now baked into the ops tooling. Fix: move the method to a separate `@Component`, or retry manually.

- **[BUG] Flag interaction: `ToolOutputCompactor` destroys the verification-gate markers — gated `completeTask` becomes permanently refusable.** The test gate matches exact substrings of the **post-compaction** envelope: `WorkerAgent.java:998-1004` requires `\"failed\":[]` + `\"errored\":[]` + `\"exit_code\":0`; the build gate `WorkerAgent.java:1011-1016` requires `\nexit=0\n`. The envelope content flows through `maybeCompact` first (`dispatchOne`, `WorkerAgent.java:1689-1690`), and `ToolOutputCompactor.SKIP_TOOLS` (`tool/ToolOutputCompactor.java:92-93`) is `{writeFile, editFile, gitCommit, completeTask, gitDiff, gitStatus}` — **`runTests` and `buildProject` are compactable**. With `worker.tool-compactor.enabled` ON, any runTests/buildProject output >3KB that isn't the last call in its batch is LLM-summarised, the markers vanish, `lastTestRunIter`/`lastBuildPassIter` never advance, and — because the test/build gates have **no refusal bound** (unlike deliverable ≤2, VBC ≤3, critic 1; see L728-806) — the worker is refused completion until the iteration cap (220 in patch mode). Affected combinations: PATCH autofix surfaces (`PatchAgent` sets `requireTestVerification` for `finding:*` sources, `agent/PatchAgent.java:140-161`) and every BUILD smoke-retry (`requireBuildVerification(true)`, `SequentialExecutor.java:917`). Both flags are individually default-OFF and individually "safe"; together they are toxic. Same fragility class even without the compactor: the markers couple byte-exactly to `RunTestsTool`'s compact-Jackson shape (`env.toString()`, `tool/RunTestsTool.java:301-309`) and `BuildProjectTool`'s `\nexit=N\n` framing — a formatting change in either tool silently bricks the gates.

- **[BUG] Retry-failed path never persists task status — DB row stranded in WORKING.** `harness/SequentialExecutor.java:977-995`: when the same-provider retry doesn't reach `COMPLETED` (and cross-provider fallback is off/failed), the method returns a `COMPLETED_WITH_WARNING` outcome **without any `persistTaskStatus` call** — the only terminal branch in `executeOne` that doesn't write the DB (compare L842, L1002, L1034, L1087, L1134). The task row stays `WORKING` (set at L563) until the run-end reconciliation; the polled task list shows a live-but-dead task for the rest of the run.

- **[BUG] PAT leak in clone failure output.** `harness/WorkspaceInitService.java:396-406` (`runGitStrict`): the PAT is masked in the *command* string (`oauth2:[^@]+@` → `oauth2:***@`) but the raw process output `out` is appended unmasked to the thrown `RuntimeException`. `git clone` failures routinely echo the authenticated URL (`fatal: unable to access 'https://oauth2:<pat>@github.com/...'`), so the customer PAT lands in exception messages → application logs. Call sites: `cloneFromRepo` L134, `cloneMultipleRepos` L306/309. (Also parked in §7.)

- **[BUG] Cross-provider retry can throw `IllegalArgumentException` and fail the entire run.** `maybeCrossProviderRetry` calls `tierConfigFor(task.complexity(), altProvider, /*runModel=*/null, …)` (`SequentialExecutor.java:1774-1775`). If `ModelResolver.resolve` throws (unregistered matrix cell, config drift), the catch-fallback builds `TierConfig(altProvider, null, …)` (L1330-1338) → `WorkerTaskRequest.builder().model(null)` → compact-constructor `IllegalArgumentException("model required")` (`engine/WorkerTaskRequest.java:156`). Nothing catches inside `executeOne`/`execute`; the exception reaches `RunOrchestrator`'s wrapper (`integration/RunOrchestrator.java:1394-1398`) which terminates the **whole run** FAILED/INTERNAL_ERROR — and the `execute()` exit cleanup (`contextStore.deleteAll` + `clearCrossProviderState`, L393-396) is skipped. A lever meant to rescue one task can kill the run. Dormant (flag V220 default OFF), but it's the kind of path that only ever executes in anger.

- **[BUG-minor] Salvage outcomes mislabeled + iteration counts fabricated.** `salvageAttempt`'s `completeTask` branch always records/returns `ITERATION_LIMIT_EXCEEDED` with `iterations(maxIterOf(req))` (`engine/WorkerAgent.java:1316-1327`) even when the salvage was entered from the **budget** path (L512-530) or **stagnation-force** path (L1136-1153) at, say, iter 13 of 220. The write-success branch (L1342-1353) similarly stamps `iterations(maxIterOf(req))`. Worker outcome metrics (`recordTerminal`), `describeWorkerFailure`, and the persisted diagnostics all report the wrong cause and an inflated iteration count.

- **[BUG-minor] Salvage/stagnation `COMPLETED` paths leak the Redis context snapshot.** Normal completion deletes it (`WorkerAgent.java:972`), the terminal finalizer deletes it (L1493, 1526), but salvage-`COMPLETED` (L1342-1353) and `COMPLETED_BY_STAGNATION` (L1154-1162) don't — 24h TTL is the only cleanup for non-BUILD callers (BUILD gets `contextStore.deleteAll` at run end, `SequentialExecutor.java:393-394`; PATCH/TB get nothing at task end).

- **[BUG-minor] Nudge messages instruct a `completeTask` argument that doesn't exist.** `CompleteTaskTool.inputSchema()` declares only `summary`, `required:["summary"]`, `additionalProperties:false` (`tool/CompleteTaskTool.java:46-58`). Three worker messages tell the model to use **`completionNotes`**: the product progress nudge ("call the `completeTask` tool now with your summary as the `completionNotes` argument", `WorkerAgent.java:1975-1977`), the verify nudge (L935-936), the VBC refusal (L2122-2123). Best case the summary lands in an ignored field and `extractSummary` records "(no summary)"; on a strict-schema provider the call can be rejected outright (completeTask bypasses `ToolArgValidator` — it's intercepted at L721 before validation — so the server never corrects it either).

- **[BUG-minor] `previewThought` first-line contract broken when text starts with `\n`.** `WorkerAgent.java:1878-1883`: `nl > 0` should be `nl >= 0`; a leading newline keeps the whole multi-line text and the "first-line only so newlines never split the banner" guarantee fails.

- **[BUG-edge] `runId.substring(0, 8)` unguarded in `persistTaskStatus` (`SequentialExecutor.java:1398`)** — `resolveResumeAction` guards short runIds (L455) but the persist path doesn't; a <8-char runId throws `StringIndexOutOfBoundsException` inside the catch-all, silently skipping persistence. Real ids are UUIDs; tests use exactly 8 chars ("run-soft").

### Worker-loop conditional complexity (the explicit ask) — concrete counts

`WorkerAgent.run(WorkerTaskRequest, SavedContext)` (`engine/WorkerAgent.java:270-1209`, ~940 lines, one method):

- **14 configuration inputs** govern the loop: `progressWarnAfter`, `progressForceAfter`, `terminalTaskMode`, `terminalVerifyGateOn`, `criticOn`, `vbcOn`, `terminalArtifactDeadlineAfter` (derived, 3-term min/max at L338-342), `terminalForcedFinalizerAfter` (derived, L343-348), `gateOn`, `buildGateOn`, `wallClockMillisCap`, `hardCapUsd`, `requiredDeliverables`, `forceToolChoiceOnSalvage` (read in 4 helpers).
- **19 mutable loop variables**: `history, toolLog, toolsDispatched, lastText, itersSinceProgress, progressNudged, terminalArtifactDeadlineNudged, terminalForcedFinalizerAttempted, lastTestRunIter, lastBuildPassIter, totalWriteCalls, lastEditIter, lastVerifyIter, verifyNudged, deliverableRefusals, vbcRefusals, criticNudged, lastInputTokens, completionSummary`.
- **~15 sequential checkpoint blocks per iteration**: interrupt (L436) → wall-clock + terminal-finalizer sub-branch (L458-492) → budget every 3 iters + salvage sub-branch (L493-551) → history compaction (L556-560) → LLM call → text-only-stop fork (nudge | terminal finalizer | stop, L655-690) → per-call dispatch with the gate chain → marker tracking (L998-1024) → progress reset/increment (L1042-1051) → progress-warn nudge (L1052) → terminal artifact nudge (L1069) → terminal deadline nudge (L1081) → terminal forced finalizer (L1095) → progress-force + salvage (L1117) → context persist every 5 (L1168).
- **`completeTask` runs a 7-stage gate chain** (L721-983): test-recency gate → build-recency gate → deliverable-existence gate → VBC server test run → critic LLM pass → verify soft-nudge (a 6-clause condition at L919-924) → accept + sibling-supersede + snapshot delete.
- **[RISK] The "ONE counter, ONE nudge" comment (L307-317) is no longer true.** `progressNudged` is consumed by **three different triggers**: the mid-loop stagnation warn (L1052, keyed on `itersSinceProgress`), the text-only stop (L663), and — in terminal mode — an **absolute-iteration** nudge `iter >= progressWarnAfter` (L1069-1080) that fires even when `itersSinceProgress == 0` (shell counts as progress, so for TB this is what usually spends the one-shot slot at iter 16, silently disabling the genuine stagnation warn for the rest of the task). Counting the deadline nudge, forced finalizer, wall-clock finalizer and 3 salvage entry points, at least **7 distinct mechanisms** inject corrective messages or terminate the loop outside the "single progress signal".
- **[RISK] Terminal forced/wall-clock finalizers are silently inert without `forceToolChoiceOnSalvage`.** `runTerminalFinalizerCall(..., allowAutoFallback=false)` returns `null` **without making any LLM attempt** when `force` is false (`WorkerAgent.java:1413-1431`: `if (force) {...} if (!allowAutoFallback) return null;`). Callers: the wall-clock finalizer (L459-472) and the iter-threshold forced finalizer (L1095-1109). The follow-up message then tells the model "TERMINAL FINALIZER DID NOT PRODUCE A CLOSING TOOL CALL" (L1110-1115) when no finalizer ran at all. Live today only because `TerminalBenchRunService` hardcodes `forceToolChoiceOnSalvage(true)` (`terminalbench/TerminalBenchRunService.java:288`) — the dependency is invisible at both call sites.

### Other findings

- **[RISK] `safeId()` is non-deterministic for null/blank tool-call ids** (`WorkerAgent.java:1791-1793`, `"call_" + nanoTime`): the C1 parallel-read map is keyed with one `safeId(tc.id())` (L1614) and probed with a freshly generated one (L987) — a null id means a guaranteed miss → silent duplicate execution of the read, and a `ToolResponse` id that won't match the assistant `tool_use` id (Anthropic 400 on the next turn). Only providers that emit null ids trigger it, but the function's contract ("safe") hides the instability.
- **[RISK] Unbounded gate refusals** (`WorkerAgent.java:728-806`): `gateOn`/`buildGateOn` have no yield bound. If the workspace can never produce the pass markers (no pytest, broken runner), the worker burns its full cap. PatchAgent scopes the test gate off for `swebench*/benchmark*` sources precisely because of this (`agent/PatchAgent.java:138-143`) — the customer `finding:*` surfaces keep the unbounded behaviour.
- **[RISK] `GateStore.awaitPlanGate` — one unguarded Redis call on the happy path.** `redis.delete(planKey(runId))` at `harness/GateStore.java:218` runs right after the in-memory future resolves and is **not** inside any Redis-failure catch (every other Redis op in the class is). A Redis blip at the approval moment converts an approved run into an unhandled `RedisConnectionFailureException` on the pipeline thread. The poll path (L225-226) catches only `RedisConnectionFailureException`; other `RedisSystemException`s propagate.
- **[RISK] Budget enforcement gaps in the loop** (`WorkerAgent.java:423-424, 493-551`): `hardCapUsd` is read once per task — mid-run cap changes invisible; the check runs every 3 iterations, so up to 2 LLM calls + an optional salvage call land after the cap (salvage overspend is documented; the cadence isn't); BYOK runs (null cap) have **no** dollar enforcement here at all — caps rest entirely on iter/wall-clock.
- **[RISK] PATCH mode has no wall-clock budget.** `PatchAgent` never sets `wallClockSeconds` (`agent/PatchAgent.java:145-172`) → unbounded real-time for SWE-bench/autofix runs (iter cap 150-220 + dollar cap only). BUILD gets 30/45/75-min ladders ×2 for project runs; TB gets 900s. Inconsistent risk posture across the three consumers of the same loop.
- **[RISK] Wall-clock is checked only at iteration top** (`WorkerAgent.java:454-458`) — accepted by design for LLM calls, but VBC makes it worse: the server-side test run inside the `completeTask` gate (L861-877 → `verifyBeforeCompleteFailure` L2094-2114) executes the **entire workspace test suite synchronously**, up to 3 times per task, all inside the loop and after the top-of-iter check. A slow suite (multi-minute `mvn test`) extends a task well past its budget. [PERF] too.
- **[INCONSISTENT] `forceToolChoiceOnSalvage` never reaches PATCH mode** — the path whose failure motivated it (native-DeepSeek zero-edit empty patches per the V224 javadoc in `WorkerTaskRequest.java:56-67`). Setters: `SequentialExecutor` (BUILD, L612/918/1080/1808, flag-gated) and `TerminalBenchRunService:288` (TB, hardcoded). `PatchAgent.run` omits the field → SWE-bench/autofix salvage always runs `tool_choice=auto`.
- **[INCONSISTENT] Null-provider default is OPENAI in the executor but the platform default is anthropic.** `tierConfigFor`: `runProvider == null ? LlmProvider.OPENAI : ...` (`SequentialExecutor.java:1312`) vs `model-matrix.default-provider: anthropic` (`application.yml:444`). Unreachable through `ExecutionRequest` (validates provider non-null) but reachable from future callers of `tierConfigFor`.
- **[INCONSISTENT] Provider prompt fragment chosen from the run-level provider, not the dispatched one.** `composeSystemPrompt(..., req.provider())` is built at `SequentialExecutor.java:551-558` *before* `tierConfigFor` resolves `cfg.provider` (L566), and the same `systemPrompt` is reused verbatim for the cross-provider retry (L1798) — when V219 provider tuning is ON, an `anthropic`-tuned prompt can drive a `gemini` worker.
- **[INCONSISTENT] WorkerAgent's resume-idempotency javadoc contradicts the actual tool.** L255: "`writeFile` — overwrites whole-file content. Re-issuing the same call is a no-op." `WriteFileTool` **errors** on existing files (`tool/WriteFileTool.java:105-108`), as the system prompt itself says (`SequentialExecutor.java:88-89`). The stated resume idempotency contract is wrong for writeFile (re-issued write → `file already exists` error; recoverable, but not what the doc promises).
- **[INCONSISTENT] Dual status vocabularies mapped in three places.** DB statuses (`COMPLETE/PARTIAL/FAILED/BLOCKED`) vs `TaskOutcome.Status` (`SUCCESS/COMPLETED_WITH_WARNING/WORKER_FAILED/...`): soft-completion paths persist `COMPLETE` while returning `COMPLETED_WITH_WARNING` (L744-764, 774-794), smoke-fail-soft persists `PARTIAL` returning `COMPLETED_WITH_WARNING` (L830-856), and `synthesizeSkippedOutcome` (L515-533) plus `summarize` (L2032-2081) re-map again. Each mapping is locally reasoned; together they make "what state is this task in" a three-table join in your head.
- **[INCONSISTENT] Flag-name handling**: four flags get named constants (`SequentialExecutor.java:1598-1624`), while `"build.test-exec-gate.enabled"` (L1978), `"worker.verify-before-complete.enabled"` (L621) and `"worker.critic-pass.enabled"`/`"worker.verify-before-complete.enabled"` in PatchAgent are inline string literals.
- **[SMELL] Multi-repo behaviour keyed on `workspaceSummary.contains("MULTI-REPO")`** (`SequentialExecutor.java:1674`) — a string-sniffing contract with `RunOrchestrator`'s summary builder; a copy edit to that header silently unwires multi-repo prompts (the regression the test pins, but only via the same magic string).
- **[SMELL] `executeOne`'s retry ladder is hand-unrolled**: primary → smoke → soft-completion branch → retry-1 (+context-retention fork L921-936) → cross-provider fork → retry-1 re-smoke → zero-write demotion → HIGH-only retry-2 → final PARTIAL. Four near-identical `WorkerTaskRequest.builder()` blocks (L598-622, 904-919, 1066-1081, 1795-1809) already drift: only the primary sets `verifyBeforeComplete`, only retries set `requireBuildVerification`, retry-2 doesn't boost budgets the way retry-1 does.
- **[SMELL] Zero-write smoke-fail demotion to SUCCESS** (`SequentialExecutor.java:1029-1051`): a task whose worker wrote nothing and whose build fails is recorded `SUCCESS`/`COMPLETE` on the theory the failure is environmental. On a single-task run against an already-broken repo this stamps a green task on a red workspace; the reviewer is the only safety net.
- **[SMELL] Stale comments asserting wrong facts**: `WorkerAgent.java:706-709` claims "the four pre-existing WorkerAgent test failures reproduce on the unmodified HEAD" — all 11 worker test classes pass today (verified by run); L53-69 javadoc still says "no compaction yet — Phase 8" (compaction exists, flag-gated, L556-560); `agent/PatchAgent.java:93-95` comment says default cap 120 (it's 180, L66); `WorkspaceInitService.java:81-91` justifies `.gitattributes` union-merge with "worker.txt step 7" + "parallel workers" — V1-era artifacts (prompt has no README mandate; executor is sequential).
- **[SMELL] `copyFromRun` fallback log lies** (`WorkspaceInitService.java:196-207`): on `git ls-files` exit≠0 it logs "copying all files instead", but the error text (stderr merged into stdout) becomes bogus "tracked files" that are skipped one by one; the actual full-copy fallback only triggers when the output is empty.
- **[SMELL] `metrics.recordToolCall` never fires for `completeTask`** (`WorkerAgent.java:721` short-circuits before L984) — tool-call metrics undercount the one call every successful task makes.
- **[PERF] GateStore plan-gate wait busy-polls** `future.get(500ms)` + Redis `getAndDelete` every 500ms for up to 24h per waiting run (`GateStore.java:212-262`) — a pinned pipeline-pool thread and ~172k Redis ops/day per stuck gate.
- **[PERF] C1 parallel reads spawn a fresh virtual-thread executor per batch** (`WorkerAgent.java:1609`) — fine — but with the compactor flag ON each parallel read can fan out its own LIGHTWEIGHT LLM call concurrently (L1690), multiplying compactor spend on read-heavy turns.
- **[LAYERING] The "engine" isn't the pure seam its contract declares.** `CodeGenEngine` javadoc: "no side effects beyond the workspace (no DB writes, no SSE)". `engine/WorkerAgent` does SSE broadcasts (`broadcaster`, L101, 1815-1848), DB reads (`pipelineRunRepository`, L91-92, 424), Redis (`contextStore`), and imports `agent.LlmRouter`/`LlmRequest`, `smoketest.WorkspaceTestRunner`, `testgen.model.TestExecutionSummary`. `WorkerTaskRequest` javadocs reference `harness.SequentialExecutor` and `terminalbench.TerminalBenchRunService` (L65-66, 90-92) — the engine package documents its own upward couplings.
- **[DUPLICATION] `salvageTools` ≡ `terminalFinalizerTools`** — byte-identical bodies (`WorkerAgent.java:1541-1548` vs 1558-1565). **`runSalvageCall`/`salvageAttempt` vs `runTerminalFinalizerCall`/`terminalFinalizerAttempt`** are parallel forced→auto ladders with copy-pasted router-call + dispatch loops (L1224-1355 vs 1363-1539). **`smokeTail` truncation** duplicated (`SequentialExecutor.java:831-840` vs 1125-1133). **Deliverable path-sanitising regex + limit(8)** duplicated (`WorkerAgent.java:2056-2061` vs 2209-2214).

## 4. Model/LLM touchpoints (for the routing redesign)

**Complexity→tier→model routing (BUILD)** — `SequentialExecutor.tierConfigFor` (`harness/SequentialExecutor.java:1192-1340`):
- `LOW → AgentTier.LIGHTWEIGHT` (60 iters / 4,096 maxTokens / warn 10 / force 16 / 30-min wall-clock); `MEDIUM`+null+default `→ WORKHORSE` (120 / 8,192 / 16 / 28 / 45-min); `HIGH → PLANNING` (180 / 16,384 / 24 / 40 / 75-min). Project runs (`projectId != null`): iters ×2, wall-clock ×2, force LOW→24 MEDIUM→36 (warn unchanged). Pinned by `SequentialExecutorTierConfigTest`.
- Model resolution: `modelResolver.resolve("WorkerAgent", LlmProvider.valueOf(runProvider.toUpperCase()), tier)` (L1310-1313) — the hardcoded agent-name string `"WorkerAgent"` + an explicit tier override, so the YAML `agent-tier-map.WorkerAgent: WORKHORSE` row (`application.yml:352`) is **bypassed** for BUILD workers (it only matters for 2-arg `resolve` callers).
- **Failure fallback** (L1323-1339): any resolve exception → `TierConfig(runProvider, runModel, …)` — the *run-level* model regardless of complexity, silently un-tiering the task (and `model=null` from the cross-provider path → the BUG above).

## 7. Security notes (parked)

- **PAT in exception text**: `WorkspaceInitService.runGitStrict` masks the command but not the git output appended to the thrown message (`WorkspaceInitService.java:396-406`); clone failures echo `https://oauth2:<pat>@…` → logs. Also the PAT-in-URL pattern itself (L127-130, 298-301) means the token is present in process argv (visible to `ps` on the box) for the clone duration.
- **Deliverable-gate shell construction**: `missingDeliverables` builds a shell command by string concatenation but filters paths to `/[A-Za-z0-9._/-]+` first (`WorkerAgent.java:2055-2066`) — injection-safe as written; the same filter is duplicated in `readDeliverableContext` (L2209-2229). Keep the two in lockstep.
- **Critic prompt ingestion**: `readDeliverableContext` cats remote-container files / git diff straight into an LLM prompt (L2207-2243) — a hostile workspace can prompt-inject the critic; blast radius is bounded (critic is one-shot, fail-open, gaps only feed back as a user message).
- `VendoredPathGuard.runGit` strips env to PATH/HOME (good); `WorkspaceInitService`'s ProcessBuilders inherit full env (PATs of other subsystems, API keys, etc. exposed to git child processes).
- `GateStore` DB fallback trusts `gate_record.status` without tenant scoping at this layer (guarded upstream by controller access checks; noted only because the gate key is guessable `gate:plan:<runId>`).
