## 2. Findings

### Real bugs first

1. **[BUG] Hand-rolled JSON escaping breaks `contract_version.inline_content` for any multi-line contract — which is virtually all of them.** `contracts/detection/ContractDetectionService.java:182-185` builds the JSONB payload as `"\"" + content.replace("\\","\\\\").replace("\"","\\\"") + "\""` — it escapes backslash and quote but **not control characters**. A newline inside a JSON string is illegal JSON, so Postgres rejects the `jsonb` insert for every real (multi-line) OpenAPI/proto/SDL file. Because `upsertContract` is **not transactional** and saves the registry row first (`:175`) then the version row (`:187`), the failure leaves `contract_registry.current_registry_version` bumped with **no matching `contract_version` row** — permanent drift between registry and history, and the catch at `:229` reduces it all to a `log.warn`. Knock-ons: planner injection shows "(content not inlined — use getContract tool to fetch)" (`ContractInjectionService.java:133`) and the breaking-change gate skips the contract (`RunOrchestrator.java:2548`, `prev == null → continue`). For the rare single-line content that *does* insert, the stored value is the **quoted/escaped** form, which feeds bug #2. Fix: `objectMapper.writeValueAsString(content)` (or store TEXT), and make the upsert atomic.

2. **[BUG] Breaking-change comparison compares raw disk content against the JSON-escaped stored form — `now.equals(prev)` can never be true.** `integration/RunOrchestrator.java:2543-2557` takes `prev` from `ContractVersion.getInlineContent()` (the quoted/escaped string from #1, when it exists at all) and `now` from `Files.readString(...)`. Even an unchanged contract mismatches (`"\"openapi: 3.0\"" != "openapi: 3.0"`), so with the flag ON every contract with an inline version becomes an `IntendedChange` on every run, and the classifiers diff escaped-vs-raw text (garbage in). The deterministic E2.7 chain is structurally fine; the data layer feeding it is wrong. (Flag default OFF is the only reason this hasn't burned anyone.)

3. **[BUG] Drift detection can never fire organically — the snapshot it compares against is only written by the drift *fix* action.** `DriftDetectionService.runCheck` (`drift/DriftDetectionService.java:113-122`) reads `.executespec/contracts/produced/<name>.<ext>`; grep shows the only writer of that path is `ContractDriftController.refreshFromSource` (`drift/ContractDriftController.java:110-125`) — the *resolution* endpoint. Detection (`runForRepo`) never seeds `produced/`, and the coverage controller Javadoc's claim that rescan "opens the writer chain to repush to .executespec/contracts/produced/" (`coverage/ContractCoverageController.java:37-38`) is false — rescan only writes DB rows. Net: every drift check returns "no .executespec/ snapshot yet (bootstrap pending?)" until a user manually runs refresh-from-source once per contract. The feature is circular: you must run the fix before the detector can ever detect.

4. **[BUG] Contract name collisions silently merge distinct contracts and cause version ping-pong.** `DetectorUtils.basenameWithoutExtension` (`detection/DetectorUtils.java:37-43`) keys contracts by basename-before-first-dot, and the upsert keys on `(repo_id, name)` ignoring type (`ContractDetectionService.java:143-144`). `api/v1/openapi.yaml` and `api/v2/openapi.yaml` both become name `openapi`: each rescan processes both, sees a different hash each time, and bumps `currentRegistryVersion` twice per scan forever — version churn, `CONTRACT_VERSION_CHANGED` activity spam, and `detectedPath` flip-flopping. Cross-type collision is also possible (`user.schema.json` + `user.proto` → name `user`): the second detector "bumps" a row whose `type` stays the first detector's type.

5. **[BUG] Migration apply from the live UI always fails with 400 for the 3 recipes with required slots.** `composer/SlotValidator.validate:43-46` flags `required && blank` with **no consideration of the slot's default**, and `MigrationOrchestrator.apply` validates (`:124-134`) *before* folding defaults into the composer (`:144-149`). The IDE apply modal sends no slot values at all (`IdeDiscovery.tsx:1467` — `{projectId, repoIds}` only; no slot inputs rendered). `express-to-fastify`, `mongoose-to-prisma`, `webpack-to-vite` all declare `required: true` slots **with defaults** (catalog YMLs) → guaranteed `400 slot validation failed: ... is required` from the only UI that can reach the endpoint.

6. **[BUG] Post-apply navigation dead-ends: `/plan/{executionRunId}` loads `GET /api/runs/{id}` with an ExecutionRun id.** `IdeDiscovery.tsx:1304-1307` navigates to `/plan/${runId}` with `resp.executionRunId`; `IdePlan.tsx:27` calls `api.getRun(runId)` which resolves against `pipeline_run` — an `execution_run` id 404s. Root cause on the backend side: `MigrationOrchestrator` Javadoc (`:77`) still promises "redirect the caller to `/v3/runs/<runId>`", a chrome that was deleted; nothing re-pointed the contract when V3 went away.

7. **[BUG] Cross-project IDOR on invite + share-link revoke.** `ProjectInviteController.revoke` (`sharing/controller/ProjectInviteController.java:93-102`) asserts write on the **path** `projectId`, then `ProjectInviteService.revoke(inviteId, actor)` (`service/ProjectInviteService.java:312-326`) loads the invite by UUID and **never compares `invite.getProjectId()` to the authorized project**. Identical shape in `ProjectShareLinkService.revoke` (`service/ProjectShareLinkService.java:112-125`). A user with write access to *any* project of their own can revoke any other org's invite/share-link given its UUID. UUIDs are unguessable, so exploitability is low — but it's the exact authz-on-path/action-on-unscoped-id bug class the `emergencyOverride` endpoint explicitly fixed (`StandardsOverrideController.java:78-81` does the ownership compare). Same-shape contrast makes this clearly an oversight, not a decision.

8. **[BUG] Cross-tenant read of another org's standards via caller-supplied `orgId`.** `standards/report/StandardsComplianceController.java:50-62` guards `projectId` but feeds the free `?orgId=` request param straight into `resolver.resolve(orgId, projectId, null)` → `orgStandardRepo.findByOrgId(orgId)`. Any authenticated user with read access to *their own* project can enumerate any other org's standard ids, descriptions, severities, enforcement types. The comment above the guard ("leaks the org's engineering standards … tenant-bound") shows the intent; the binding of `orgId` to the project's actual org was never implemented (`RunStandardsEnforcer.java:78-83` does it correctly server-side).

9. **[BUG] Spring self-invocation: boot-time catalog reseed runs without its transaction.** `migration/seeder/MigrationRecipeSeeder.onStartup` (`:60-68`) calls `this.reseed()` — the `@Transactional` on `reseed()` (`:70`) is bypassed at `@PostConstruct` time. The repos patched around it with per-method `@Transactional` on `deleteByRecipeId` (acknowledged in `MigrationVariantRepository.java:19-24`), so each delete/save auto-commits — meaning a mid-recipe failure leaves a recipe with its variants/slots deleted and not re-inserted until the next boot. Low probability, real window; the admin `/reseed` path is fine (proxied).

10. **[BUG] ProcessBuilder pipe-deadlock pattern in both CLI runners: stdout is read only after `waitFor`.** `contracts/breaking/CliBreakingChangeRunner.java:73-81` and `standards/enforcement/lint/LintProcessRunner.java:49-57` block in `waitFor(timeout)` *before* draining stdout. If the child writes more than the OS pipe buffer (~64KB) it blocks on write, the parent blocks until timeout, and the run is misreported as "CLI exceeded Ns timeout". An `eslint --format json` over a whole repo or a large `oasdiff` diff trivially exceeds 64KB. `lint/LintPass.applyOne` (`:129-138`) has the same shape (mitigated by `redirectErrorStream(true)` + mostly-quiet formatters, but `mvn spotless:apply` failure output can blow it). Fix: stream-gobble concurrently or use `redirectOutput(File)`.

11. **[BUG] `StaleScmCleanupJob` re-attempts the same branch deletions every day, forever.** `compliance/StaleScmCleanupJob.deleteStaleBranches` (`:155-203`) selects every terminal PR row older than 30 days with an `executespec/*` head branch — there is **no "branch deleted" marker on `PullRequestRecord`** (grep-verified), so rows that were already processed (or whose branch never existed) are re-fetched and re-DELETEd against the GitHub API every night, bounded only by `MAX_PER_PASS=1000`. As terminal PRs accumulate this becomes 1000 pointless GitHub calls/day. Also both sub-sweeps do `prRepo.findAll()` (`:92`, `:158`) — full-table load into heap, twice (see PERF).

12. **[RISK] `DataRetentionService.runRetentionSweep` has no `@SchedulerLock`.** Every other scheduled job in this batch (`ActivityFeedPartitionJob:55`, `ActivityFeedRetentionJob:60`, `StaleScmCleanupJob:73`, `WorkspaceDiskCleanupJob:96`) is ShedLock-guarded; the retention sweep (`compliance/DataRetentionService.java:69`) is not. On a multi-instance deployment the GDPR/tier sweep double-fires; deletes are idempotent-ish but `saveAll` races are possible. Inconsistency more than catastrophe.

13. **[RISK] Partial-write states in `ExecutespecFolderWriter`.** PR mode aborts mid-batch on a failed PUT (`folder/ExecutespecFolderWriter.java:257-261`) leaving an orphaned `executespec/*` branch with partial commits and no PR (never cleaned; `StaleScmCleanupJob` only deletes branches that have a PR row). DIRECT_PUSH mode (`:284-313`) is worse: it commits file-by-file straight to the default branch and aborts midway → half-applied batch on main. Callers get `Optional.empty()` either way and can't distinguish "nothing happened" from "half happened".

14. **[INCONSISTENT] Export bundle does not contain what its own controller says it does.** `export/ProjectExportController.java:48-51` ("bundles the entire .executespec/ folder (standards, ADRs, invariants, contracts, activity feed)") vs `ProjectExportService.composeBundle` — actual content is manifest, project.json, a **placeholder** members.json (`:108-114`, literally a "note" key), a contract *index* (no bodies), 90-day activity NDJSON, README. No standards, no ADRs, no invariants. The root CLAUDE.md API table makes the same overclaim. Also exports activity via the **unbounded** `findRecentForProject` (`:147`) — a busy project's 90 days could be large (synchronous byte[] response).

15. **[INCONSISTENT] `ActivityFeedController` Javadoc promises cursor pagination + role-gated admin events; neither exists.** `activity/ActivityFeedController.java:26-30` — there is no cursor param (window+limit only) and `includeAdminEvents=true` is honored for **any** project member (no ORG_ADMIN/PROJECT_ADMIN check, `:94`). Also `hasMore` (`:121`) is `entries.size() >= safeLimit` — false positive when exactly `limit` rows matched; and the 3× headroom fetch (`:78`) can under-fill the page when >2/3 of recent rows are ADMIN_TOGGLE, returning a truncated feed with `hasMore=false`.

16. **[INCONSISTENT] `PlanBreakingChangeReport` is "the plan-approval gate report" that never runs at the plan gate.** Javadoc (`contracts/gate/PlanBreakingChangeReport.java:20-32`) + `requiresTypedAck` describe pre-approval friction ("UI must show the typed-'BREAKING' confirmation and disable approve"). The only production caller composes it **post-run** in `RunOrchestrator.detectBreakingChangeIssues` (`:2564`) and downgrades everything to report-only MINOR issues (`toBreakingChangeIssues`, `severity=MINOR`); `requiresTypedAck` is logged (`:2571`) and dropped. The typed-ack UX does not exist anywhere in `frontend/`.

17. **[INCONSISTENT] Claimed-but-absent validations across sharing/standards.** (a) `ProjectInvite.invitedOrgId` Javadoc: "preserved so accept can validate even if it changes" (`entity/ProjectInvite.java:56`) — `accept()` never reads it (grep: only the write at `service/ProjectInviteService.java:211`). (b) `StandardsOverrideController.addProjectException` persists a `SEVERITY_DOWNGRADE` row without checking the new severity is actually lower (or even a valid enum) — the resolver silently rejects upgrades later at read time (`EffectiveStandardsResolver.java:141-150`), so the admin sees their override "saved" but it never takes effect, with only a server-side `log.warn`. (c) `ProjectInviteService.assertCanInvite(inviter, projectId)` — the `projectId` parameter is unused (`:108`); cross-checking the inviter against the project is left entirely to the controller guard. (d) `MigrationDryRunCache` Javadoc says the signature is major-version-only (`entity/MigrationDryRunCache.java:24-26`); the implementation is a SHA-256 of the whole stack JSON (`MigrationDryRunService.stackSignature:196-209` — its own Javadoc admits the discrepancy).

18. **[BUG] (minor) `OrgStandardController.update` NPEs on a null body.** `standards/OrgStandardController.java:125` dereferences `body.standardYaml` without the null check `create` has → 500 instead of 400.

19. **[RISK] `ExecutespecMigrationController.migrate` throws 500 on non-UUID projectId.** `folder/ExecutespecMigrationController.java:108` does `UUID.fromString(projectId)` unguarded while project ids are strings everywhere else (`length 64` columns). Also its comment "falls back to system PAT inside the writer" (`:64`) is stale — `ExecutespecFolderWriter.pat()` (`:461-463`) has no system fallback (correct post-GITHUB_PAT-removal; the Javadoc at `:107` repeats the stale claim).

20. **[RISK] Prompt-rot: injected planner text instructs the model to call tools that don't exist.** `ContractInjectionService` INDEX_ONLY mode tells the planner "Use the getContract(id, version) tool" (`injection/ContractInjectionService.java:145`) and FULL_BODY's miss-path says "use getContract tool to fetch" (`:133`) — grep confirms no `GetContractTool`/`getContract` tool exists in `tool/`. The ADR side was *fixed* for this exact issue (audit L #66, `AdrInjectionService.java:20-24` now says "the getAdr tool is not yet wired"); the contracts side was not given the same treatment. With the flag ON and >15 contracts, the planner is told to call a nonexistent tool.

21. **[SMELL] Severity/format quirks in classifiers.** (a) `OpenApiBreakingChangeClassifier.parseLines` (`:85`) uses `lower.contains("info")` — any line merely *containing* "info" is classified COSMETIC (e.g. an error mentioning `/info` path is caught by the earlier `startsWith("error")`, but warning text containing "info" is fine; the contains-match is sloppier than the other two). (b) `CliBreakingChangeRunner` writes temp files with a `.tmp` suffix (`:51-52`); `buf` (which takes *inputs*, normally directories/modules) and `graphql-inspector` (loader keyed by extension) are unlikely to accept bare `.tmp` files even when installed — meaning PROTO/GRAPHQL classification likely degrades to UNCLASSIFIED *with the CLI present*. Untestable here (CLIs not installed) but worth a spike before flipping `contracts.breaking-change.enabled`. (c) `DriftDetectionService.runCheck` inserts a **new** unresolved drift event on every check while drift persists (`:148-155`) — no dedupe against existing unresolved events; repeated "Check drift" clicks pile up rows (dismiss clears all, mitigating).

22. **[SMELL] Glob matcher accepts non-boundary matches.** `DetectorUtils.matchesGlob` compiles `**/` to `.*` with the slash consumed (`:58-62`), so `**/openapi.yaml` matches `myopenapi.yaml`. Content sniffs mostly mitigate. The same matcher is reused by `FilePatternEnforcer` for standards where a `forbidden_patterns: ["**/secrets.yaml"]` also flags `not-secrets.yaml` — false positives in enforcement.

23. **[LAYERING] `standards/enforcement` and `contracts/breaking` each own a near-identical subprocess runner.** `CliBreakingChangeRunner` vs `LintProcessRunner` — acknowledged in the latter's Javadoc ("could be unified later"). Both carry the same waitFor-then-read bug (#10), so the duplication doubled the defect. Similarly `ExecutespecFolderWriter.sha256` duplicates `DetectorUtils.sha256` byte-for-byte.

24. **[DUPLICATION] Per-controller copies of `principal(...)` / `parseUuidOrNull(...)` / `patFor(...)`.** Identical private helpers in `ContractDriftController`, `ContractConsumerController`, `ContractCoverageController`, `AdrController`, `StandardsComplianceController`, `ActivityFeedController`, `StandardsOverrideController`, `ExecutespecMigrationController` (8 copies of UUID-parse; 6 of principal-extract; 3 of PAT lookup). One `@ControllerAdvice`-level or util extraction would erase ~150 lines.

25. **[PERF] `StaleScmCleanupJob` full-table scans `pull_request_record` twice per night** (`:92`, `:158` — `findAll().stream().filter().limit()`); should be derived queries. **`ExecutespecFolderWriter.prFlow` does two GitHub `getContents` per file per write** (pre-flight compare `:220` + existing-sha lookup `:246`) — the pre-flight snapshot already carries the blob sha (`FileSnapshot.contentSha`); one call suffices. **`ContractInjectionService.consumerSummary`/`producerNameFor`** issue one `projectRepoRepo.findById` per consumer per contract (N+1 against the planner's cold-start path). **`ActivityFeedController`** post-filters event types in memory instead of pushing `eventType IN (...)` to the query (self-acknowledged at `:80-82`).

26. **[SMELL] `WorkspaceDiskCleanupJob.classify` GCS branch is a no-op.** `compliance/WorkspaceDiskCleanupJob.java:217-229` — both arms of the `gcsArchivedAt == null && gcsWorkspaceKey == null` check return `TERMINAL_OLD`; the comment narrates two different policies ("want the archiver to finish first" in the class Javadoc `:53-55`) but the code deletes in both cases. Either the guard is missing or the comments are theater.

27. **[SMELL] Tier metaphor mismatch in sharing caps.** `ProjectShareLinkService.assertCanCreate` (`:54-74`) counts active links **per project** but caps by the **caller's** tier, and a missing TierConfig yields `cap=0` → hard 429 for any tier not present in `tier_config` (fail-closed; defensible but surprising). Also `createLink` is called *after* `assertCanCreate` and there's no unique race guard — two concurrent creates at cap-1 both pass (cosmetic).

## 4. Model/LLM touchpoints

This batch makes **zero direct LLM calls** — by design everything here is deterministic. Touchpoints are indirect:
- `ContractInjectionService` / `AdrInjectionService` compose planner context blocks consumed in `RunOrchestrator.runPipeline` behind `enterprise.inject.enabled` (OFF) — contracts block currently injects the JSON-escaped `inlineContent` form (bug #1) so even when flipped on, the planner would see `\"`-escaped text; index mode references a nonexistent tool (#20).
- `LlmReviewEnforcer` was designed to extend the reviewer's prompt + parse its JSON verdicts — never wired (dead).
- `StandardsPromptComposer` was designed to tell the LLM about standards pre-generation — never wired (dead). Net: standards are enforced only *after* code exists; the model is never told what standards to satisfy, which inverts the package's own stated design ("the LLM agents need to *know about* the standards so they generate compliant code in the first place").
- `ContractDiff.Confidence.LLM_DERIVED` exists as an enum value; no LLM fallback classifier exists — only DETERMINISTIC/UNCLASSIFIED are ever produced.
- `migration_recipe.ai_fallback_prompt_path` columns are seeded but nothing loads those prompts (the W8 hybrid-AST/AI-fallback path isn't built).

## 7. Security notes (parked)

- #7 (revoke IDOR) and #8 (orgId cross-tenant standards read) above are the two concrete items.
- `ProjectSharePublicController` is solid for an unauthenticated surface: 410 on revoked/expired, surface pinning, load-bearing `assertSameProject` returning 404-not-403, DTOs token-free. View-counter `recordView` is an unauthenticated DB write per hit — a hot link is a write-amplification vector (no rate limit visible at this layer; `RateLimitFilter` coverage of `/api/shared/**` not verified in this batch).
- `GET /api/invites/preview?token=` (public) discloses invitee email + projectId + role for a valid token — acceptable for the signup landing flow, but it makes the 64-char token the only secret protecting a PII pair; tokens go through email, so standard email-compromise caveats.
- Standards lint enforcement executes `npx eslint` / `checkstyle -c <repo-config>` **in the customer's cloned workspace** (`LintProcessRunner.run` with `pb.directory(repoRoot)`, no sandbox, no env stripping — contrast `LintPass.isSecretEnvVar` which *does* strip secrets for formatters). ESLint loads plugins/configs from the repo → arbitrary code execution on the host with the JVM's env when `standards.enforcement.enabled` flips ON for a hostile repo. `LintPass` (default ON) has the same property for `mvn spotless:apply` / `./gradlew spotlessApply` / `npx prettier` (build scripts execute), though it strips secret env vars; it does not consult `ShellSandboxPolicy` or the cleanroom container. Worth routing both through the existing sandbox machinery before any default-ON expansion.
- `ExecutespecFolderWriter.requireFolderRoot` is a `startsWith(".executespec/")` check — `.executespec/../foo` passes the prefix check; protection relies on GitHub's API rejecting `..` path segments. All current callers build paths from controlled inputs (contract names are slash-free basenames), so theoretical today; a cheap normalize-and-recheck would close it.
- `ActivityFeedPartitionJob`/`RetentionJob` build DDL by string concat — inputs are regex-validated (`SAFE_SUFFIX`) / pg_inherits-derived respectively; fine.
- `BootstrapService.checkPatScopes` fails *open* on network errors and fine-grained tokens (documented, reasonable).
- `ProjectExportController` allows `BILLING_ADMIN` to pull the full project bundle — deliberate per M-012 comment, but billing-role-can-export-code is a curious grant to revisit.
