- **SWE-bench `/run`**: real `submitRun(runMode=BUILD, source="swebench-codegen", repoMode=NONE, executionMode=PROTOTYPE, skipApproval=true)`; `PipelineEvent.RunStarted` is published synchronously on the caller thread (RunOrchestrator.java:664-669) so the ThreadLocal `PENDING` recipe handoff to `onRunStarted` works; the listener does pull(skip-if-present)→create→`docker cp /testbed/.`→`docker run -d --rm --network none -v ws:/testbed`→`SwebenchContainerStore.put`. ## 2. Findings

### Real bugs first

1. **[BUG] `@Async` on all three bench capture loops is dead — self-invocation; "202 Accepted" endpoints actually block until run-terminal.**
   `BenchmarkRunService.submit` calls `captureOnTerminalAsync(...)` directly on `this` (BenchmarkRunService.java:331 → :368); same in `ProgramBenchTaskService.java:339 → :344` and (dead) `SwebenchTaskService.java:325 → :331`. `@EnableAsync` is default proxy mode (ExecutespecApplication.java:39; `AsyncObservabilityConfig` is a plain `AsyncConfigurer`), so a self-invoked `@Async protected` method runs **synchronously on the HTTP request thread**. Consequences: `POST /api/admin/benchmark/run` returns `ResponseEntity.accepted()` (BenchmarkController.java:59) only **after** the 5s-poll loop reaches terminal or the wall timeout (default 60 min) — a Tomcat thread is held per run (bounded only by the semaphore, default 4 + 180s queue wait); the in-code comments ("the async capture's finally frees it", BenchmarkRunService.java:336-341) and the javadoc ("Returns the runId so the caller can poll", :227-229, ProgramBenchTaskService.java:250-253) describe behavior that does not exist; and `AsyncAllowlistTest.java:157-166` pins all three methods as approved `@Async` methods, codifying the fiction. Either make the call go through the proxy (self-injected bean / separate component) or drop `@Async` and document the synchronous contract.

2. **[BUG] Cleanroom-setup failure does NOT stop the run — the FAILED mark is clobbered and the pipeline burns tokens on a junk workspace.**
   `BenchmarkRunService.onRunStarted` catch-block sets status FAILED + `BENCH_SETUP_FAILED` (BenchmarkRunService.java:196-212) "to avoid poisoning benchmark stats", and `ProgramBenchTaskService.onRunStarted` does the same (ProgramBenchTaskService.java:220-232). But the listener runs *before* `pool.submit(runPipeline)` (RunOrchestrator.java:669→694) and `runPipeline` has **no FAILED-status guard**: it proceeds, overwrites status (`updateStatus(runId,"WORKING")` RunOrchestrator.java:1368), runs classifier→planner→worker against the host-side, container-less workspace (tools fall back to host shell because no containerId was registered), and `terminate(...)` preserves only CANCELLED (RunOrchestrator.java:2250-2257) — so the run ends COMPLETE/PARTIAL with a meaningless diff and real LLM spend. Exactly the false-stat case the mark was supposed to prevent. Fix: check for the setup-failure marker at pipeline start (or have `submit` abort when the listener flagged failure).

3. **[BUG] Diff-strip + blind-spec divergence between the two SWE-bench paths — the “preferred” `/generate` path emits the polluted diffs the `/run` path fixed.**
   `BenchmarkRunService.captureSubmission` excludes build-config/test/repro paths (pyproject/setup.py/setup.cfg/tox.ini/MANIFEST.in/requirements*/.github + tests/ + conftest + repro/tmp/scratch — BenchmarkRunService.java:449-465). `BenchmarkGenerationService.captureDiff` has only the original 7 excludes (BenchmarkGenerationService.java:264-267) — none of the strip set. The empirically-load-bearing fix (the harness’s own comment: “~38-47% of unresolved diffs were sabotaged by non-source pollution”) lives on one capture site only. The blind specs also drifted: BenchmarkRunService.synthesizeBlindSpec has exact-public-API naming + `/tmp/repro.py` reproduce-first + verify steps (:536-568); BenchmarkGenerationService.synthesizeBlindSpec is the older, weaker 4-step version (:344-355). Any `/generate`-based measurement is not comparable to `/run` numbers.

4. **[BUG][working tree] Uncommitted `FIREWORKS` provider breaks the build’s arch test.**
   `LlmProvider` now has 6 constants (FIREWORKS added, LlmProvider.java diff), but `FailoverOrderEnumAlignmentTest.testEnumItselfContainsExpectedProviders` asserts `LlmProvider.values().length == 5` (FailoverOrderEnumAlignmentTest.java:134-136). `mvn verify` on this tree fails. The test message itself instructs updating yaml + the count.

5. **[BUG][working tree] Every Fireworks benchmark run will record $0 cost.**
   `FireworksModelMapper` allow-lists `qwen3-coder-fw / deepseek-v3-fw / deepseek-v3p1-fw / kimi-k2-fw / glm-4p6-fw` (FireworksModelMapper.java:27-33) and `LlmRouter.callFireworks` dispatches them, but **no `model-matrix.models` entries exist for any of them** (application.yml diff adds only the OpenRouter `mimo-v2.5-pro`). `RunCostTracker.priceCall` returns `0.0` with a debug-level log when pricing is missing (RunCostTracker.java:~673-677). So the planned “TB 2.0 across all configured models” sweep would book tokens but $0.00 for the whole Fireworks leg — poisoning `benchmark_run.cost_usd`, `/api/runs/{id}/cost`, and any cost-per-resolved comparison. Also `priceCall`’s gateway special-case handles only `"openrouter"`, not `"fireworks"`, so even adding vendor-keyed pricing rows wouldn’t be found without a fireworks-keyed row. The mapper javadoc itself says slugs are unverified (“refine if one 404s post-smoke”).

6. **[BUG] eval/v2 PLANNING cases send an unsubstituted prompt template — the “production-shaped” claim is false for the planning tier.**
   `PlanningCases.plannerCase` loads `prompts/outline-planner.md` **verbatim** as the SystemMessage (PlanningCases.java:112-114), but the file contains `{{SPEC}} {{CLASSIFICATION}} {{MAX_TASKS}} {{WORKSPACE_SUMMARY}} {{PROJECT_MEMORY}} {{PROJECT_BRIEF}} {{REFERENCE_DOCS}} {{CONTRACTS}} {{PROJECT_ADRS}} {{TDD_MODE_BLOCK}}` markers (outline-planner.md:49,121-139) that are never substituted; the spec is then duplicated in a separate user message. The model sees literal `- Spec: {{SPEC}}` and `max tasks: {{MAX_TASKS}}` while the validator scores task-count bands. Scores still come out (models cope), but planning-tier numbers measure a malformed prompt, not production. Contrast `LightweightCases.loadClassifierPrompt` which substitutes all 6 markers manually (LightweightCases.java:160-166). The submitOutline shim also re-declares the schema with all `description` fields dropped (PlanningCases.java:219-271 vs `OutlinePlannerAgent.SUBMIT_OUTLINE_SCHEMA`’s enum-bearing descriptions at OutlinePlannerAgent.java:74-137) — same keys, weaker guidance.

7. **[BUG] `run()` shell helper can deadlock on >64KB output → silent empty patch.**
   All four copies (`BenchmarkRunService.java:574-592`, `BenchmarkGenerationService.java:360-377`, `SwebenchTaskService.java:650-668`, `ProgramBenchTaskService.java:572-590`) do `p.waitFor(timeout)` **before** `readAllBytes()` with `redirectErrorStream(true)`. A child producing more than the OS pipe buffer (~64KB) blocks on write → `waitFor` expires → `destroyForcibly` → result is treated as failure. On the diff-capture path (`run(preCmd, 120)` → `diff.exit()==0 ? output : ""`, BenchmarkRunService.java:476-477; BenchmarkGenerationService.java:278-279) a large agent diff silently becomes an **empty `model_patch`** in preds.json → counted unresolved with no error. Chatty `docker pull` output can hit the same wall. Fix: stream-drain the output concurrently (or `redirectOutput(File)`).

8. **[RISK] Tracking-layer ingest is not concurrency-safe (idempotency only holds serially).**
   `BenchmarkTrackingService.upsertTaskResult` is load-all-then-scan check-then-insert (BenchmarkTrackingService.java:161-167): two concurrent `TASK_SCORED` for the same (task, attempt) — a plausible verifier retry — both pass the exists check; the second insert hits `uq_benchmark_task` → `DataIntegrityViolationException` → HTTP 500, not the documented no-op (the controller maps only `IllegalArgumentException` to 404, BenchmarkTrackingController.java:127-129). Event `seq` is `count(*)` at write time (:209) with no unique constraint on (run_id, seq) in V236 — concurrent events get duplicate seq values, making replay order ambiguous. Also: first-write-wins means a re-published *corrected* reward for the same attempt is silently ignored. Low stakes today (single Harbor publisher), but the “idempotent” contract is over-claimed.

9. **[RISK] TB wall-clock budget can still blow Harbor’s 1350s in the worst case.**
   The worker checks wall-clock only at iteration boundaries (WorkerAgent.java:458) and `DEFAULT_WALL_CLOCK_SECONDS=900` (TerminalBenchRunService.java:62) leaves a 450s buffer — but a remote tool call dispatched just before the boundary may block up to `executespec.remote-tool.timeout-ms` = **600s** (RemoteToolDispatcher.java:51-58). 900 + 600 = 1500s > 1350s, i.e. the configured tool timeout alone exceeds the buffer the comment claims covers “one slow in-flight tool … turn”. Either cap the remote-tool timeout for TB runs or compute it from the remaining wall budget.

10. **[RISK] TB terminal cleanup ordering can leak the remote session.**
    `runWorker`’s `finally` runs `finalizeTerminal(...)` **before** `remoteToolDispatcher.unregister(runId)` (TerminalBenchRunService.java:311-314). If `finalizeTerminal` throws (DB/Redis down — `stateStore.findRun`/`costTracker` are not wrapped), `unregister` and `deleteTree` are skipped: the session map entry leaks, `isRemote(runId)` stays true, and an in-flight client tool call blocks for the full 600s. The code’s own invariant (“unregister MUST run on every terminal/exception path”) needs a nested try/finally.

11. **[RISK] `RemoteToolDispatcher.register` silently replaces an existing session** (RemoteToolDispatcher.java:67-70): old pending futures are stranded (the `complete()` lookup finds the new Session → callId unknown → original `dispatch` waits out the full timeout). Unreachable with UUID runIds today; one `putIfAbsent` + log would close it.

12. **[INCONSISTENT] preds.json / DB model attribution can lie for BUILD-mode bench runs.**
    `captureSubmission` writes `model_name_or_path = "executespec-build/" + plannerModel` (BenchmarkRunService.java:483-484) and `submitRun` persists `workerModel = <run-level default or pin>` (RunOrchestrator.java:628), but in BUILD mode the actual worker model is complexity-routed per task (LOW→LIGHTWEIGHT) unless an ENTERPRISE pin overlays all tiers. With an explicit `modelName` the pin works (the bench org is bootstrapped ENTERPRISE — SwebenchBootstrap.java:60, gate at RunOrchestrator.java:557-565 + 899-933); **without** one, the recorded model is not necessarily the model that wrote the code. Note the pin is also *silently* dropped for non-ENTERPRISE owners (debug log only, RunOrchestrator.java:926-932) — a misconfigured bench org would quietly benchmark the wrong model.

13. **[INCONSISTENT] `BenchmarkController.SubmitRequest` carries `projectId`/`selectedRepoIds` for project-mode eval, but `/generate` silently drops them** (BenchmarkController.java:75-85 passes only instanceId/provider/model). Either wire them or reject them.

14. **[INCONSISTENT] ProgramBench’s claimed safety net doesn’t exist.** The `PENDING` javadoc says a “Defensive fallback: onRunStarted validates that PENDING is set for any runId we expect to be programbench-driven … and panics if the contract is violated” (ProgramBenchTaskService.java:90-96). There is no recipe map and no panic — `onRunStarted` just returns on null (:136-137). The documented protection against someone making `RunStarted` async is fictional (and no test pins the synchronous-publication contract, as the same javadoc admits).

15. **[INCONSISTENT] Raw-string LLM prompts violate the project’s own MUST-rule** (“LLM prompts: external files in prompts/*.md”): `TB_SYSTEM_PROMPT` (TerminalBenchRunService.java:134-202, ~70 lines), `synthesizeBlindSpec` ×2 (benchmark), `synthesizeUserRequest` (ProgramBenchTaskService.java:442-514, SwebenchTaskService), `WorkerTestController`/`ReviewerTestController` system prompts. The TB prompt is the most-tuned prompt in the TB program and the least visible/reviewable.

16. **[INCONSISTENT] `NativeToolsTestController` uses field injection** (`@Autowired(required=false)` + `@Value` fields, NativeToolsTestController.java:58-73) — the codebase’s explicit MUST-NOT. Also its javadoc says “Will be removed once LlmRouter is in place” (:43) — LlmRouter has been in place for months.

17. **[INCONSISTENT] Profile/annotation asymmetry on the `/api/v2/test/**` surface**: the 9 test controllers are `@Profile({"local","dev"})` while `TerminalBenchController` + `BenchmarkTrackingController` add `"benchmark"`; `BenchmarkTrackingController` carries a class-level `@PreAuthorize` while `TerminalBenchController` relies solely on the SecurityConfig URL matcher. Both end up SUPER_ADMIN (SecurityConfig.java:242-243), but the inconsistency invites a future controller to be added outside the matcher with no annotation.

18. **[DUPLICATION] The cleanroom/capture stack is copy-pasted 4× and has already drifted.** pull→create→cp→run→cid-last-line-parse + poll-to-terminal + `ShellResult run()` + `isTerminal()` exist in `BenchmarkRunService`, `BenchmarkGenerationService`, `SwebenchTaskService`, `ProgramBenchTaskService`; drift instances: skip-pull-if-present exists only in benchmark/gen (SwebenchTaskService still unconditionally pulls with a 1200s budget, :120); diff-strip only in BenchmarkRunService (finding 3); `isTerminal` triplicated. `deleteTree()` is additionally copy-pasted in 5 test controllers + TerminalBenchRunService + TierEvalRunner.cleanup. One `BenchSandbox` helper would erase ~400 duplicated lines and the drift class.

## 4. Model/LLM touchpoints (bench adapters — exhaustive; feeds the TB-2.0-across-models plan)

**Server-side env vars (the ONLY ones the backend reads, all TB gates):** `ES_TB_VERIFY_GATE`, `ES_TB_DELIVERABLE_GATE`, `ES_TB_CRITIC` — default ON, read **once at class load** (`static final`, TerminalBenchRunService.java:77-95) → JVM restart to change. `ES_PROVIDER`/`ES_MODEL`/`ES_BASE`/`ES_MAX_ITERS`/`ES_PAT` are **client-side** (Harbor adapter in `~/tbench`, not in this repo); grep confirms no Java code reads them.

No server default, **no `ModelResolver`, no YAML/matrix validation, no ENTERPRISE gate** — any string is accepted; an unknown provider throws at LlmRouter dispatch, an unknown model 404s at the provider API. `maxIterations` request field is **floored** to 120 (`normalizeMaxIterations` — you cannot run fewer). Fixed knobs: wall clock 900s (constant), stagnation warn 16 / force 64, artifact deadline 32, temperature 0.0, `forceToolChoiceOnSalvage=true`. Tool round-trip: `executespec.remote-tool.timeout-ms` (default 600000). Cost: `workerModel` persisted; **pricing requires a `model-matrix.models` entry for the exact id** — else $0 (finding 5).

## 6. Test coverage

- **benchmark/ (both concerns): 0 tests.** The tracking layer’s ingest state machine (idempotent upsert, resolved%/cost recompute, SUBMISSION_* transitions, unknown-type passthrough) is pure-logic and trivially unit-testable — highest-value gap. The harness’s diff-strip exclude list and `synthesizeBlindSpec` content (both empirically load-bearing) are pinned by nothing, which is exactly how finding 3’s drift happened.
- **swebench/ programbench/: 0 tests** (incl. the cid-last-line parse that fixed a real arm64 bug — unpinned).
- **terminalbench/: 1 test** (`TerminalBenchDeliverableExtractTest`, 9 good cases for both regexes) — env-sensitive (finding 27). No test for `normalizeMaxIterations`, finalize ordering, or session unregister.
- **eval/: 0 tests** — scorers (`EvalScorer` curves, `LlmJudgeValidator.parseJudgeResponse`, the v2 case validators) are deterministic functions begging for unit tests.
- **test/: 0 tests** (they *are* manual tests; fine).
- **arch/: strong.** AccessGuardCoverageTest (forward-protective, empty legacy set, write-guard rule + excluded local helpers), AsyncAllowlistTest (bidirectional drift), ApiContractTest (frontend URL ↔ backend route, with depth-aware template-literal neutralisation), FailoverOrderEnumAlignment (yaml↔enum), AnthropicModelAccess (BYOK regression), folder-writer caller allowlist, InvariantCheckerTest. Caveats: AccessGuardCoverage reads only `value()[0]` of mappings (a `path=`-attributed or multi-path mapping would evade it — currently zero such usages, verified by grep) and AsyncAllowlistTest pins methods whose `@Async` is dead (finding 1) — the allowlist verifies lazy-collection safety, not that async actually engages.

## 7. Security notes (parked)

- `BenchmarkController` + `ProgramBenchController` have **no `@Profile`** — registered in prod, protected by `/api/admin/**`→SUPER_ADMIN + the `enabled=false` flags (503). Tracking + TB controllers are additionally profile-gated. Acceptable; the asymmetry is finding 17.
- Bench bootstraps create **SUPER_ADMIN users with empty password hash + verified email** (`SwebenchBootstrap.java:77-84`, `ProgramBenchBootstrap.java:83-87`). BCrypt match against "" fails, so not logn-able today, but a standing SUPER_ADMIN principal row on any env with `*.bootstrap=true`; would become live if any alternate auth path (magic link / password-reset to that mailbox) applies. Consider `status=DISABLED` or a non-login role.
- Shell command interpolation: `instanceId`→image is constrained by `loader.findById` (must exist in the dataset) before use; ProgramBench `taskId` flows into `tasksDir.resolve(taskId)` (path traversal possible, e.g. `../`) and then into a `sh -c` docker command (ProgramBenchTaskService.java:419, 439) — SUPER_ADMIN-only input, but unsanitized; cheap to validate `[A-Za-z0-9_-]+`.
- `RemoteToolController` correctly requires run-write access; callIds are UUIDs.
- Tracking ingest accepts arbitrary `payload` JSON persisted + re-broadcast verbatim to the operator dashboard (XSS depends on frontend rendering; operator-only audience).
- `swebench`/`programbench` flags are `@ConfigurationProperties`, not `FeatureFlagService` — deliberate (boot-time infra switches), noting it against the “flags via FeatureFlagService” convention.
